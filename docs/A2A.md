# Agent 之间委派（A2A）：子集语义

> **状态（2026-11-12）：P0–P2 与 P3-a、P3-b 均已实现。** P0 = 只读同步子调用，
> P1 = 引用传递，P2 = 写操作委派（审批链 `delegated_from` / `delegation_depth` + 逐跳复核），
> P3-a = 委派预算按 Agent 可配，P3-b = `/observability/agents` 的 `delegated_turns`。
> 本文的规则未变，只有 §4 的一处推导与 §9 的复核顺序在实现时被修正（见对应小节）。
> **P3 全部完成**（P3-c 做的是按会话保留的产物；跨会话取用是另一个产品决策）。
> 编号曾经错开过，现以本文 §13 为准。

## 0. 一句话

委派必须**单调收窄**：被委派方的边界是委派方的子集。判定只做一件事——
禁止变宽，不传递权限。

## 1. 为什么委派危险

委派是**权限放大器**的教科书形态。A 把自己的能力交给 B，若继承规则不严，
下面这条链会在没人察觉的情况下成立：

```
只读 Agent A → 委派给 B（可写）→ 委派给 C（能执行代码）
```

三个 Agent 单独看都没问题，A 的 `can_write=false` 在界面上也清清楚楚。
但一次委派就把只读绕成了可写。事后查审计，看到的是「C 执行了写操作」，
而 C 本来是允许写的——**没有任何一条记录说不该走到这里**。

所以本文的核心不是「怎么让 A 调 B」，而是「怎么让 A 只能调一个不比它更宽的 B」。

## 2. 先把三种「多智能体」分开

| 形态 | 含义 | 本设计 |
|---|---|---|
| 编排 orchestration | 流程写死，A 之后一定跑 B | 声明式做，见 `ORCHESTRATION.md`：图是配置、解释器是代码，每次调用仍走本文件的边界判定 |
| 委派 handoff | 运行时把一件事交给另一个 Agent，等它做完 | **只做这种，同步子调用** |
| 协商 debate | 多个 Agent 同时看一个问题，再合并 | 不做：单机跑并行 Agent 会先把时延打爆 |

「同步子调用」的意思是：A 的工具调用里跑一次 B 的完整执行图，拿到结果后**控制权回到 A**，
由 A 决定怎么表述。不是把会话交给 B（那样用户会突然在跟另一个角色说话，而 A 的历史还在库里）。

## 3. 子集判定的形式定义

记父边界 `A`、子边界 `B`。`B ⊆ A` 成立当且仅当：

### 3.1 `allowed_tools`

| `A.allowed_tools` | `B.allowed_tools` 合法取值 | 说明 |
|---|---|---|
| `None`（不收窄） | 任意（`None` 或任意数组） | A 没有设上界，B 怎么设都是子集 |
| 数组 | `None` **或** `B ⊆ A` | `None` 合法，见下 |
| `[]`（一个都不给） | 只能是 `None` 或 `[]` | 实际效果都是「一个都没有」，因为逐层求交 |

**`B` 为 `None` 为什么安全。** 因为最终权限是逐层求交：`人 ∩ A ∩ B`。
B 写 `None` 的含义是「我不额外收窄」，而不是「我放开」——A 那一层还在。
把 `None` 当成越权是常见误解，代价是每建一个 Agent 都要把父清单抄一遍，
抄漏一个就变成真的越权。

### 3.2 `can_write`

`B.can_write = True` 要求 `A.can_write = True`。反向永远安全。

这一条不能靠 `allowed_tools` 兜住：`can_write=false` 挡的是**一整类风险等级**
（`WRITE`/`EXECUTE`/`DESTRUCTIVE`/`EXTERNAL`），而不是名单里的某几个名字。
A 只读、B 可写，即使 B 的工具清单是 A 的子集，B 仍然能写——因为 `can_write` 才是那道闸门。

### 3.3 `allowed_skills`

同 3.1。技能不带权限，但它带作业步骤；A 被收窄到不用某套步骤，B 不该把它带回来。

### 3.4 判定要落成一份函数

`agent_subset(sub, super) -> tuple[bool, str]`，返回违反的是哪一条。
不要在两个地方各写一遍（配置时一处、执行时一处），否则一定会出现两处判断不一致的缝——
`agent_denial()` 当初就是为了这个才被抽成单一入口的（`docs/AGENTS.md` §5）。

## 4. 有效权限仍然是 `人 ∩ A ∩ B`

不需要任何「边界传递」机制。原因：网关在执行时本来就按**当前 Agent 的边界**判断
（`_check_permissions`），B 执行工具时用的是 B 的边界。委派要做的事只有一件：
**保证 B 不比 A 宽**。

这条推论让实现小得多——不必把 A 的 `allowed_tools` 序列化进 state 传给 B，
也不必担心「传丢了怎么办」。传丢了只会更严（B 用自己的边界），不会更宽。

**修正（2026-11-12，实现时发现）**：`人 ∩ A ∩ B ≡ 人 ∩ B` 只在 **B 显式收窄**时成立。
`B.allowed_tools = None` 的含义是「我不额外收窄」，这时 `人 ∩ A ∩ B` 是 `人 ∩ A`，
而运行时给的是 `人 ∩ B`，两者不等。可选做法是父级算好 `A ∩ B` 再下传（让等式恒成立），
**没选**：A 收窄到三个工具、B 是全量配置时，下传交集会把 B 需要的工具一起砍掉，
委派的用途当场消失。所以实现里 `None` 放行，真正守住的是 `can_write` 单调——
它挡的是一整类风险等级，不是名单里的几个名字。

反过来也要认：B 不会因为「被 A 委派」而获得 A 的额外能力。A 能做的事 B 可能做不了，
这是正确的，不是缺陷。

## 5. 为什么不能像 RBAC 那样在配置时静态校验

这是本设计与普通权限模型最大的分歧，也是它容易被做错的地方。

RBAC 可以在「给人分配角色」时一次性校验；委派不行，因为**目标是运行时才确定的**：
模型在 `plan_request` 之后才知道该把任务交给谁。所以：

- **配置时无法穷举。** 保存 B 的时候，不知道将来谁会委派给 B；保存 A 的时候，
  不知道 A 会委派给谁（那是模型的决定，不是配置）。
- **唯一的强制点是执行时。** 在 `delegate_to_agent` 真正要跑子图之前，
  用「当前 A 的边界」与「当前 B 的边界」做一次 `agent_subset`，不通过就拒绝。

配置侧能做的只有两件辅助：

1. `delegate_to_agent` 必须出现在 A 的 `allowed_tools` 里才能用——一个静态开关，
   让「谁能委派」至少是可配的。
2. 控制台的 Agent 编辑页给一个提示：勾了委派工具、但 `can_write=false` 时，
   提示「它只能委派给同样只读的 Agent」。

**不做的**：建一张「委派关系表」在配置时校验。那张表一定会在第一次「模型选了表外的目标」
时失效，然后维护者会把它改成「白名单」——那就退化成写死编排了。

## 6. 实现位置：一个内置工具，不是图分支

`delegate_to_agent`，`source=builtin`，`risk_level=NORMAL`，`requires_approval=False`。

```json
{
  "target": "ops",
  "task": "查一下 T002509008 昨天下午的压力异常，只回报结论",
  "context": "用户问的是 3 号泵跳停的原因"
}
```

- `risk_level=NORMAL`：委派本身不产生外部副作用，不审批。**被委派方执行写操作时，
  B 自己的审批照走**。给委派也加审批会导致「一次写操作两次确认」，人会开始闭眼点。
- `requires_approval=False` 同上。
- 目标解析用 `agent_service.resolve_for_chat` 的同类逻辑：不存在 404、`draft`/`disabled` 409。
- **不能委派给默认 Agent**：默认 Agent 是「不传 agent 时的承接者」，把它作为委派目标
  等于给了一条「绕过显式配置」的暗路。

为什么不做成图节点：图是固定的 7 个节点（`app/agents/graph.py`），加一个 `delegate` 节点
意味着图要知道「什么时候该委派」，那等于把决策写进代码。工具形态让模型在现有 planner
里做选择，与「Agent 是配置对象」的立场一致。

## 7. 上下文裁剪

子调用**不能**继承父对话的原始消息。要传的只有四样：

| 传 | 不传 |
|---|---|
| `task`（A 写的任务描述，必填） | 原始消息历史 |
| `context`（A 判断必要的背景，选填） | A 的系统提示词与职责说明 |
| 槽位（`station_id` 这类结构化标识） | 全部附件句柄 |
| **`refs`（A 显式列出的引用，P1）** | 父会话的附件目录 |

理由不是「省 token」，是**数据边界**：A 的历史里可能有 B 这个角色不该看到的业务信息
（跨场站、跨客户）。B 的职责更窄，给它更宽的上下文等于用上下文绕过职责。

`refs` 是这条规则的唯一出口，而且它是**显式**的：A 逐个列出 `{kind, id}`，
服务端在 B 的身份下重判可见性，通过的才变成 B 那里的一份材料。
「附件默认不过桥」与「引用可以过桥」不矛盾——前者是默认值，后者是一次明确的动作，
两者中间没有「自动带过来」这种状态。

代价：A 必须在 `task` 里把话说清楚，否则 B 会答非所问。这是可接受的——
一份写不清的任务描述，本来就该在 A 那一层被追问。

## 8. 深度、环与预算

| 约束 | 默认值 | 可配 | 不设会怎样 |
|---|---|---|---|
| 最大深度 | 2（A→B→C） | `agents.max_delegation_depth`，0–5 | 无限链，一次请求跑十几层，成本与时延都失控 |
| 禁回边 | 链上已出现的目标不可再进 | 不可配 | A→B→A 无限循环，且每轮都过子集校验（合法但无意义） |
| 单轮委派次数 | 3 | `agents.delegation_budget`，0–10 | 模型在 B 答不好时反复重试，一次对话烧掉 20 次子调用 |

三个计数都挂在 `ToolExecutionContext` 上传递（新增 `delegation_path: tuple[str, ...]`），
不放 state：它们是**执行纪律**，与「模型看到了什么」无关，混进 state 会让提示词里多出
一堆模型看不懂的字段。

**实现时的偏差**：子调用是一个**新的执行图**，跨图只能走 state，所以 `delegation_path` /
`delegation_count` 在 state 与 context 各有一份，由 `_context()` 还原到 context。
每轮归零放在入口（`chat_service` 构造状态时写空值），**不能**放 `begin_turn`——
`begin_turn` 在子图里也会执行，在那里清零会把深度与环的记录当场抹掉。

超限的拒绝理由要分开写（`depth` / `cycle` / `budget`），否则排障时只能看到
「委派失败」四个字。

### 8.1 按 Agent 可配（P3-a）

两列都挂在**发起方**身上（`agents.max_delegation_depth` / `agents.delegation_budget`），
因为被约束的是「它能往外派几次、派多深」，不是「它愿意接几层」。

**合并规则是取 min，不是取当前这一环。**

A→B→C 里若 B 把上限调成 5 就用 B 的那一份，整条链就能悄悄跑 5 跳——而 A 从来没有
同意过这个深度。所以生效上限是一条**单调收窄**的值：根节点从平台默认起步，
每进一层与这一环的配置取 min，再原样传给子调用。

```
生效上限 = min(上游传进来的, 这一环的配置 or 上游传进来的)
```

代价要说清：**想让整条链更深，链上每一环都得放宽**。这刻意做得很麻烦，
因为「一次请求跑十几层」的代价是整条链一起付的。它和 `allowed_tools` /
`can_write` 是同一条不变量——配置只收窄。

**空值不是 0。** 列可空且不回填：空 = 走平台默认，0 = 一次都不许。
回填成 2/3 会把「没配」变成「配了一个具体数字」，日后调整默认值时存量数据不跟着动，
而界面上显示的是用户从没设过的值。代码里同理：折配置时写成 `x or DEFAULT`
会让 0 静默变回默认，「不许转交」这个开关就失效了（有单测钉住）。

生效上限随 `delegation_limits` 走 state，跨图传给子调用；**这一环的配置**
另存 `agent_max_delegation_depth` / `agent_delegation_budget`。两样都要有：
只留前者，B 自己的配置进不来；只留后者，A 收窄到 1 这件事在 B 那一跳就丢了。

拒绝时的审计记下**生效上限**而不是配置值（`metadata.limits`）。回答的是
「为什么这次不行」——而答案往往不是他配的那个数，是上游更严的那一个。

## 9. 审批链

B 执行写操作时，审批单上除了现有的五个边界快照字段（`agent_id/name/revision/
allowed_tools/can_write`），再加两项：

- `delegated_from`：A 的 name（为空表示不是委派来的）；
- `delegation_depth`：第几跳。

批准时的复核顺序：**B 的快照 ∩ B 当前 ∩ A 当前**。

为什么要把 A 当前也算进来：批准期间若 A 的边界被收窄到不再包含 B，这张单子就是
「一个已经不该发生的委派」的产物。只复核 B 会漏掉这一类——B 自己没变，是它的上游变了。

审批人在界面上要看到完整一句：「ops 在 cs 的委派下，要把工单状态改为已关闭」。
只显示「ops 要改工单」，审批人无从判断这是不是越权链的末端。

### 9.1 实现时的三处修正

**一、「三方」在跳数 > 1 时是「逐跳」。** A→B→C 里 C 的单子上 A 不是直接上级。
只比「C ⊆ B」时，A 收窄而 B 没变会放行——那张单子已经是越权链的产物的产物。
所以落地的存储是**整条链** `delegation_chain = [{id, name}, ...]`（根 → 直接上级，
执行方不在链上），复核是从直接上级往根走，每跳都要 `子 ⊆ 父`。
`delegated_from` / `delegation_depth` 由链**派生**，不单存列：多存一份就多一处能对不上，
而审批卡上那句话与复核判断必须来自同一个来源。

存 `id` 而不是只存名字：名字在 Agent 删除后可被新 Agent 占用，按名字复核等于让
新建的同名 Agent 继承一张别人批过的写单。

**二、子线程的审批只能由子线程等。** 父图不跟着中断——它拿到的是「对方在等确认」，
`status=awaiting_approval`。这不是妥协：让父图也中断，恢复时整个委派会被重放一遍
（这正是 P0 强制只读的原因）。代价是子图的检查点必须**留到有人确认**，
而不是像只读委派那样当场删掉。

**三、结论要回到发起方的会话。** 子线程是一次性的，把结论写在那里等于没写。
所以单子上多存一列 `parent_thread_id`（发起方会话线程），确认后从子线程恢复，
结论落到父会话，并点名是谁做的——那个会话里从头到尾只有 A 在说话，
不点名就成了「A 自己办的」。

拒绝时的错误码分三种，不能合成一个：

| 错误码 | 含义 | 排障方向 |
|---|---|---|
| `AGENT_UNAVAILABLE` | 执行方被删 / 停用 | 看 B |
| `DELEGATION_REVOKED` | 上游某一跳被删 / 停用 / 收窄 | 看 A（B 可能完全正常） |
| `AGENT_BOUNDARY_CHANGED` | B 自己的清单变了，不再有这个工具 | 看 B 的工具清单 |

## 10. 观测：一条 trace，委派是一个 span

**不给 `obs_traces` 加 `parent_trace_id`。** 一旦一次用户请求变成两条 trace，
所有求和口径当场失效：`/observability/agents` 里 `by_agent` 之和等于 `traces` 的等式
不再成立，概览的分布图会和总数对不上，而这类不一致最难被发现。

> **补记（2026-11-12）**：委派写操作的恢复是**新 trace**，两条 trace 之间需要有可查的关联，
> 所以最终加了 `obs_traces.operation_id`。它不是树边，是**扁平分组键**（同一次运行的所有
> trace 取同一个值，第一轮用自身的 `trace_id`），因此上面那条求和等式不受影响，
> 并已有一条测试钉住它。

正确做法：整条委派链写在**一条 trace** 里，每个 Agent 执行是一个 `kind="agent"` 的 span
（`obs_spans.kind` 已经是字符串，注释里列了 `run|graph|node|llm|tool|mcp|db|retrieval|approval`，
加一个 `agent` 不需要迁移）。span 的 `attrs` 带：

```json
{"agent": "ops", "revision": 3, "depth": 1, "delegated_from": "cs"}
```

于是：

- `obs_traces.agent_name` 仍然是发起的那个 Agent，`traces` 口径不变；
- 新增 `delegated_turns`（被委派次数）由 `kind=agent` 且 `depth>=1` 的 span 数出来；
- 按 Agent 看用量时，「谁被叫去做事」与「谁发起」是两个数，不能相加成一个。

## 11. 失败语义

| 情形 | 返回 | A 该如何表述 |
|---|---|---|
| 目标停用 / 不存在 | 工具失败，`AGENT_UNAVAILABLE` | 如实说「它现在不可用」，**不能自己代做** |
| 子集校验失败 | 工具失败，`delegate_widens`（带具体违反项） | 说明「这个任务需要超出我可转交的权限」 |
| 深度 / 环 / 预算 | 工具失败 | 说明「转交层级已到上限」 |
| 子调用超时 | 工具失败，不重试 | 「没有在预期时间内返回」 |
| 子调用执行了写操作但超时 | `verified=false` 的未知态 | **必须说结果未知**，让用户去看审批 |

最后一行是最容易被写错的一句。委派不是幂等操作，超时后就重试会在外部系统产生两次写入。

## 12. 明确不做

| 事项 | 理由 |
|---|---|
| 并发 / 辩论 | 单机跑并行 Agent 先把时延打爆；且合并多份答案的规则没人定得了 |
| 动态编排图（运行时改图） | 图结构进数据库，等于把「配置」和「代码」的边界抹掉。**声明式图是另一回事**：`ORCHESTRATION.md` 的图是启动时冻结、保存即编译的版本化配置，不允许运行时改，也不新增任何执行语义 |
| 跨租户委派 | 租户是硬边界，不是权限问题。任何形式的跨租户引用都不开放 |
| 「A 把权限借给 B」 | 这正是本设计要防的东西 |
| 委派关系白名单表 | 见第 5 节 |
| 提示词层面的角色扮演 | 在提示词里「你现在是技术专家」不是委派，不得声称是 |

## 13. 分期

| 期 | 范围 | 验收 |
|---|---|---|
| P0 ✅ | `delegate_to_agent` + `agent_subset` + 深度/环/预算 + 观测 span + `agent_delegated` 审计 + 能力目录 | 第 14 节 1–8 条（第 8 条的 `delegated_turns` 数值见 P3） |
| P1 ✅ | 引用传递（`refs` 四类 / 三态 / 全有或全无） | 第 14 节 9–10 条 |

| P3-a ✅ | 委派预算按 Agent 可配（深度 / 单轮次数，取最严合并） | 第 14 节 14–16 条 |

## 14. 验收用例

每条都要能在去掉实现后失败（反向验证），只测「成功路径」的用例在这个模块里没有价值。

1. `A=[t1,t2]`、`B=[t1,t3]` → 委派被拒，理由点名 `t3`。
2. `A.can_write=false`、`B.can_write=true` → 拒绝，理由为 `can_write`。
3. `A.allowed_tools=None`、`B=[任意]` → 通过（父无上界）。
4. `A→B→A` → 拒绝，理由 `cycle`。
5. 深度 3 → 拒绝，理由 `depth`。
6. B 停用后再委派 → `AGENT_UNAVAILABLE`。
7. **B 执行时用的是 B 的边界**：A 白名单含 `t2`，B 不含，B 调用 `t2` 必须被拒。
   （这条最容易漏：如果实现里图省事把 A 的边界传给了 B，前面所有用例都会通过。）
8. 观测：一轮请求产生 1 条 trace、**恰好 1 个** `kind=agent` span（`agent.{B}`），
   审计 `agent_delegated` 一条。多套一层就是错的：每个 Agent 都会凭空多出
   「被叫过 1 次」，而那一层根本没人叫它。

P1（引用）另有两类：

9. B 拿不到 A 的材料：引用不可见返回 `REF_NOT_VISIBLE` 并点名缺的 scope，
   **不是空内容**；已删除返回 `REF_GONE`，两者不能同形。
10. 5 个引用里 1 个不可见 → 整单拒绝，不静默送过去 4 个。

P2（写操作委派）：

11. A、B 都可写 → 子调用可以真的发起写操作，但停在 **B 自己的审批**上；
    父图不中断，用户看到的是「对方在等确认」，不是「已经办完」。
12. 批准期间把 A 收窄到不再包含 B 要用的工具 → 执行被拒，错误码
    `DELEGATION_REVOKED`（不是 `AGENT_UNAVAILABLE`），外部系统一次都没被写。
    两跳链（A→B→C）里 A 收窄、B 未变，同样必须作废——只复核直接上级会放行。
13. 确认后结论落在**发起方**的会话里，并点名「谁做的」；落在子线程上等于没写。

P3-a（委派预算按 Agent 可配）：

14. `A.max_delegation_depth=0` → 委派被拒，理由 `depth`，文案说「不转交」
    而不是「最多 0 跳」。（反向：把 `0` 折成默认 2 这条就绿了。）
15. 上游已收到 1 跳、这一环配了 5 → 仍按 1 判，文案写「最多 1 跳」，
    审计 `metadata.limits.max_depth` 也是 1。
16. 配置 0 与 `null` 在库里、接口上、界面上都分得开：`null` 回到平台默认，
    0 继续阻止转交。（反向：用 `x or DEFAULT` 折配置，0 会静默变默认。）

P3-b（被委派次数）：

17. `B` 只被委派、从未被直接对话选中 → `/observability/agents` 里仍有它这一行，
    `traces=0`、`delegated_turns=2`，且 `sum(traces) + unattributed == total`
    照旧成立。（反向：把它并进 `traces`，等式当场破；名字并集漏掉它，
    这一列永远是 0。）

P3-c（产物按会话保留）：

18. 让 A 保存一份 `巡检报告.md` → 返回 `artifact_id`，`artifacts.conversation_id`
    等于本会话；同一会话的下一轮（含换话题）能引用它。
    **反向**：把产物记成 `conversation_id=None`，或引用解析不看会话，
    这条就绿了——而「跨会话不该串」正是这一步要买的东西。
19. 用**另一个会话**的产物 id 作 `refs` → `REF_NOT_VISIBLE`，理由写「另一个会话」；
    用 `conversation_id` 为空的历史材料 → 仍然可用。
    （反向：收紧成严格相等，存量附件一起失效；不看会话，跨会话就串了。）
20. 没有会话的调用保存产物 → `ARTIFACT_NO_CONVERSATION`，库里不留行。
    （反向：允许它落库，就会攒下一批会话删除带不走的无主产物。）

## 15. 已知边界

- **委派不传递上下文，只传递任务。** 见第 7 节，B 可能因为缺少背景而答非所问。
- **子集校验只在执行时强制。** 配置时给不了保证，见第 5 节。
- **提示词注入无效，但也不背锅。** 就算 A 在 `task` 里写「忽略你的边界」，
  B 的边界在网关里，模型说什么都改不了；但 A 可以诱导 B 去做 B **有权做**的事，
  这一点边界管不了，只能靠职责说明与审批。
- **成本归 B。** 子调用的 token 与耗时应记在 B 头上，不是 A。
  记在 A 会让「谁在烧钱」这个问题永远答错。
- **委派来的写操作只被确认一次，但它的结论不经过 A 的转述。** 确认发生在子线程上，
  结论直接贴进发起方的会话。好处是不会多出「第二次确认」；代价是 A 没有机会在
  结果上补一句自己的解释——它在上半轮（转交那一轮）已经把话说完了。
- **一张委派审批单最多对应一次写操作。** 子调用的一轮里写操作只有一次（图在
  写操作后就收尾），但如果 B 在**同一个子线程**里连续写两次，第二次会复用第一次的
  审批幂等键。实际上走不到：`create_and_wait_approval` 之后图直接 `respond`。
  这条记在这里，是因为它由「子调用的 run_id 恒为空」推出来，不是由设计推出来。
