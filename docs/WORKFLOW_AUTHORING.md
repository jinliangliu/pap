# 用一段话建一张图：编排的起草层

> 相关：[`ORCHESTRATION.md`](ORCHESTRATION.md)（图怎么跑）、
> [`STUDIO_ASSISTANT.md`](STUDIO_ASSISTANT.md)（谁在建）、
> `app/orchestration/definition.py`（什么算「能跑」）。

## 0. 一句话

**把「起草」与「保存」拆开。** 现在这两件事被绑在同一个工具里，所以模型每想试一下，
都要付一次审批卡的代价——它只能赌一把写完整张图；赌错了，整份重写。

## 1. 现状：能力有了，路径不顺

「用自然语言建流程」在 PAP 里不是新功能，构建助手已经能做（`studio_workflow_save`），
提示词里也写清了「用户描述有先后顺序、多角色接力、按条件分流的过程 = 要建流程」。
不顺的是路径：

| 环节 | 现在 | 卡在哪 |
|---|---|---|
| 发现 | 只在右下角构建助手面板里 | 对话页的下拉**有意**不列构建助手（`console.js` `loadChatTargets`），说「帮我建个流程」得到的是解释 |
| 起草 | 直接调 `studio_workflow_save` | 起草即保存：一进审批卡、二进库、三涨 `revision`。改一个字要重走一遍 |
| 校验 | 保存时才编译，错误一次性抛给模型 | 模型拿到「缺兜底边」的反应通常是**重发整份 JSON**，而漏掉的那个节点等于被删掉 |
| 改一处 | 只能整份重存 | 「把第二步换成 ops」在数据层是一次全量替换，提示词里得写「不要凭印象重写，漏掉的节点等于被删掉」——**能用工具形状解决的问题，不该靠提示词兜** |
| 回看 | 保存后才有 `definition` | 中途没有任何可看的东西，用户对着一句「已建好」的承诺点确认 |

对照扣子那套「AI 生成式工作流」，差距不在模型能力，在**这几个环节的次序**：它先在对话里
反复改、在画布上反复看，最后才「发送并执行变更」。我们把它压缩成了一次提交。

## 2. 扣子那套，抄什么、不抄什么

| 扣子 | PAP 对应物 | 结论 |
|---|---|---|
| 自然语言 → 生成**工作流代码**（语义层 / 参数层 / 代码层） | 自然语言 → 生成**受约束的图**（`definition` + `compile_definition`） | **不抄**。见 §3 |
| 画布预览，点节点看输入输出 | `_workflow_graph()` + 控制台编排页的结构化编辑器 | 已有骨架。画布缺独立坐标列，另案 |
| 框选节点 → **引用** → 只改这一处 | **没有** | **抄**，落成 `patch`（§5） |
| 试运行 + 每节点耗时/输入输出 | `workflow_runs.nodes_json` + 黑板 | 已有。但不做「假跑」，见 §7 |
| 测试失败 → 一键修复 | `DefinitionError.node` + `_preflight_workflow` | **半抄**：给结构化问题清单，不给自动改图 |
| 对话里反复改，工作副本随身带 | **没有**（每次都是全量提交） | **抄**，落成 `studio_workflow_draft`（§4） |
| 回滚版本 | 只有 `revision` 号，没有快照 | 用 `write_backups`（§6） |
| 上传附件 / 技能 / 选模型 | `studio_import` 已通 | 不在本文范围 |

## 3. 为什么不抄「让模型写代码」

扣子的产物是代码，表达力没有上限；PAP 的产物是图，表达力被刻意收窄：三种节点
（`agent` / `compose` / `parallel`）、五个算子（`eq` `neq` `in` `gt` `lt`）、必须显式写兜底边、
`max_nodes` 上限 12（顶 20）。这些限制是治理资产，不是欠债：

- **保存即编译**：存进库的一定是能跑的图，坏图在保存那一刻变成一句看得懂的拒绝；
- **图只排顺序，不分配能力**：每次节点调用仍然逐跳判定边界（`agent_subset`），
  所以「谁的图」不等于「谁能写」；
- **`revision` 可冻结**：在飞的 run 按旧图走完，`cursor` 不会指向一个改名的节点。

一旦允许模型生成代码，这三条同时失效——而它们正是「出事能复盘」的全部依据。
所以本文抄的是**交互形态**，不是产物形态。

## 4. 改动一：`studio_workflow_draft`（只读，不落库）

给构建助手加一个读工具：把一张图交上去，回答「能不能存、差在哪、存下来长什么样」。
**它不写库、不建审批单、不涨 `revision`**，所以可以无限次调用。

```
studio_workflow_draft(name?, definition) -> {
  ok: bool,                        # 图能存、且图里的角色都在库里启用中
  errors: [{node, code, message}], # 差在哪；空数组 = 没问题
  graph: {entry, nodes, edges},    # 与确认卡同一份形状；ok 时才给
  writable_nodes: ["advise"],      # 这几步的智能体允许写，动手时会停审批
  message: "这张图能存。\n步骤：…\n分流：…\n角色：…\n允许写的步骤：…\n下一步：…"
}
```

`message` 是给人看的那一段（步骤 / 分流 / 角色与确认卡同一份拼接）；结构化字段是给
气泡画图和给下一轮引用用的。**下一步的提示写在 `message` 尾部**，因为模型对工具
返回末尾那句话的服从度高于系统提示。

四条设计约束：

1. **`errors` 必须带 `node`**。`DefinitionError` 已经带（能定位时），库校验那两类
   （角色不存在、不是启用中）由 `_workflow_agent_facts` 补齐。没有 `node` 的问题，
   模型只能整份重写。
2. **库校验只读、且与保存同一份口径**。用的是 `save_workflow` 里那两个函数改名后的
   公开版（`plan_agents` / `AGENT_STATUS_TEXT`），不另写一套「大概一样的遍历」——
   口径分叉的表现是「起草说能存、保存被拒」，比不校验更让人不信任。
3. **报「允许写」，不报「会审批」**。停不停审批取决于模型在那一轮决定调什么工具，
   图上答不出来；能回答的只有「这一步的智能体允许写（`can_write`）」。
4. **不落库的代价**：跨轮只剩摘要。所以 `definition` 要**原样回显**在结果里，
   并且 `chat_service` 落库时那份显式字段清单（`add_message(metadata={...})`，
   在 `persist.assistant_message` 那一段）要加上 `workflow_draft`——
   节点写进 `response_metadata` 不等于落库，漏加这一行就是「当场有、刷新没有」。
   （P0 尚未做，见 §14。）

工具名带 `studio_` 前缀，会由 `_studio_tool_names()` 自动进构建助手的边界，
**不要**加进 `STUDIO_BUSINESS_READ_TOOLS`（那是业务读工具名单，有单测钉形状）。

## 5. 改动二：`studio_workflow_save` 的 `patch` 参数

**不新增写工具。** `STUDIO_ASSISTANT.md` §4.2.1 已经论证过「一个写工具 + 一个删工具」，
再加一个 `studio_workflow_patch` 会让审批、摘要、verifier、备份各长出第二套。
改成同一个工具的可选参数，与 `definition` 二选一。**`studio_workflow_draft` 同样接受它**，
否则「改一处」在起草那一步仍然要重发整张图：

```json
{
  "name": "pressure-triage",
  "patch": {
    "set_nodes": [{"id": "b", "agent": "ops", "task": "按超压处置：{{nodes.a.level}}",
                   "next": [{"when": null, "to": "c"}]}],
    "remove_nodes": ["diagnose"],
    "entry": "check"
  }
}
```

三个键，语义只有三条：

| 规则 | 为什么 |
|---|---|
| `set_nodes` 按 id **整节点替换**，没有的 id 就**新增** | 合并语义会让「我没写 next」同时表示「沿用旧 next」和「它没有后继」，而这两件事跑起来完全不同。整节点替换只有一个含义：你写的就是它 |
| `remove_nodes` 摘掉所有指向它的边，**并说出来**；若某节点因此没有后继，**报错不改接** | 指向不存在的节点编译不过；但自动把 `A→X→B` 折成 `A→B` 是猜，而「三步走完」变成「停在第二步」不会抛任何异常 |
| `entry` 可改；删掉入口却没给新 `entry` → 报错 | 入口是流程的起点，静默换成别的节点等于换了一张图 |

**底图从哪来**：先按 `name` 取库里的那张；库里没有（还没建、或上一轮刚起草过）就取
**本会话最近一份草稿**（`_latest_workflow_draft`，读消息元数据）。返回里会多一行
「叠在本会话上一版草稿上」——不说的话，读者以为改的是库里那张。

**改动清单要回显**：「本次改动：替换节点「b」；删掉节点「diagnose」」出现在起草正文、
保存正文、确认卡三处。不回显的话，模型下一轮会以为那个节点还在，再删一次、
然后被告知「图里没有这个节点」。

### 与最初设计的差异（2026-11-23 实现时改的）

设计稿原本是 `patch` 为一串 ops（`upsert_node` / `remove_node` / `set_entry` / `set_max_nodes`）、
「没给的字段保留」、施加在 `workflow_service.save_workflow` 里。三处都改了，各有理由：

1. **ops 数组 → 三个键**：数组要模型逐条保证顺序与合法性，而实际改动通常是一处。
   键名固定之后，写错键会在 `apply_patch` 里被拒并列出可用的键，不必等到编译。
2. **字段保留 → 整节点替换**：见上表。代价是改一个字段要重发整个节点——比整张图便宜
   一个数量级，而且不会出现「我以为它保留了 next」。
3. **不进服务层**：把 `compile_definition` 挪进事务是这套设计里唯一有风险的动作
   （编译是纯函数，挪进去之后事务变长、错误点变多）。改为在工具层施加后照常编译，
   `save_workflow` 一行不动。代价是控制台的 `POST /workflows` 用不上 patch——
   那边本来就是整张图编辑，不需要它。

`_preflight_workflow` 与 `summarize` 共用同一份解析（`_graph_from_arguments`）：卡上画的
必须就是存下去的那张。preflight 对拼不上的 patch 直接返回错误、不弹卡。

## 6. 改动三：回滚（P2，借 `write_backups`）

`revision` 只有号，没有快照，所以「回到第 3 版」现在做不到。**不新建版本表**：
`studio_workflow_save` 的 `_backup_workflow` 钩子已经在每次保存前把整份 `definition`
存进 `write_backups`（含 `resource_id` 与 `payload`）。

回滚 = 从 `write_backups` 取某一份 `definition` → 走一次正常的 `save`：

- **回滚是一次新的保存**，`revision` 继续涨，审计里是 `workflow_updated`。
  「版本号退回去」等于声称那段时间没发生过，而运行记录上记的是它——这条与
  `studio_agent_restore` 的口径一致（恢复类不能拿版本号当证据）；
- 备份是「保存**前**」的，所以「回到上一次的样子」是按 `created_at` 倒序取第一条，不是当前行。

**保留期已经落在 `write_backup_service`**（回滚的前置条件）：每个资源留最近
`KEEP_PER_RESOURCE=5` 份、且只留 `MAX_AGE_DAYS=90` 天内的。裁剪跑两次——
插入前一次（腾出空间，总量判据要用清理后的用量）、插入后按资源压回 5 份
（只在插入前裁，稳态会是 6 份，与「留几份」这个承诺不符）。
没有它，总量上限会让备份在某个时刻全体静默停止（`store_full` 每天刷日志），
而真正需要恢复的那一件恰好落在停止之后。

## 7. 试运行：不造假跑

扣子的「试运行」是**真跑**（真调模型、真调工具、真花钱），我们有 `/workflow <name> <输入>`。
不做「假跑」（只走图不调智能体），理由两条：

1. 假跑的结论是假的——每个节点的输出要靠编，而用户会拿它当证据；
2. 假跑要跳过工具调用，等于绕开审批：写节点在假跑里「成功」了，用户以为流程能跑通。

所以「试运行」= `draft` 的静态预检 + 真跑一次。真跑的节点流水（`nodes_json`）与黑板
已经在运行页可见，缺的只是**在对话里回显**：跑完把每条节点的耗时与输出前 N 字贴回会话
（助手消息的 `metadata.workflow` 已经记了流程名，只差内容）。

## 8. 入口：`/build`

**不要复用 `/workflow` 命名空间。** `parse_command` 的第二个词一定是流程名，
`/workflow new ...` 会被当成「跑一条叫 new 的流程」，而 `new` 恰好是合法名字。

`/build` 是**界面快捷方式**，不是平台命令：

- 前端 `sendChat()` 见到 `/build ` 前缀 → 不发 chat 请求，直接 `setStudioOpen(true)`
  并把原话预填进构建助手的输入框（面板本身就在同一个页面，成本是一次开关）；
- 后端仍要认识它：万一被客户端直接发过来（`/build` 不是 `/workflow`，会当普通消息交给模型，
  模型只会配合地编一段），`chat_service` 返回 409 + 一句「这条要在构建助手里做」，
  不落库、不进历史。**平台做过什么由平台说，不由模型编。**

默认助手的提示词加一句：识别到「有先后顺序、多角色接力、按条件分流」时，说明这是编排、
并提示「输入 /build 或打开右下角构建助手」——**不给默认助手任何写工具**
（`ToolGateway.internal_denial` 已把 `studio_*` 按身份挡在这里，提示词只是让它说得自然）。
身份边界按会话记（`_channel_of`），同一个 thread 里换人会让「这条会话是谁」失去意义。

### 8.1 为什么是「跳一跳」而不是「同一个会话里换人」

| 路 | 做法 | 代价 |
|---|---|---|
| A（本文） | `/build` 一跳，落到构建助手面板 | 用户多一次视线移动 |
| B | 给默认助手 `studio_workflow_save` | 默认助手是被诱导性输入说服概率最高的角色；等于开一条不经审批的配置写入。**否决** |
| C | 主对话页加「编排模式」，UI 复用面板 | 两套输入框、两套历史、两套「我刚说了什么」；收益只有省掉一次视觉跳转 |

A 的代价是可见的、C 的代价是长期的，B 的代价是治理上的。选 A。

## 9. 一轮对话走查

用户：`压力高了先让现场查规程，再让运维决定关不关阀，最后汇总给我`

1. `studio_describe resource=agent` → 有哪些角色（`field-ops` / `ops` / `assistant`）
2. `studio_workflow_draft`（第一版：check 只在「泄漏」时去 advise，**忘了兜底边**）
   → `ok=false`，`errors=[{node:"check", code:"WORKFLOW_NO_FALLBACK"}]`；说明「其余情况没有去处」
3. 模型**只给** check 补一条兜底边再交一次
   → `ok=true`，`preflight.approval_nodes=["advise"]`（`ops` 带写工具）
4. 模型把图 + 3 步 + 「第 2 步会停在审批」说给用户；用户说「就这样」
5. `studio_workflow_save`（`definition=那张图`）→ 确认卡：图 + 角色 + 分流
6. 批准 → `verify_workflow_saved` 回读（节点集合一致、`revision`、`enabled`）→ 给触发方式
7. 后续「把第 2 步换成 assistant」→ `patch` 里 `set_nodes` 一个节点（并带上它的 `next`）
   → 正文说「本次改动：替换节点「advise」」，其余节点一个字不动；确认卡上的图与它一致

第 3 步是这套改动真正省下来的东西：**一次改动 = 一个节点**，而不是一整份 JSON。

## 10. 边界（都不动）

| 不变量 | 为什么不能动 |
|---|---|
| 写工具只在构建助手 | 默认助手最容易被动过嘴，给它 `studio_workflow_save` 等于开一条不经审批的配置写入。**这条现在是硬隔离**：`ToolGateway.internal_denial` 按身份把 `studio_*` 挡在所有别的智能体之外（目录与执行两处同一份判断）。之前只写在提示词里，而默认智能体 `allowed_tools=None`、平台管理员跳过 scope，工具其实一直在它的目录里 |
| 起草不落库、不要审批 | 起草失败是常态；对失败也弹确认，人会对确认卡闭眼 |
| `patch` 仍然是「保存一张完整的图」 | 施加 patch 后照常 `compile_definition`，`revision` 语义、冻结、审计都不变；它只是省掉「重打一遍」 |
| 校验只有一份 | `compile_definition` 是唯一权威；draft 与 preflight 都只是它的包装 |
| 角色替换必须说出来 | 用户点名 `ops`、图里用了 `field-ops` 时，**调用前**要用一句话说明换成了谁（卡上列得出用了谁，列不出他原本说了什么） |

## 12. 验收用例

每条去掉实现后必须失败。

1. 一张缺兜底边的图交给 `draft` → `ok=false`，`errors[0].node` 是被指出的那个节点，
   且**库里没有新增行**、`revision` 没变。
2. `draft` 里写了清单上没有的角色 → `preflight.agents_missing` 非空；
   `save` 同一张图 → 被拒，理由点名那个角色。
3. `patch.set_nodes` 只给一个节点 → 其余节点的 `task` / `emit` / `next` 与改动前
   逐字相同。**（反向：把 patch 实现成整图替换，这条绿）**
4. `set_nodes` 里那个节点没写 `next` → 它就没有后继，**不是沿用旧值**；由此让别的节点
   走不到时，`save` 报 `WORKFLOW_UNREACHABLE_NODE` 并指出节点，`revision` 不变。
5. `remove_nodes` → 指向它的边被摘掉并在正文里说出来；若某节点因此没有后继，
   报 `WORKFLOW_PATCH_ORPHAN_EDGE` 并指出是哪一步，**不自动改接**。
6. `patch` 与 `definition` 同时给 → 被拒，文案说「只能给一个」，`revision` 不变。
7. `patch` 带 `name` 但库里没有、本会话也没起草过 → 拒绝，并说明「新建要给 definition」。
8. 不带 `name`、但本会话上一轮起草过 → 落在草稿上，正文写「叠在本会话上一版草稿上」；
   随后 `save(mode=create)` 能把改完的图建出来（`revision=1`）。
8. 直接 `POST /api/v1/chat` 发 `/build ...` → 409，`messages` 表没有新增行。
9. 保留期：同一资源连存 8 次 → 库里正好 5 行（不是 6）；八张不同的图各存一次 → 8 行都在
   （按资源计份，不是全局）；总量已满但旧快照过期时，先清理再判，写入不被 `store_full` 误伤。
10. 回滚（未实现）：`write_backups` 里取第 N 份 → 保存后 `revision` = 原值 + 1，审计是
    `workflow_updated`，且 `definition` 与第 N 份逐字段相等。
11. `test_studio_tool_verifiers` 仍绿：`studio_workflow_save` 有 `verifier` 与 `summarize`，
    `studio_workflow_draft` **不**需要 `verifier`（它不写）。

## 15. 上线后第一轮对话暴露的三件事（2026-11-23）

用户按 WB 系列走了一遍，卡在这一段：

```text
你    压力高了先查规程再决定关不关阀
助手  这句是要建流程，还是先查一次现场？      ← ①
你    建流程
助手  建流程前需要确认「查规程」这一步由谁做。
你    通用助手
助手  「查规程」这一步由谁来？               ← ②
```

三件事都不是模型「听不懂」，是我们把一个它本来答得出的问题推给了人。

### ① `/build` 已经说了「要建流程」，面板又问了一遍

`/build` 是命令，用户用它就是在回答这个问题。前端把话带过去了，却没带「来源」，
模型手上只有一句描述——那就只能问。

改法：转过去的那一条消息前面加一行 `[来自 /build：这次是要建编排流程]`。
写成**可见前缀**而不是隐藏字段（与「（当前对象：…）」同一个做法）：历史里还在，
不必猜「它为什么突然知道我要建流程」。只跟一条，第二句就不带了。

顺带修掉一个更实际的：预填之后发送键是灰的。`input.value = ...` 不触发 `input`
事件，而面板刚打开时按钮是按空输入框算的——用户看到话已经填好、键却是灰的，
只能按回车。补一次 `updateStudioSend()`。

### ② 「由谁做」是闭集问题，答案在库里

`agents` 表里就是 `name=assistant, display_name=通用助手`。模型不知道这个映射，
所以它要么问，要么编一个名字被拒。**问和编都不是它的错**。

改法（`workflow_service.agent_lookup` / `resolve_agent_name` / `resolve_plan_agents`）：

- 图里填**标识或显示名**都认，落库前统一换成标识（运行时按标识取 Agent，
  `agent_invoker.invoke` 那条路一个字没动）；
- 显示名重名**不猜**：两个「运维」是两张不同的边界，按名字挑一个等于替用户
  决定了权限；标识占住的键也不会被显示名覆盖；
- 起草与保存**共用这一份**（和 `plan_agents` / `AGENT_STATUS_TEXT` 一样）：
  起草说能存、保存说改名，是最糟的一种不一致；
- 换过谁要在草稿里说出来（「通用助手 → assistant」）：图上从此写 `assistant`，
  不说清就成了凭空换人。

同时把枚举摆到它眼前：`studio_describe resource=agent` 的清单末尾固定一行
「能放进编排图的（启用中的业务智能体）：…；不能进图：…」。以前它读完清单还要问用户，
因为清单里没把「启用中」提炼出来。**内置助手不在这一行里**：它拿的是平台管理工具，
不承接编排节点（`_ensure_agents_available` 报 `WORKFLOW_INTERNAL_AGENT`）。

### ③ 面板从来没有追问卡，`options` 一直是白给的

看代码才发现：`metadata.clarify.items` 从来没被存进 `studioUI.messages`，
`studioBubble` 也不认识它。模型给出候选、界面只显示一句话——用户只能打字。
这也解释了为什么对话台上「点一下就回答」的体验在面板里完全不存在。

改法：面板里把候选渲染成按钮，点一下就把那句发出去（填进输入框再走
`studioSend`，不另开一条提交路径——否则面板会有两套「怎么发出去」）。
**只给最后一条**：后面的用户消息一出现，这个问题的答案就定了；刷新之后照同一条
规则走（历史里带着同一份 clarify），所以不会「当场能点、刷新只剩一句话」。

### 一条判断

写进代码注释也写在这里：**让用户把答案再打一遍，是把平台该做的事推给用户。**
「这一步由谁做」的答案是一份枚举，枚举在库里；模型问它，等同于反问用户
「你们租户里有哪些智能体」——而这句话它刚在工具结果里读过。

### 验收

- `tests/unit/test_workflow_agent_names.py`（8 条）：显示名映射、标识优先、
  重名不猜、节点与并行分支都改写、保存落库存标识、草稿说清换成了谁、
  未知角色带显示名候选；
- 仓外 jsdom 冒烟：`/build` 来源标记只跟一条、候选按钮渲染、点一下发出、
  答完消失、状态码翻成人话；
- 手测 WB10–WB14。

### 上线后补的两处（同一轮）

模型真的开始起草之后，暴露出两件它看不见、用户躲不开的事：

- **读工具的结果里没有图**。`execute_read_tool` 的 `response_metadata` 少了
  `_result_graph`（写那条路一直有），于是起草出来的图只画在确认卡上，气泡里
  只剩「步骤：a → b」。用户要核对的是形状，不是那一行字。
- **起草被挂了「尚未通过回读核验」**。`verified=False` 时 `_summarize_result`
  会在末尾补一句——那是给写工具用的。起草不写库，用户读到这句会以为刚才
  那次起草落了库却没核上。`studio_describe` 一直标 `verified=True`，同一条口径。

顺带把 `ok` / `writable_nodes` 从正文里拿掉：`message` 已经说了「这张图能存」，
再铺一行 `ok：True` 等于把报文原样贴给用户。

### 一条调不动的经验

「先起草再问」这句话写在系统指令里**三遍都没用**：模型仍然先给一张表、等用户
点头才起草。写到 `studio_workflow_draft` 的工具描述里（"它是只读的，不需要先等
用户确认"）之后才稳定生效——它选工具时读的是那份描述，不是那段长指令。

但也不是每次都照做：实测 7 次，5 次直接起草、2 次先问一句（"关阀那步放不放进图"）。
差别不在措辞，在那个问题本身是否真的挡住了图的形状。这一层不打算再调——
把「一定先起草」做成确定行为，得让入口强制一步（首轮 `tool_choice`），那是另一个改动。

## 16. 图上的名字，与那一次多余的确认（2026-11-23）

用户贴回来的那张图已经对了：直接起草、图出现在气泡里、说了「按你说的用
assistant（通用助手）」。剩下两处是「看着费劲」，不是「跑不通」。

### 图上写谁：标识还是显示名

图里存的是标识（`assistant`，`agent_invoker.invoke` 按它取 Agent），可图是给
人核对「谁在第几步」的。用户嘴里说「通用助手」，图上写 `assistant`，他就得在
心里对一次——而平台明明知道这个对应关系。

改法：`_workflow_graph(plan, labels)` 多带一个 `agent_label`，渲染时副标题用
显示名、悬停提示里写 `通用助手 / assistant`（排查按标识搜日志是常态，标识不能
真的消失）。两者相同时不带这个字段——多一个一模一样的值只是噪音。

`_agent_labels` 的三条约束：

- **键要两种都登记**。起草与保存后的图已经换成标识，而确认卡的图是**原样参数**
  （`_summarize_workflow_call` 不改写它，那不是它的职责），可能还写着「通用助手」。
  两种键都指向同一个显示名，渲染侧只查一次。
- **只查图上真出现的几个名字**（`plan_agents`），不是整表。
- **出错返空、绝不抛**。这张图出现在三处：起草气泡、确认卡、保存后气泡。确认卡
  那一处要是因为一次查询失败就生不出卡，用户看到的是「点了保存没反应」；
  退回标识的图照样能读、能确认。

### 那一次多余的「存」，与第一版为什么没成

线上那轮，起草通过后它说的是「确认这张图就回一句『存』，我提交保存」。用户回
「存」，然后还要在卡上点一次——**同一件事确认两遍，前一遍什么也拦不住**。

第一版改法是「在尾行写：直接调 `studio_workflow_save`（mode=create/update），
不要问存不存」。上线探针发现三件事，一件比一件实在：

1. **那行话是给用户看的**。读工具的结果就是正文——`mode=create/update` 这种参数
   提示原样出现在气泡里，用户不知道那是什么。
2. **它起草完就停手了**，保存根本没发生。原因有两层：尾行写成完成态（「下一步：
   直接调…」读起来像一个交付物），而 `STUDIO_INSTRUCTION` 里还留着一句
   「能存了再把图贴回回复里」——那句等于教它「交完就算完」。
3. 文字行还是 `field-ops` / `assistant`，而图上已经是「现场作业」「通用助手」：
   **同一屏里同一个角色两个名字**，读的人得先判断是不是同一个人。

最终改法：

- 尾行只留人话，且**说清还没落库**：「图还没落库。要存就保存——会弹一次确认卡，
  那是唯一一次确认；不想存就说改哪一步。」用户读到的是事实，模型读到的是「没完」。
  删掉工具名与参数模式（那是给模型的，而模型从工具清单里知道该调哪个）。
- 指令里删掉「能存了再把图贴回回复里」，改成「能存就直接调 `studio_workflow_save`，
  会弹一次确认卡，图和卡在同一屏」；工具描述补同义一句。**工具描述那份才是决定性的**：
  上一轮实测，同一句话写在系统指令里三遍都没用。
- `_step_label` / `_roles_line` 统一走 `_who(agent, labels)`，与图同一份名字。
  **结构化结果 `workflow.roles` 仍是标识**（调用方按标识取 Agent）：换名只发生在
  文字那一层，数据契约不动。

改完探针：`status=awaiting_approval`、`preview.graph` 三步都带 `agent_label`、
卡上「角色：现场作业（check_pressure）；通用助手（check_rule）」——起草后直接弹卡，
用户只点一次。取消后 `workflows` 里 0 行（没写）。

图还不成立时（`ok=false`）**不能**说「要存就保存」：那等于让人对着一张注定被拒
的卡点确认。这一支留在「把上面这几处改掉再交回来」。

### 验收

- `tests/unit/test_workflow_agent_names.py` 新增 8 条：图带显示名、显示名等于标识
  时不带、尾行不出现工具名/参数模式、说明还没落库、不能存时不催保存、文字行用同一
  个名字、确认卡的图带人话、没有 context 也生得出卡；
- `node scripts/check_flow_labels.mjs`：副标题写显示名、正文不出现标识、悬停两者
  都在、无 label 退回标识、同值不重复、汇总与并行不被覆盖；
- 手测 WB15–WB18。

## 17. `/clear` 之后那句话，和图其实并不存在（2026-11-23）

用户清掉上下文，说了一句「压力高了先查规程再决定关不关阀」（没有 `/build` 前缀，
他本来就在构建助手的会话里）。回来的是一段散文：

> 这条处置顺序已经记下来了……对应的编排流程 `check_pressure` 之前也定过：
> check_pressure(field-ops) → check_rule(assistant) → report 汇总……
> 要我现在按这个顺序把图重新起草一版给你看，还是直接保存？

图一张没交，问题倒是问了。查下去发现三件互不相干的事叠在一起。

### 它没有历史，只有记忆

12:46:10 那条 `/clear` 把水位划在了前面，所以 12:46:12 那轮的 `context.inject`
是 `turns: 0`——**这是设计**，不是缺陷。问题在于它没历史可看，却仍要说「之前也
定过」，那结论只能来自 `known_user_facts`。

那条记忆确实存在：「决策｜高压处置编排流程：高压处置编排流程为
check_pressure(field-ops) → check_rule(assistant) → report 汇总」，
`source=auto_extract`、`created_at=12:36:29`。

### 那条记忆是错抽取

12:36 那一轮，助手回答的开头是「这张图能存。步骤：check_pressure（field-ops）→
check_rule（assistant）→ report 汇总」。抽取器把**助手自己排的一版草稿**读成了
「用户拍板的方案」。而库里 `workflows` 是 0 行——12:43 那次 `studio_workflow_save`
弹了确认卡，用户点了取消（「已取消本次操作，未执行任何写入」）。

于是模型手里握着一份「已经定过的流程」，而它不存在。它据此判断「图有了，只剩存不存」，
问出那句二选一，是顺理成章的。

### 三处都改

1. **抽取层不记平台状态**。流程、智能体、技能、工具、连接器的名字、结构、开关
   状态，在库里一查就有；记下来只会过期，或者像这次一样，把草稿记成事实。
   提示词里连「库里查得到吗」一起写进判定标准——记的是「人怎么想、业务怎么定」。
   起草过、待审批、被取消，一律不算「已定」。
2. **构建助手说「之前定过」要有本轮证据**。指令里点名这一句：记忆里的步骤清单只是
   背景，要说出「已经有一张流程」先 `studio_describe resource=workflow` 读一眼，
   读不到就说「还没建」，然后直接起草。
3. **「要不要我起草」这句不问**。起草不写库、不弹卡、不涨版本号，问一句只是让用户
   白等一轮；「先给你看一版」和「直接保存」也不是二选一。指令与工具描述两份都写
   （工具描述那份才是决定性的，见 §16）。

顺带把 `STUDIO_INSTRUCTION` 压回 4000 字符以内：它是写进 `agents.instruction` 的
正文，而管理员在「补充指令」里点一次保存，会撞上 `MAX_INSTRUCTION_CHARS` 校验——
界面上那份看起来完全正常，只有保存时才知道超了。`test_build_invariants.py` 盯着
这条线。

### 验收

- 同一条消息（清空上下文后直接发，不带 `/build`）连打 5 次：应当每次都直接交草稿
  进气泡，没有一次以「要不要起草 / 还是直接保存」收尾；
- 库里仍有一张叫 `check_pressure` 的图时，它要先读到那张图再谈「已有」；
  库里没有时，不许出现「之前定过」「上次定的是」；
- 新的一轮抽取不再产出「流程为 A → B → C」这类条目。

### 写进职责说明不管用，得在入口纠一次

上面三条改完之后，同一条消息连打 5 次，只有 1 次交出了图。剩下的四种绕路一次一换：

| 它说的是什么 | 实际发生的事 |
|---|---|
| 「这条处置顺序我记下了……要我重新起草一版，还是直接保存？」 | 把两件自己能做的事推回给用户 |
| 「这句是原则，不是一次具体动作，两种做法：查一次现场 / 建成流程」 | §15 已经明令禁止的那一问，换了措辞 |
| 「本身只有一步判断、没有接力，所以不起草」 | 把「同一个智能体串两步」判成不成图 |
| 在回答里画一张 ```svg 流程图 | 看着像交图，库里没有，也点不了保存 |
| 「当前租户还没有任何编排流程。新建用 studio_workflow_save mode=create……」 | 工具消息原样成了答复 |

对照组的差别很干净：**提到「由谁做」的那句**（「先让现场作业查一次读数，再让通用
助手对照规程给判断」）每次都直接走到确认卡。也就是说，卡住的不是句式，是「分工由谁
决定」——模型倾向把分工当成用户的事，于是先问一句。

职责说明里已经写了「分工由你定」，还是这样。**同一句话写在提示词里三遍，不如把它变成
这一轮唯一的任务**。所以在 `plan_request` 里加了一次纠正（`nodes.py`）：

- 触发条件三个且同时成立：当前智能体是构建助手、这一轮只回了 chat、用户原话里有先后
  （`先`/`首先` 起手，且有 `再`/`然后`/`最后`/`→` 接续，且不是问句）；
- 动作：把 `STUDIO_BUILD_NUDGE` 追加进 **system**（`agent_block` 尾部）重规划一次。
  进 system 而不是 payload 的道理与职责说明相同：payload 里的东西模型会当「数据」引用；
- 只纠一次，纠完还是 chat 就沿用原答复；**只对构建助手**——别的智能体说一段先后，
  很可能就是要你照着做一遍；
- 两次调用的 token 都算进这一轮（只记后一次会让压缩水位偏低），观测上留
  `studio_build_nudge=retried`。

`_looks_like_process` 的判据要窄。它不是通用意图识别，只是「这一轮白过了」的那一种：
带问号、带「怎么 / 如何」的一律不算，超过 300 字也不算。

### 还有一条不是我们引入的：工具正文被当成了答复

上面那张表最后一行，跟提示词无关。模型重复调同一个工具（同参数）时，
`plan_request` 的收敛分支直接拿工具的 `message` 当答案交出去——而
`studio_describe resource=workflow` 在 0 张时的 message 是写给模型的：

> 当前租户还没有任何编排流程。新建用 studio_workflow_save mode=create，但要先
> studio_describe resource=agent 看有哪些智能体……

读工具的 message 就是正文，这条早就写在 §16 里；这回漏的是**清单类工具**。改成：

> 当前租户还没有任何编排流程。想建一张，把「谁先做、再做什么、按什么分流」说清楚就行，
> 我会起草一版给你确认，确认后才会建。

用例（`test_studio_tools.py`、`test_studio_workflow_tools.py`）现在盯两条：这段正文里
不许出现 `studio_`，也不许出现 `mode=`。

### 最终验收

同一条消息（`/clear` 之后直接发，不带 `/build`）连打 5 次：**5 次都交出了草稿**，
其中 3 次一路走到确认卡；另外三种说法（新流程、带角色、纯提问）分别走到卡、走到卡、
只读清单不作答，没有一次以「要不要起草」收尾。
