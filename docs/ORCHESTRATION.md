# 智能体编排（Workflow）：把委派序列声明化

> **状态（2026-11-13）：P0 / P1 / P2 已实现并全量回归通过。**
> 代码在 `app/orchestration/`（定义 + 编译期校验 + 解释器）、
> `app/services/agent_invoker.py`（委派与编排共用的唯一调用实现）、
> `app/services/workflow_service.py`（增删改查、run 生命周期、续跑）、
> `app/api/routes/workflows.py`（管理与运行记录）。
> 本文原本要说的不是「怎么加一个 DAG 引擎」，而是**凭什么现在可以做**——
> `A2A.md` §2/§12 两处都写着
> 「不做编排」，理由是同一条：图进了数据库，配置与代码的边界就没了。
> 那三条不撤销，只是把边界挪到一个能守住的位置。挪法见 §2；
> 实现时与设计稿不一样的地方、以及踩到的东西，见 §12。

## 0. 一句话

**编排不新增执行语义，只新增「谁在第几步」。**

每个节点跑的还是 `delegate_to_agent` 那一套子调用：同一套边界收窄、同一套审批链、
同一个 span、同一套成本归属。编排多出来的只有一个东西——**顺序是人事先写死的，不是模型临场选的**。

## 1. 委派与编排，买的是两样不同的东西

| | 委派 handoff（已有） | 编排 workflow（本文） |
|---|---|---|
| 谁决定路径 | 模型，运行时 | 人，配置时 |
| 同一输入 | 可能走不同路径 | 走同一条路径 |
| 出问题时 | 看 trace 才知道它当时怎么想的 | 图就是答案，对照图即可 |
| 改行为 | 改提示词，靠模型领会 | 改配置，有版本号 |
| 代价 | 不可回归、不可预测 | 僵硬：没写进图的分支就是不会发生 |

所以编排的适用面很窄：**步骤可枚举、顺序有要求、且出错要能复盘**的流程
（巡检、工单分派、发布前核验）。开放式问答套编排，只会得到一条走不通的路
加一句「流程不允许」。

技能（`SKILLS.md`）与编排不在同一层：技能是**单 Agent 内部**的动作序列
（`ActionPlan` 一轮一个动作），编排是**Agent 之上**的顺序。`SKILLS.md` 说
「不做 DAG / 多步编排，硬塞流程图会变成两套调度」——那条对技能仍然成立，
因为编排不往 `ActionPlan` 里塞任何东西，Agent 内部的调度规则一个字不改。

## 2. 三条旧结论真正担心的是什么

原文写的是「图结构进数据库，等于把配置和代码的边界抹掉」。拆开看是三个具体风险：

| 担心 | 具体会坏在哪 | 本文的守法 |
|---|---|---|
| 权限判定失去唯一来源 | 图里配了谁调谁，就可能有人以为「图里连了 = 有权连」 | 编排**不参与**权限判定；每次节点调用仍走 `agent_subset`，逐跳收窄（§4 D3） |
| 恢复语义分叉 | 动态建 LangGraph 子图 → 审批恢复、checkpoint、thread 归属再长出一套 | 解释器是固定的，状态只有「游标 + 黑板」；审批恢复复用既有委派审批路径（§6） |
| 配置漂移成第二份事实 | 图说 A→B，实际跑的是 A→C，两处对不上且没人发现 | 图只画「应该这样」，拓扑只画「实际这样」，**差异本身进界面**（§8） |

第一条是最要命的。所以本文有一条硬约束：

> **`definition` 里不允许出现「能力」——只有 agent 名、任务模板、顺序与条件。**
> 不能内联新 Agent、不能临时给工具、不能写提示词覆盖。图能改的只有「什么时候轮到谁」。

## 3. 数据结构

```jsonc
{
  "id": "wf_alert_triage",
  "revision": 3,                    // 只在**图**变了时 +1；跑起来就冻结，中途改图不影响在飞的 run
  "name": "设备告警排查",
  "entry": "classify",
  "max_nodes": 12,                  // 本图允许跑的节点数（与模型的 max_per_turn 分账，见 §7）
  "nodes": [
    {"id": "classify", "agent": "cs",
     "task": "判断这条告警属于哪一类：{{input.text}}",
     "emit": {"field": "category", "values": ["电控", "液压"]},
     "next": [
       {"when": {"key": "category", "op": "in", "value": ["电控", "液压"]}, "to": "diagnose"},
       {"when": null, "to": "answer"}          // null = 兜底边，必须显式写
     ]},
    {"id": "diagnose", "agent": "tech",
     "task": "按 {{nodes.classify.category}} 给出排查步骤：{{input.text}}",
     "inputs": {"category": "$nodes.classify.category"},
     "on_error": "fail",
     "next": [{"when": null, "to": "onsite"}]},
    {"id": "onsite", "agent": "field",
     "task": "把结论整理成现场可执行的工单：{{nodes.diagnose}}",
     "next": [{"when": null, "to": "answer"}]},
    {"id": "answer", "agent": null, "kind": "compose",
     "task": "汇总上游结论，用一段话回复用户。",
     "next": []}
  ]
}
```

几条刻意的限制：

- **`conditions` 只允许 `eq / neq / in / gt / lt` + 一个键路径**。没有表达式语言、
  没有脚本、没有 `{{#if}}`。要复杂判断就再加一个 Agent 节点。
- **`inputs` 是显式映射**，键必须已在黑板上，否则**编译期**报错。
  不在运行时给空串——静默的空值比报错难查十倍。
- **`next` 必须有一条 `when: null` 的兜底边**（终节点除外）。没有兜底边意味着
  「条件都不满足时流程静默死掉」，那是所有工作流引擎最经典的坑。
- **`kind: "compose"` 是唯一不需要 agent 的节点**：它只把上游输出拼成一段话，
  不调模型。要给用户一句像样的答复又不想多花一次调用时用它。
- **`kind: "parallel"` 不需要自己的 `task`**：它自己不执行任何东西，每个分支各带
  `task`，引擎也只渲染分支的。写在这儿的文字只当说明用，不参与执行。

## 4. 五个决定

### D1 图在配置里，解释器在代码里

不用 LangGraph 动态建图。原因很实际：现有审批恢复依赖「父图不中断、子图停在
`create_and_wait_approval`」，`interrupts.py` 与 `chat_service` 都按这个形状写的。
动态子图会把 `thread_id` 归属、中断载荷、`pending_delegated_approval` 三件事
再推演一遍，而收益只是省掉一个 `while`。

解释器的状态只有两样：**游标**（下一个节点 id）与**黑板**（节点输出）。
恢复 = 读这两样继续，没有第三种情况。

### D2 节点之间只传结论，不传对话

与 `A2A.md` §7 同源：一条链上 B 不该看到用户对 A 说的原话。所以节点拿到的
只有 `task` 模板渲染出的那一段（模板只能取黑板里的键，不能取原始消息），
以及 `refs` 里显式列出的材料。

代价说清楚：**编排不能「传话」，只能「传结论」**。上一节点没写进 `emit` 的东西，
下一节点永远看不到。这是它能被审计、能被 replay 的原因——也是它经常不够用的原因。

单节点输出上限 `max_chars`（默认 2000，顶 8000），超了截断并在黑板里标
`truncated: true`，不静默。

### D3 次数预算分账，深度预算共用

**这是全篇最关键的一处。** 现有 `DelegationLimits.max_per_turn` 默认 3，是给
「模型临场决定要不要再转一次」踩刹车的。一条 5 节点的编排会被它卡死在第四个节点。

两类风险不同源：

| | `max_per_turn` 防的 | `max_nodes` 防的 |
|---|---|---|
| 谁产生的次数 | 模型即兴 | 人配的，有版本号，界面上看得见 |
| 典型事故 | 答不好就换个目标重试，烧钱 | 图配了 40 步，一次请求跑十分钟 |
| 所以 | 按次计，默认 3 | 按图计，默认 12，硬顶 20 |

**深度在编排里不累积。** `max_depth` 防的是「只读 Agent 借两跳变成可执行代码」，
而编排的每一跳都以**发起方**为父（§12.9），不构成 A→B→C 的链，所以运行时深度恒为 1。
图能跑多长由 `max_nodes` 管；深度只回答一件事——发起方还能不能转交。

换句话说：**可以多跑几步，不能借链变得更深。** 次数是配额，深度是边界。

### D4 并行只用于收集，不用于合成答案

`parallel` 节点：N ≤ 4 个分支，每个分支必须声明自己的 `emit` 字段。合并规则是
**按 key 摊平成数组**，引擎不做任何语义合并——不投票、不选优、不「综合两方观点」。

`A2A.md` §12 说「合并多份答案的规则没人定得了」，那条仍然成立。所以这里只做
**收集**：三台设备各查一次状态，得到三条状态，拼成一个列表。谁要是想要「两个
Agent 各写一版，再选好的那份」，那是评测问题，不是编排问题。

- 并发上限 2（DB 连接池与供应商速率限制，不是拍脑袋）；
- 任一分支失败 → 整节点失败，黑板里不留半个键；要容忍缺项必须显式写 `on_error: "skip"`，
  且结果里带 `missing: [branch_id]`。

### D5 触发是显式的，模型不自己选编排

不给 planner 增加 `workflow` 意图。让模型选图，等于把刚刚买到的确定性又交回给模型。
入口只有对话，但有两种操作方式：输入框的下拉里选这条流程（`ChatRequest.workflow`），
或直接打 `/workflow <name>`。两者产出同一个 `Command`，见 §12.6。

定时触发不在本文范围：那需要调度器、错过补偿、并发互斥，是另一件事。

## 5. 执行模型

```
run   = load(workflow, revision)      # 冻结：跑起来之后管理员改图不影响本 run
bb    = {}                            # 黑板：node_id -> 输出
cursor = run.entry

while cursor and run.nodes_used < run.max_nodes:
    node = run.nodes[cursor]
    task = render(node.task, bb, input)          # 模板只能取 bb 的键，缺失即编译期报错
    inv  = invoke(node.agent, task, refs=node.refs,
                  delegation=child(node.agent))  # ← 既有 subcall，一字不改

    match inv.status:
        completed:        bb[node.id] = truncate(inv.output, node.emit.max_chars)
                          cursor = pick_edge(node, bb) or fail("no_matching_edge")
        awaiting_approval: return pause(run, cursor, inv.approval_id)
        failed:           node.on_error == "skip"
                              ? (bb[node.id] = {"missing": inv.error_code}, cursor = next)
                              : return fail(run, node, inv.error_code)
finish(run, compose(bb))
```

三处值得单独说：

**`invoke` 就是 `delegate_to_agent` 的核心。** 实现时把它抽成
`agent_invoker.invoke(...)`，`delegate_to_agent` 变成「模型调用它的薄壳」。
两处各写一份的下场是：编排绕过了边界校验，而所有单测都还是绿的。

**`pause` 不新开审批。** 直接复用既有「委派来的审批单」那条路：审批单由被调方开，
`approval.delegated_from` 指向发起方，结论回到发起方会话。`run` 只记 `cursor`
与 `approval_id`，不复制审批内容——复制就会有两份状态，然后慢慢不一致。

**`cursor` 在调用之前就落库。** 先记「我要跑第 3 个节点」再跑，进程崩了重启能
知道崩在哪；反过来只会在日志里留下一句「不知道跑到哪了」。

## 6. 状态与恢复

`workflow_runs`：`id / tenant_id / workflow_id / revision / thread_id /
conversation_id / run_id / status / cursor / blackboard(JSONB) / nodes_used /
started_at / finished_at`

| status | 含义 | 谁来推进 |
|---|---|---|
| `running` | 解释器在跑 | — |
| `paused` | 停在某节点等审批 | 审批终态后由 `close_runs_for_approval` 的同一路径唤醒 |
| `completed` | 走到终节点 | — |
| `failed` | 某节点失败且 `on_error=fail` | — |
| `cancelled` | 用户取消 / 审批被拒 / 过期 | 审批侧 |

`paused` 的唤醒挂在既有的审批收口上（`run_service.close_runs_for_approval` 已经
在两个终态写入点被调用），不新增一个轮询器。过期走 `expiry_service`，语义同审批过期。

## 7. 观测与呈现

一次 run = **1 条 trace**（发起方的），每个节点 = 一个 `kind="agent"` 的 span，
带 `attrs.workflow_run_id` / `attrs.node_id` / `attrs.revision`。

这样详情页不需要新组件：既有的「编排流程」卡片本来就是按 span 树摊平的，节点
自动成为其中的一段，点进去就是该节点的子调用详情。

**拓扑页是这次设计里唯一「新长出来」的界面**，因为它终于有了可对账的东西：

| 层 | 画法 | 回答 |
|---|---|---|
| 声明 | 灰虚线 | 配的图长什么样 |
| 实际 | 实线，按 ok / 暂停 / 被拒 着色 | 这周真的走了哪几条 |

两种边不一致时，两个方向都有信息量：
- **声明了但从没跑过** → 配了没人用，或者入口藏得太深；
- **跑过但从没声明** → 模型自主委派的路径。要么该把它固化成流程，要么说明边界太宽、
  模型在替人做路由。

这正好补上 `observability.py` 里那句「平台上没有编排配置可对账，硬画等于编造」——
有了配置之后，对账才成立，而不是编造。

## 8. 明确不做

| 事项 | 理由 |
|---|---|
| 运行时改图 | 图是版本化配置，不是运行时状态。要改就发新 revision |
| 条件里的表达式语言 | 一旦允许写表达式，就会有人写 `len(x) > 3 and y.startswith(...)`，然后图变成代码 |
| 循环边 | 只允许 DAG。要重复就用 `parallel` 显式列，不给自己留死循环的可能 |
| 编排级审批 | 一次写操作只过一次人的手（`A2A.md` §9）。再加一层 gate = 两次确认，人会对确认卡闭眼 |
| 跨租户 | 租户是硬边界 |
| 节点内联提示词 / 临时给工具 | 越过 §2 那条硬约束，等于绕过 `agent_subset` |
| 定时触发 | 需要调度、错过补偿、并发互斥。P3 之后再说 |

## 10. 验收用例

每条都要能在去掉实现后失败。

1. A→B 且 B 边界宽于 A → 整 run `failed`，错误码 `DELEGATE_WIDENS`，
   节点 `B` 的 span 上带 `violation`。**（反向：编排里若跳过 `agent_subset`，这条绿）**
2. 5 节点编排、`cs.max_per_turn=3` → **仍然跑完 5 个节点**；把次数改成与
   `max_per_turn` 共用 → 第 4 个节点失败。**（反向：分账写错就是第二条的现象）**
3. `cs.max_delegation_depth=1`、编排 3 跳 → 第 3 跳被拒，理由 `depth`。
   深度必须**共用**，与次数分账是两条相反的规则，不能一起改。
4. 节点 2 停在审批 → run 为 `paused`；**审批单只有 1 张**；批准后从节点 2 继续，
   `nodes_used` 不清零。**（反向：从头重跑会在外部系统写两次）**
5. run 跑到节点 3 时把 `definition` 改成 6 个节点 → 本 run 仍按 `revision=旧` 走完；
   下一次 run 用新 revision。
6. 节点输出 5000 字、`max_chars=2000` → 黑板里是 2000 字且 `truncated=true`，
   下游拿到的是截断后的。**（反向：截断但不标 = 下游以为看到了全部）**
7. 模板里引用 `{{nodes.diagnose}}` 而 `diagnose` 不在 `diagnose` 节点之前的路径上
   → **保存时**拒绝，不是运行时给空串。
8. `parallel` 3 分支，1 个失败 → 整节点失败，黑板里没有该节点的键；
   加 `on_error: "skip"` 后才允许，且结果带 `missing`。
9. 审计：一次 3 节点 run → 3 条 `agent_delegated`，`metadata` 各带
   `workflow_run_id` 与 `node_id`，`from_agent` 都是**发起方**（不是上一个节点，见 §12.9）。
10. 拓扑：一条声明了但窗口内没跑过的边 → `observed=false`、虚线；
    一条跑过但不在任何 workflow 里的边 → `declared=false`。

## 12. 实现回写：与设计稿不一样的地方

写了代码才知道的那部分。每一条都对应一处具体的坏法，不是口味。

### 12.1 编译期校验比设计稿多三条

| 规则 | 代码 | 不这么做的坏法 |
|---|---|---|
| **必须有兜底边**（`when: null`，且只能最后一条） | `WORKFLOW_NO_FALLBACK` | 条件全不命中时 `pick_edge` 返回 `None`，run 在跑到一半时失败，而配图的人以为它「总会往下走」 |
| **`max_nodes` 按最长路径判、不按节点总数判** | `_longest_paths` | 分支图（3 个节点、两条互斥边）会被「上限 2 装不下 3 个节点」误拒 |
| **模板与 `inputs` 的引用必须在必经路径上** | `_must_reach` + `WORKFLOW_UNREACHABLE_REFERENCE` | 引用一个分支里的节点，另一条分支走到时必然缺键；运行时报错比保存时报错难查一个数量级 |
| **条件键必须有来源** | `_check_condition_keys` + `WORKFLOW_UNKNOWN_CONDITION_KEY` | `resolve_key` 只在黑板的 `keys` 里找，而 `keys` 只来自声明的 `emit`。没人产出这个键 ⇒ 这条条件永远不成立 ⇒ 每次走兜底边。**不报错、没有日志**：分流那一步看起来在跑，实际从来没分过流 |

模板缺键抛 `TemplateMissing` 而**不给空串**：空串会让下游 Agent 收到一句「按 排查」，
它照样能编出一段像模像样的结论。

### 12.2 `resume` 是三种结局，不是一个布尔

审批那一跳可能是「批准且成功」「用户取消」「批准但执行失败」。写成一个布尔，
「用户取消」和「执行失败」会被归成同一件事——前者是人的决定，后者是故障，
在运行记录里混成一类之后就再也统计不出来。落库分别是
`cancelled / approval_rejected` 与 `failed / approval_failed`。

### 12.3 `nodes_json` 必须接在暂停前那段后面（踩到了）

解释器每段 run 的 `trace` 只包含**本段**跑过的节点。续跑时直接拿它覆盖
`nodes_json`，一条停过审批的 run 在运行页上就成了 `['execute', 'answer']`——
看起来像从第二个节点凭空开始。修法在 `_merge_nodes()`：接上暂停前那段，
并去掉末尾那条 `paused`（它记的是「还没产出」，而本次 trace 的第一条正是它的产出）。
`test_workflow_pause.py` 里有反向验证。

### 12.4 恢复后的节点不再走一次 planner（实现行为的确认）

设计稿写的是「审批恢复链路把结论给回来」。实测确认：子图从审批那一跳收尾，
`final_response` 就是执行结论，**不会再消费一个 `ActionPlan`**。所以测试里给
停住节点准备 3 个计划就够，多给一个反而会掩盖这条路径是否真走通。

### 12.5 `parallel` 的出边不进声明层

静态图无法确定并行节点之后的那一跳实际由谁发起（引擎用的是「进入并行之前」的
父上下文）。硬画会产生一条「跑过但没声明」的假边，把真正的信号淹掉。所以
`agent_edges(plan)` 只取 `parallel` 的**入边**。

### 12.6 没有「立即运行」接口，但触发有两个入口

`POST /api/v1/workflows/{name}/run` 刻意不存在。编排的输出必须落在一个会话里，
用户才看得见、审计才查得到、写操作才落得到同一条审批链上。开一个 `/run` 会让这三件事
同时断掉，而它多出来的能力只是「能被脚本调用」——那是定时触发要解决的问题。

**入口有两个，落到同一件事上：**

| 入口 | 形态 |
|---|---|
| 打字 | 消息正文 `/workflow <name> <要处理的事>` |
| 选 | 对话输入框左下角的下拉里选一条流程，`ChatRequest.workflow=<name>`，正文就是输入 |

两条路都产出同一个 `Command`（`workflow_service.parse_command` /
`triggered_command`），**名字校验共用一份**。分开写就会出现「手打的名字不合法、
下拉选同一个名字却放行」，而排查时没人会想到是那两个分支不一样。
正文本身以 `/workflow` 开头时以正文为准——那是更明确的那句话。

三条界面与接口约定：

- **选了流程就不再传 `agent`**：流程每一步用节点自带的智能体，这条路上「谁回答」
  由节点决定。两个都传会被 422 拒掉（`CHAT_TARGET_CONFLICT`），而不是静默丢掉一个
  ——「我选了客服，回答却来自别人」在界面上无从查起。
- **流程读不到附件**：节点里没有「读附件」这一步，正文是唯一输入。带附件选流程时
  前端当场拦住并说明原因，不让它静悄悄失效。
- **流程是一次性触发**：发完自动回到直接对话。留着选中态，下一句「谢谢」会再跑一遍
  整张图——这不是用户想表达的意思。

### 12.7 顺手修掉的一个既有缺陷

`DelegationLimits.for_root()`：根上下文的 `delegation_limits` 原本从平台默认值
（`max_depth=2`）出发，之后沿链只取 min——于是 Agent 上配的
「最大转交深度 = 5」**永远不起作用**。这条此前没有测试覆盖，是被编排的深度预检
（「要走 3 跳，现在允许 2 跳」）照出来的。现在根以本 Agent 配置为基准，硬天花板内允许更宽。

同一个坑还有一处：`save_workflow()` 在更新已有流程时，`updated_at` 是库端
`onupdate`，flush 之后本地副本被置为过期，`expunge` 让它变成读不出值的游离对象，
接口层拼响应就 500。**更新一张已存在的流程必然 500**，此前没有用例踩到，
因为所有保存测试都只保存一次。修法是 flush 后 `refresh` 再脱离。

### 12.8 `emit` 默认是截断文本，要分流得显式声明抽取

`emit.field` 默认做的是把本节点输出的**前 `max_chars` 字**存进黑板。所以
`eq "泄漏"` 只有在整段回答恰好就是那两个字时才成立——按「分类 → 分流」配完，
条件几乎永远不命中，看起来像分支没生效（这条是上线实测照出来的）。

补了两种抽取，二选一：

| 写法 | 语义 | 适合 |
|---|---|---|
| `{"field":"category","values":["泄漏","超压","火警","其他"]}` | 回答里**最先出现**的那个枚举值；同位置取更长的 | 分类分流 |
| `{"field":"level","pattern":"风险等级[:：]\\s*([1-5])"}` | 第一个捕获组；没有捕获组就取整个匹配 | 有固定格式的数字 / 编号 |

规则都能在保存时拒绝，不留到运行时：

- **抽不到 → 退回截断文本**，不是留空。留空会让下游模板缺键、整条链跑到后半段才
  失败；退回截断则条件不命中、走兜底边——那是显式声明过的路。
- **`values` 与 `pattern` 同时给 → 拒绝**。实际存哪个取决于优先序，而配图的人看不出来。
- **配了抽取却没有 `emit.field` → 拒绝**。看起来该分流，实际什么都不会发生。
- **`pattern` 编译不过 → 拒绝**。别等某个节点真跑完才发现正则写错，那时候要重跑整条链。
- **条件值与 `emit.values` 对不上 → 拒绝**（`WORKFLOW_CONDITION_NEVER_TRUE`）。
  枚举是「严重 / 轻微」而条件写 `eq 高危`、或者对着这种枚举写 `gt 5`，都是一条
  **死分支**：`condition_holds` 的 `gt/lt` 在 `float()` 失败时 `return False`，
  静默不命中，分流节点看着在跑、每次都走兜底边。判断只在能枚举得出值的时候做，
  纯截断与 `pattern` 不判；同一个键被多处产出时取并集，有一处不可枚举就跳过。
- 上限：枚举 20 项、每项 32 字；正则 200 字符。再多就不叫「收敛成一个值」了。

代价说清楚：**抽取失败与抽取成功在黑板里长得一样**（都是一个字符串），所以它只适合
「兜底边有实际意义」的图。要让失败可见得再加一个标记键——目前没有，这是已知取舍。

### 12.9 编排节点不以「上一个节点」为父（一次语义修正）

初版按「逐跳下传」实现：下一节点的父是刚跑完的那个 Agent，深度逐跳累积。
真实用例第一条就撞墙——「只读 Agent 查规程 → 可写 Agent 落单」被判成
`DELEGATE_WIDENS`（只读的不能把任务交给可写的），而这条分工恰恰是编排存在的理由：
查和写分开，才谈得上边界收窄。

纠正后的语义：**编排不是 A 把任务转交给 B，而是人一声令下、图依次调度 A、B。**
每个节点都跟**发起方**重新比一次边界。连带四处变化：

| 位置 | 初版 | 现在 |
|---|---|---|
| 运行时深度 | 逐跳累积（A→B→C 是 3 跳） | 恒为 1 跳 |
| 审计 `from_agent` | 上一个节点 | 发起方（真正发起这一跳的是人） |
| 深度预检 | 图的 agent 节点数 > `max_depth` 就拒 | 只看发起方还能不能转交（`max_depth ≥ 1`） |
| 续跑 | 从 `nodes_json` 逐跳重放上下文 | 直接用补全了边界的根 |

不是安全放松：每次调用仍然重新判定边界，「管理员收窄立即生效」不变（`A2A.md` §9）；
每次写操作仍然走审批。代价说清楚——**管理员能配出「只读 → 可写」的链**。这条能力
由 `agent:write` 守着，而配图本身就是治理动作。

### 12.11 图是「总览卡片 + 单步详情」，不是自由画布

控制台的编排页原来把 `definition` 摊成一个 JSON 文本框：能改，但「第三个节点之后
分了两岔」在 JSON 里看不出来，改错也要等保存才被后端拒。

第一版改成「每个节点一张完整表单」——能用了，但三张卡片就超过一屏：找「第 4 步改的那格」
要靠滚动，而改动图的时候人脑子里想的是「第 2 步要加个条件」，不是「往下翻 600 像素」。
现在分两层：

- **总览**（`.wf-card`）：走一遍图排出的顺序，一步一张小卡片，只写「第几步 / id /
  类型 / 承办者 / 往哪走（`1 条条件 · 其余 →3`）」。卡片是 `<button>`，**不含任何输入框**——
  能填的地方只出现在详情里，免得分不清「这里能不能打字」。
- **详情**（`.wf-detail`）：只画被点开的那一步，完整表单（id、类型、智能体、任务、
  输出与边界、下一步）都在这里。标题行写「配置第 N 步」，两侧是「← 第 N-1 步 /
  第 N+1 步 →」，顺着往下改不用回总览找卡片。

默认选中入口；添加步骤后选中新那一步；删掉正在看的那一步，选中落到原位（原来第三步
没了就落在新的第三步），否则详情卡突然空掉像页面坏了。保存被拒时后端点名的节点会被
**自动选开**并标红——只标红不选中的话，人还得自己点开猜是哪个字段。

**为什么不做画布。** 这张图的形状只有「链 + 条件分叉 + 并行收集」，坐标不携带信息；
而自由画布会让人以为节点可以随便连，可后端只接受 DAG、必须有兜底边、不能有走不到的
节点。画布能表达而保存不了的东西越多，界面就越像在骗人。

**但要有一张只读的形状图。** 编辑页的三行字（`1 条条件 · 其余 →3`）说的是「有分叉」，
画出来才是「哪一支走哪条、其余怎么绕」。所以确认卡与结果气泡上有一张只读 SVG
（`render.js` 的 `flowDiagram`）：一层一行、同层最多三列，兜底边画成虚线并写「其余」，
跨层的边（跳过中间那一步的「其余」）走右侧绕行通道——不绕的话它会从中间那张卡片
背后穿过去，看着像连到了那个节点上。它**只读**：能点的还是下面的表单。

四条实现约定：

1. **前端不判这张图能不能存。** 规则只有 `compile_definition` 一份，抄进前端必然
   与后端漂移（改了其中一处，另一处仍按老规矩放行）。保存被拒时后端返回
   `detail.node`，界面只负责把那张卡片标红、把那一步选开。
2. **只改认识的键**，其余原样留在对象里：`inputs`、`on_error`、未来加的字段都不丢，
   切回 JSON 视图看到的仍是同一份定义。
3. **打字不重绘。** `input` 只写数据；只有增删节点/分支/条件、换类型、换视图、切选中
   才重建 DOM。每次输入都 `innerHTML` 一遍，光标会跳到行首——这种毛病只有在真机上
   打字时才发现。
4. **出口按数据里的顺序画，不重排。** 新条件插在兜底之前；但手工写成「兜底在前」
   或「两条兜底」的图，界面**照原样**把它们列出来并指出会被拒（前者给「移到末尾」，
   后者把第二条标成「多余的兜底」可删）。按好看的顺序显示、保存却报错，这条错误在
   人看来就是平台在刁难他。同一条规则也管着「缺兜底」：红着说「条件都不满足时流程
   会停在这一步」，不等保存那一刻。

两个顺带的界面约定：改节点 `id` 会级联改写边、入口、`{{nodes.x}}` 与 `$nodes.x`
（否则「名字改了图还指旧名字」，报错说的是「指了不存在的节点」，联想不到是自己刚改的）；
删节点会提示还有几处模板引用指向它。**编辑器只降低手写 JSON 的门槛，不放宽任何一条
图规则**——放开循环、表达式、任意连线的讨论在 §8 已经否决过。

### 12.12 第三条配置入口：构建助手

控制台编排页之外，构建助手（`studio`）也能配流程：`studio_describe resource=workflow`
读清单与整张图，`studio_workflow_save` 建/改（启停也是它的一个字段），
`studio_workflow_delete` 删。三条铁律与前面几节同源：

1. **校验只有 `compile_definition` 一份。** 工具的 `definition` 原样转手
   `workflow_service.save_workflow`，助手这边不写第二套「有没有兜底边」的判断——
   否则会长出「控制台存得进去、助手存不进去」，而两边看到的都是「保存失败」。
   被拒时把 `WorkflowError.node` 一起给模型，它才能说出「第几步错了」。
   **唯一的例外是「图里的智能体存不存在」**：`compile_definition` 是纯函数，读不到库，
   而这句话又必须成立——存进库的是能跑的图。所以它放在 `save_workflow` 里
   （`_ensure_agents_available`），控制台与助手走同一个函数，口径仍然只有一份。
   拒绝理由带**当前租户可用的标识**：自然语言建图时模型不知道有哪些智能体，编一个
   `inspector` 是最自然的动作；只说「不存在」，下一轮它还会编。
   这条校验**只在图真的变了时执行**（新建，或传进来的 definition 与库里那份不同）：
   否则删掉一个智能体之后，引用它的流程连改名、停用都做不了。
   **内置智能体（构建助手）同样被这一层拒**（`WORKFLOW_INTERNAL_AGENT`）：它拿的是
   `studio_*`，职责是替人改配置，不是替图跑某一步业务。运行期本来就会以
   「不能承接转交任务（内置智能体）」拒绝（`agent_invoker`），在保存期拦是为了
   别把错误留到有人触发的那一刻。`studio_describe` 的「能放进编排图」那一行也
   因此只列业务智能体——列进去只会让模型填一张注定被拒的图。
2. **不传 `definition` 就是不动图**（只改显示名、说明或 `enabled`）。这一条被单测钉住：
   若把「没传」当成「清空」，一次改名就会删掉整张流程，而审批卡上写着「修改说明」。
3. **删除只删配置。** `workflow_runs` 在行上冻结了自己的 `definition`，未完结的 run
   照原图走完或继续等审批；结果里点名还有几条在跑——「删了之后它们还算数吗」
   是紧接着会问的那句话。只是暂时不想被触发就用 `enabled=false`。

**没有「立即运行」仍然是硬约束。** 助手也不能跑流程：它的工具集里只有读写配置的
那几个，加一个 `run` 就等于把上面 §12.6 的理由绕过去（结论不落会话、审计对不上、
写操作脱开同一条审批链）。

工具形态为什么是两个而不是三个，见 `docs/STUDIO_ASSISTANT.md` §4.2.1；
用例落点 `tests/unit/test_studio_workflow_tools.py`（17）。
