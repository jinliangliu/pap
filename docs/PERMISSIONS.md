# 权限：三态工具策略与平台开关

控制台「权限」页（`#/permissions`）回答一个问题：**这个工具，在这个租户里，
到底是能直接跑、要先确认，还是根本不能用。**

它不是工具配置页的另一份副本。工具页回答「这个工具怎么调」，权限页回答
「谁能用、要不要拦一下」，两者共用同一份注册表，但改的是两种东西。

---

## 1. 三层边界，只有中间这层是这一页管的

| 层 | 存在哪里 | 谁能改 | 回答什么 |
|---|---|---|---|
| 平台边界 | `ToolDefinition`（代码注册时） | 开发者 | 这个工具**最多**能做什么：`risk_level`、`required_scopes`、`requires_approval` |
| **租户策略** | `tenant_tool_policies`（本页） | 平台管理员 | 这个租户**实际**放不放行、要不要确认 |
| 智能体边界 | `agents.allowed_tools` / `allowed_connectors` | 智能体维护者 | 某个智能体能碰哪些 |

有效权限恒为三者交集，**任何一层都只能收窄不能放宽**。权限页把一个工具设成
「允许」，不会让它在缺少 scope 时能调、也不会让智能体边界之外的调用通过。

---

## 2. 三态：不是开关的三个档位

| 动作 | 模型目录 | 执行前 | 典型用途 |
|---|---|---|---|
| `allow` | 可见 | 按风险兜底：写入及以上仍审批 | 默认状态 |
| `confirm` | 可见 | **一律**先生成审批单 | 只读但敏感的查询（查别人站点的台账） |
| `deny` | 不可见 | 直接拒绝，审计 `DENIED_TENANT` | 下线某个工具，但不想删配置 |

三条判据都收在 `app/tools/gateway.py::approval_required` **一处**。
目录过滤、执行前判定、权限页回显都调它——分开写会出现「页面写需确认、
对话里直接跑了」，而且单独看每一处代码都是对的。

`deny` 与「未配置」在库里是两种状态：

- `action IS NULL` = 未配置，跟随平台默认动作；
- `action = 'deny'` = 显式拒绝，平台默认动作改成允许也不会回来。

`enabled` 布尔列已在 2026-11-16 的迁移里换成 `action`。两份并存时总有一处先被改，
而这类不一致只在「界面上点允许、执行时被拒」时才暴露。

---

## 3. 风险覆盖只能上调

页面上的「策略风险」可以把工具的真实风险**往上**调：读取 → 写入，之后它就不再
免审批。反方向不提供：

> 把 POST 工具标成「读取」等于给它开一条免审批直通。调用不再弹卡片、直接执行，
> 而从返回值、审计与页面上都看不出这次调用本该有人确认。

下调会在两个入口被拒（`gateway.risk_override_error`，权限页与租户策略接口共用），
400 的文案直接说明原因。库里被手改成 `read` 也不会生效：`risk_with_override`
只认上调。

---

## 4. 两个平台级开关（不分租户）

| 键 | 默认 | 作用 |
|---|---|---|
| `permissions.default_action` | `allow` | 未配置的工具默认放行还是拒绝 |
| `mcp.inbound_enabled` | `true` | 对外 MCP 通道总开关；关掉后 `/mcp` 与 `/mcp/upload` 都返回 503 |

为什么不分租户：同一个进程只有一套「不去逐个配置时怎么对待工具」的行为。
按租户分叉会让默认值失去意义——它的全部价值就是「不配也有一套可预期的行为」。

`default_action = deny` 是安全基线：新接一个连接器带来二十个工具时，
默认拒绝比默认放行更安全。设成拒绝后，只有显式配成 `allow` / `confirm` 的行还能被
模型看到。

`mcp.inbound_enabled` 是紧急刹车：改 nginx 要重载、删令牌要逐个点，这个开关点一下
就到。**鉴权仍在前面**（`BearerGate`），所以未认证请求依旧是 401——这不算泄露，
反而避免把「通道被关」这个状态告诉陌生人。

## 5. 生效时机与部署顺序

- 保存后立刻生效：租户策略缓存当场 `invalidate()`，下一轮工具调用就按新值走。
- 平台开关走 `platform_settings` 的内存缓存，保存即改写，不重启。
- **迁移必须先于代码上线**：`tenant_tool_policies.enabled` 被删、`action` 被加，
  旧代码读 `enabled` 会在迁移后直接 500。

```bash
uv run alembic upgrade head
systemctl restart pap-api   # 单进程 uvicorn，重启即全部生效
```

## 6. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/permissions` | 清单：每个工具的配置值与**生效值**一起返回 |
| PUT | `/api/v1/admin/permissions/tools/{name}` | 保存单工具；`action=null` 表示恢复未配置 |
| DELETE | `/api/v1/admin/permissions/tools/{name}` | 删行，回到「未配置」 |
| PUT | `/api/v1/admin/permissions/platform` | 两项平台开关 |

`?tenant=` 供平台管理员跨租户；不带则用当前身份所在租户。

清单里同时返回 `base_risk` / `action` / `effective_action` 三组值：只回前两组的话，
人得自己在脑子里过一遍「未配置 + 平台默认 = 什么」，而这个推导一旦和
`approval_required` 有一处不同，页面就成了错误信息源。

---

## 7. 不做什么

- **不做按人的授权**。人是通过角色与 scope 介入的，这一页只配「工具在这个租户里的
  结局」。把「张三能用、李四不能用」塞进工具策略，会和 RBAC 变成两套并行的事实。
- **不做审批人指定**。审批链由委派关系与审批服务决定，工具策略只说「要不要拦」。
- **不放宽平台边界**。`required_scopes` 与智能体边界在这一页完全不可见、不可改。
