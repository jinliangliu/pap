# 多智能体平台实战（六）：工具网关与观测

> 网关决定「谁不能做什么」，观测决定「是谁做了什么」。
> 这两个东西放在同一篇，因为它们服务于同一个问题：**信任的边界画在哪。**

---

| 篇 | 主题 | 回答的问题 |

**本篇小节**：一条公式 → 单一判定入口 → 子集判定 → 审计为什么不能跟业务同事务 →
span 树的三列 → 留什么不留什么 → 代价。

## 1. What：一条公式和四个部件

生效权限只有一条公式：

```
生效权限 = 人的权限 ∩ 入口 Agent 边界 ∩ 被委派 Agent 边界₂ ∩ …
```

箭头方向是「收」，不是「传」。链条中间任何一个 Agent 配宽了，也漏不到更下游——
它只能把整条链收得更紧。

四个部件各管一段：

| 部件 | 职责 | 不该做的事 |
|---|---|---|
| 注册表 | 存工具定义、风险等级、是否需审批 | 不判断谁能调 |
| 网关 | 判定 + 执行前检查（限流、连接器、沙箱） | 不组装 prompt |
| 审计 | 记录每一次判定与执行 | 不参与业务事务 |
| 观测 | 记录每一段耗时与状态 | 不记录业务内容本身 |

---

## 2. Why：目录和执行必须共用一份判据

这是本篇最核心的一条，也是实践中最容易写错的地方。

工具目录是给模型看的清单。执行拦截是在真正调用时做的检查。两者如果各写一套逻辑：

- **目录宽、执行严**：用户看到一个按钮，点下去报「无权限」。他会反复点。
- **目录严、执行宽**：更糟。清单里没有，但知道名字就能调通。这就是漏洞。

现实里两套逻辑一定会分叉。因为它们的输入不一样：目录生成时手里有 Agent 边界和用户 scope，
执行时手里多了一个工具实例和一次请求上下文。写的人会自然地「就地取用」，
两套判断就这么长出来了。

所以只能有一个判定函数，目录和执行都调它。

```python
def agent_denial(tool, agent, user_scopes) -> Denial | None:
    if not agent.can_write and is_write_risk(tool.risk):
        return Denial("write_forbidden")
    if agent.allowed_tools is not None and tool.name not in agent.allowed_tools:
        return Denial("tool_out_of_boundary")
    if tool.required_scope not in user_scopes:
        return Denial("scope")
    return None
```

注意它返回的是 `Denial | None` 而不是布尔值。返回值里带原因，
前端才能说清「为什么点不动」，日志才能聚合出「哪条规则挡得最多」。

## 3. How：子集判定是一个纯函数

委派时要回答：B 的边界是不是 A 的子集？这个判断**只能在执行前做**，
配置期给不出保证——目标是模型在规划之后才选的。

所以它必须是一个纯函数，不碰数据库，能直接用单元测试覆盖：

```python
def agent_subset(sub: AgentBoundary, sup: AgentBoundary) -> tuple[bool, str]:
    if sub.can_write and not sup.can_write:
        return False, "can_write"
    if sup.allowed_tools is not None and sub.allowed_tools is not None:
        for name in sub.allowed_tools:
            if name not in sup.allowed_tools:
                return False, f"allowed_tools:{name}"
    return True, ""
```

三个易错点，每个都对应一次真实的误判：

| 情况 | 正确判定 | 常见误判 |
|---|---|---|
| `A.allowed_tools = None` | B 可以任意设 | 以为 B 必须也是 None |
| `B.allowed_tools = None` | 合法，含义是「我不额外收窄」 | 当成越权，要求抄一遍父清单 |
| `A.allowed_tools = []` | B 只能是 `None` 或 `[]` | 以为 `None` 等于全放开 |

为什么 `B = None` 安全？因为最终权限是逐层求交，A 那一层还在。
把它当越权，代价是每建一个 Agent 都要复制父清单，抄漏一个才是真越权。

还有一条不能靠清单兜住：**`can_write` 挡的是一整类风险等级，不是名单里的几个名字。**
用工具清单去表达「不能写」，迟早会漏掉某个新增的写工具。

## 4. Why：审计不能跟业务同事务

直觉上，审计应该跟业务操作在同一个事务里——一起成功，一起回滚，多干净。

实际不行，两个原因。

**第一，回滚会带走证据。** 业务失败回滚时，审计行也没了。但「这次尝试失败了」
本身就是需要记录的事实，尤其当它是权限拒绝或者参数错误的时候。

**第二，行级安全会让它静默失败。** 审计表挂了 `FORCE ROW LEVEL SECURITY`。
如果审计写入的会话没有正确的租户上下文，插入会被过滤成 0 行——
**不报错，不抛异常，就是没写进去。**

这个 bug 在 SQLite 上测不出来（SQLite 没有 RLS），在 PostgreSQL 上也不会报错。
表现是「功能都正常，审计表就是空的」。

正确写法：审计自带上下文，单开会话。

```python
async with tenant_scope(TenantContext(tenant_id=tenant_id)):
    async with async_session_factory() as audit_session:
        audit_session.add(AuditLog(...))
        await audit_session.commit()
```

这段代码看起来啰嗦，但它是「审计真的写进去了」的唯一保证。写完还要读回来断言一次。

## 5. How：span 树的三列

观测数据只有一个结构：树。每条 span 有 `trace_id`、`span_id`、`parent_span_id`，
前端自己建树。

有三列是设计过的，不是顺手加的：

| 列 | 为什么必须成列 |
|---|---|
| `seq` | 同一 trace 内并列 span（如同一轮两个工具）顺序稳定，不依赖 `started_at`（可能完全相同） |
| `kind` | `run / graph / node / llm / tool / mcp / db / retrieval / approval / agent`，聚合时按类看 |
| `agent_name` | 委派时子图里的节点归被委派方，不是 trace 发起方 |

第三列值得展开。没有它，A 委派给 B 的那一轮里，B 的规划和工具调用认不出是谁的。
一整个 trace 看起来都是 A 干的。有了它，`GROUP BY agent_name` 就能画出委派拓扑。

**为什么不放 JSON 字段里？** 因为要按它聚合。扫 JSON 会随数据量线性退化，
而且 `->>` 和 `json_extract` 不通用——同一段查询在 PostgreSQL 和 SQLite 上要写两遍。

## 6. How：留什么，不留什么

观测最容易走两个极端：什么都不记（出事了没法查），什么都记（存储爆炸且泄露风险）。

这里的取舍是：**记结构，不记内容。**

| 记 | 不记 |
|---|---|
| 工具名、参数哈希、耗时、状态 | 参数原文（可能含个人信息） |
| 检索命中数、top1 文档 id | 切片全文 |
| LLM 的 token 数、模型名、状态 | 正常轮次的完整 prompt |

**唯一的例外是错误轮次。** `llm.call` 失败时，把完整输入留下来。

原因很实际：结构化输出被工具清单带偏这种问题，只看错误信息永远查不出来。
「无法解析」四个字背后可能是二十种原因。留着完整 prompt，可以离线重放，
十分钟定位；不留，就只能靠猜和复现。

代价是这类 span 的 `content` 字段很大。做法是只对 `status='error'` 的行保留，
并定期清理。

## 7. How：网关还管两件容易被忘的事

网关除了判定权限，还有两个职责，都是「不做就会在半夜被叫起来」的类型。

### 7.1 限流必须在判定之后

顺序是：先判权限，再限流。反了会有一个难受的效果：没有权限的调用也消耗配额，
一个写脚本刷接口的人能把正常用户的配额耗光——而他本来一次都调不通。

计数放 Redis，按「租户 + 工具」两个维度。只按租户限，一个高频工具会把同租户
其他工具挤掉；只按工具限，一个租户刷满会影响所有租户。

### 7.2 沙箱执行走独立进程

需要跑代码的工具（数据清洗、格式转换）不能在主进程里 `exec`。
一旦那段代码死循环或者吃满内存，整个服务跟着完蛋。

所以沙箱是一个独立服务，通过 HTTP 调用，带三个约束：超时、内存上限、无网络。
「无网络」这条经常被忽略，但它是沙箱存在的理由——能联网的沙箱等于给了一个
不需要审批的任意 HTTP 客户端。

网关在这里的职责是：调用前确认沙箱可达，调用后按普通工具一样记 span 与审计。
沙箱挂了，工具应该从目录里消失，而不是调用时报 500。

## 8. Trade-off：这一层的账

**span 全量落库是写放大。** 一轮对话可能产生几十条 span。缓解办法是异步批量写、
按时间分区、只对慢请求保留全量。

**审计与观测有重叠，但不能合并。** 审计要回答「谁批准了什么」，是合规口径，必须
不可篡改、按租户隔离。观测要回答「哪一步慢」，是运维口径，可以采样、可以清理。
把两者合成一张表，最后两边都做不好。

**单一判定入口会让网关变胖。** 所有检查挤在一个函数里，改一处要跑全量回归。
这是有意的：宁可一个函数难改，也不要两个地方各判一半。

---

## 9. 本篇小结

- 生效权限是逐层求交，只收窄不放宽。
- 目录过滤与执行拦截必须共用同一个判定函数，否则一定分叉。
- 子集判定做成纯函数，`None` 的含义是「不额外收窄」，不是「全放开」。
- 审计不能与业务同事务，且必须自带租户上下文，否则在 PG 上静默失败。
- span 的 `agent_name` 必须成列，委派拓扑靠它聚合。
- 记结构不记内容，唯一的例外是错误轮次要留完整输入。

最后一篇讲编排：**怎么让一段话变成一张可校验的图，并且不把它搞成一个
「看起来很聪明、跑起来到处是坑」的功能。**
