# 知识库语料缺口清单

这份清单回答一个问题：**知识库答不了现场问题，缺的是检索能力还是资料？**
结论是资料，而且缺口比「少几份文档」更根本——**缺的是整类资料的形态**。

探测工具与用例已固化，补一类跑一次即可验证：

```bash
uv run python -m scripts.probe_knowledge_gaps                      # 全部 23 条
uv run python -m scripts.probe_knowledge_gaps --category 泄漏与隐患处置
uv run python -m scripts.probe_knowledge_gaps --min-covered 0.8    # 补完当闸门用
```

用例在 `tests/fixtures/knowledge_gap_probe.json`。它**不标 relevant**——补之前本就无解，
标了只是把期望写死。

## 1. 实测基线（2026-11-15，生产库）

```
合计：2/23 拿到内容（9%） | 空 0 · 扣 21 · 报错 0
```

三种状态必须分开看，它们是三种不同的病：

| 状态 | 含义 | 条数 |
|---|---|---|
| **空** | 召回即 0，查询词与语料没有任何交集 | **0** |
| **扣** | 有召回，但候选全被语义重筛判为「不回答问题」 | **21** |
| **中** | 拿到了内容——**不等于答对** | 2 |

**「空 0」是这份清单最重要的一个数字。** 它说明 BM25 从来没有「搜不到」的情况：
`阀`、`压力`、`报警`、`处理`、`作业` 这些通用词在《技术规范》里到处都是，
所以每条查询都能召回 5–12 条。问题在于召回来的全是**产品标准条文**，
没有一条在讲现场怎么做，于是重筛逐条判「不回答问题」——**判得对**。

那 2 条「中」也经不起看，都是误命中：

- `报警 等级 分级` → 命中《4.2 型号表示方法》。那里讲的是型号编码里的等级位，不是报警分级。
- `切断阀 跳闸 复位 操作` → 命中《5.3 智能控制器》。那里讲控制器应具备什么功能，不是复位怎么做。

所以真实覆盖是 **0/23**。

## 1.5 「补语料就能命中」的验证（2026-11-15，内存预演）

上面那个可证伪的预测——「因为基线空 0，补进规程后应当直接命中，不必动召回层」——
已经验过了。手上没有真实规程，所以用**内存索引预演**：从生产库读出 118 条活跃切片
作为基线，叠加一份**明确标注不得作为作业依据的测试规程**，只在进程内构造
`KnowledgeRetriever`，不写库、不建索引、不产生任何可检索的记录。

三组对照，同一批 4 条 leak 查询：

| 组 | 语料 | 召回 | 留 | top1 是否测试规程 |
|---|---|---|---|---|
| A 基线（不补） | 118 片 | 12 / 12 / 12 / 12 | 0 / 0 / 0 / 0 | 否 |
| B 补**规范写法** | 124 片 | 12 / 12 / 12 / 12 | **4 / 2 / 1 / 1** | **是 4/4** |
| C 补**坏写法** | 119 片 | 12 / 12 / 12 / 12 | **1 / 1 / 1 / 1** | **是 4/4** |

**结论一（预测成立）**：补进同类内容后 4/4 命中，召回层一行代码都不用改。
「需要向量检索」这个念头对现场类问题可以彻底放下。

**结论二（修正了本文档早先的一个说法）**：坏写法（整段一块、`section=正文`、无型号）
**也 4/4 命中**。所以切片形态**不影响「能不能拿到内容」**，只影响拿到什么：

- 规范写法：leak-01 留 4 条，分别是关阀、通风、设置警戒、上报时限——模型能逐条引用。
- 坏写法：留 1 条，是 6 个步骤粘在一起的整块——模型只能给一坨，用户没法照着做一步一确认。

（C 组召回仍 12 条、只留 1 条，是因为一大段同时命中了 4 个查询，重筛只保留一次；
不是没找到。）

这个区别不体现在命中率上，但直接决定回答有没有用。所以第 4 节的规范照旧要遵守，
只是理由要改对：**不是为了「不白补」，是为了「补了能照着做」。**

两份产品国标入库（27791 = 48 片、27790 = 119 片，活跃切片 618），同 23 条查询重跑：

```
合计 23 条：空 0 · 扣 18 · 中 5
```

|---|---|---|
| `调压箱 泄漏 通风` | GB 27791《5.2 箱体》 | **真**（箱体通风与泄压口，正是泄漏处置要引的条文） |
| `调压器 膜片 破损 表现` | GB 27790《6.9 失效状态》 | **真**（失效状态即破损表现） |
| `调压器 维护 保养 周期` | GB 27790《9.2 使用说明书》 | 仍属误命中（讲说明书要写哪些参数，没给周期） |

原先那 2 条误命中（型号表示方法、智能控制器）照旧存在。所以现场规程类语料
**依然缺**：产品标准回答「设备该做成什么样」，不回答「现场这一步怎么干」。

## 1.7 复测：补进三份计量标准、下架废止版之后（2026-11-16，生产库）

再入三份：GB/T 18604-2023（超声流量计，142 片）、GB/T 18603-2014（计量系统，111 片）、
GB 27791-2020（调压箱，61 片）。活跃切片 **884**，文档 12 份。

第一次跑出 **3/23**——比 §1.6 还少两条。原因不是新语料没用，而是**同一标准两个版本
同时在库里**：GB 27791-2020 的前言写着「代替 GB 27791—2011」，两版正文高度重合，
在 12 个候选位里互相挤占，`调压器 膜片 破损 表现` 由「中」变成「重筛全删」。
下架 2011 版（48 片，走 `soft_delete` + 审计）后重跑：

```
合计 23 条：空 0 · 扣 18 · 中 5
```

| 查询 | top1 | 判断 |
|---|---|---|
| `调压箱 泄漏 通风` | GB 27791-2020《5.2 箱体》 | **真**（现在落在现行版，不再是 2011 版） |
| `调压器 膜片 破损 表现` | GB 27790-2020《6.9 失效状态》 | **真**（失效状态即破损表现） |
| `切断阀 跳闸 复位 操作` | T/CGAS 027《5.3 智能控制器》 | **真** |
| `报警 等级 分级` | T/CGAS 027《4.2 型号表示方法》 | 误（讲型号编码，不是报警分级） |
| `过滤器 清洗 更换` | GB/T 18604《8.2 管道配置》 | 误（讲流量计上下游管道，不是过滤器维护） |

**教训**：语料数不是单调向好的。重复主题（同标准的废止版、同题材的两份标准）
会稀释候选位——「库里东西更多了，反而更答不上来」是真实的，判据要看
`recall` 与 `keep` 的差值，不要看文档数。

### 附录的 section 归属仍是个瑕疵

GB/T 18603-2014 的 `表 B.1` 被标成《10 运行和维护 / B.1 计量系统》：附录不在章号之下，
section 沿用了上一个遇到的章标题。与 27791-2011 第 7 章同类——检索不受影响，
但引用定位会误导。**没有伪造标题**，等确认是补 OCR 还是接受现状。

### 这次复测顺带修掉的一个检索 bug

27791 入库后问「过滤精度和初始压损」永远答不上来，`tool_error=knowledge_not_found`。
实探下来召回第一名就是对的（《5.1 一般要求》，score 33.3），是**重筛把 12 条全删了**：
`rerank.MAX_PROMPT_CHARS` 是 500，而「5.1.6 过滤装置的过滤精度……」正好在**第 507 字**，
模型根本没看见那句话。切片上限是 800 字，两个常量早已脱钩。

已改 `MAX_PROMPT_CHARS = 900`，并加单测盯「重筛上限 ≥ `ingest.CHUNK_SIZE`」这个耦合。
**这不是放宽判定口径**——判定口径一个字没动，只是让模型看到整片。
改完同一句问话直接命中并给出引用。

## 2. 现有语料到底是什么

| 切片 | 字数 | 文档 |
|---|---|---|
| 93 | 54885 | TCGAS 027-2023《城镇燃气智能调压箱技术规范》（OCR） |
| 25 | 4310 | 平台自述：操作手册 / 项目规划 / 平台能力说明 / 使用说明 / approval_policy / overview |

表里是**参与检索的活跃切片**（`documents.status='READY'` 且 `chunk.is_active`），共 118 片。
库里 `document_chunks` 有 127 行，多出来的 9 行属于已下架文档——别拿 127 估算语料，
会高估近一成。

**118 个切片里 93 个来自同一份产品标准**，章节是「4 基本规定 / 5 技术要求 / 6 试验方法」。
它回答「**产品该造什么样、怎么检验**」，不回答「**现场该怎么干**」。
剩下 25 片是平台讲自己，跟业务无关。

这个形状本身就决定了：任何处置、操作、周期类问题都答不了，与检索质量无关。

## 3. 要补什么

先说明现状：**这六类目前一份都没有**。2026-11-15 查过仓库 `data/knowledge/`（只有 inbox /
manuals / notes / projects 四个目录，全是平台自述）与服务器 `uploads/`（已空），
库里唯一的业务文档就是那份产品标准。所以本清单是「待补」，不是「已有但没入库」。

按现场风险与提问频次排序。每类都给出「补进来应该能回答」的探测用例 id，
补完用 `--category` 跑一遍即可验收。

### P0 泄漏与隐患处置（当前 0/4 全「扣」）

现场风险最高的一类，也是「调压箱 泄漏 通风」那条投诉的落点。

| 要补 | 应命中用例 |
|---|---|
| 泄漏发现与初期处置：如何判断、先关什么、能不能动电气 | `leak-01` |
| 上报链路与时限：报给谁、多久内、报什么内容 | `leak-02` |
| 警戒与疏散：半径怎么定、谁来决定、如何隔离 | `leak-03` |
| 箱体通风要求：什么情况下强制通风、用什么设备、多久 | `leak-04` |

来源：企业自有《泄漏应急处置预案》《现场处置方案》、燃气运行单位安全操作规程。
**不要**拿产品标准里的「气密性试验」条文充当处置规程——那是出厂检验，不是现场动作。

### P0 报警与联锁动作（当前 1/4，且那 1 条是误命中）

| 要补 | 应命中用例 |
|---|---|
| 报警分级与各级响应动作（谁看、谁去、多久到） | `alarm-01`、`alarm-02` |
| 误报识别：如何区分传感器漂移、通信中断、真实超限 | `alarm-03` |
| 超压 → 切断 → 放散的联动逻辑与整定值 | `alarm-04` |

来源：设备厂家的控制器说明书（报警代码表是关键）、企业运行规程。
这一类的难点是**报警代码表**：现场最常问的是「E-03 是什么意思」，而代码表几乎总在厂家手册里。

### P1 停气复供与阀操作（当前 1/3）

| 要补 | 应命中用例 |
|---|---|
| 停气、置换、复供的作业步骤与合格判据 | `supply-01` |
| 切断阀跳闸后的复位条件（不是「怎么按」） | `supply-02` |
| 放散阀操作规程与放散量控制 | `supply-03` |

这一类的合规性最重（复供不合格会直接出事故），资料必须带**版本号与批准人**。

### P1 故障判断与处理（当前 0/4）

| 要补 | 应命中用例 |
|---|---|
| 出口压力异常的排查树：偏低 / 偏高各自往哪查 | `fault-01` |
| 喘振、异响、振荡的成因与处置 | `fault-02` |
| 冰堵 / 冻堵的成因、判断与解堵方法 | `fault-03` |
| 膜片破损的表现与更换要求 | `fault-04` |

来源：调压器厂家维修手册 + 企业故障案例库。**故障案例库的边际价值很高**——
现场问的往往是「上次那种情况怎么处理的」，这类内容标准里永远没有。

### P2 巡检与维护保养（当前 0/3）

| 要补 | 应命中用例 |
|---|---|
| 巡检周期、路线、项目、记录要求 | `maint-01` |
| 调压器保养周期与保养项 | `maint-02` |
| 过滤器清洗 / 滤芯更换的判据与周期 | `maint-03` |

这一类的答案通常是**表格**（周期 × 项目）。切片时注意别把表打散成互不相干的几段。

### P2 安全作业与应急（当前 0/5）

| 要补 | 应命中用例 |
|---|---|
| 动火作业审批层级与前置条件 | `permit-01` |
| 有限空间作业的气体检测、监护、救援要求 | `permit-02` |
| 作业票种类与办理流程 | `permit-03` |
| 应急预案的响应分级与启动条件 | `emerg-01` |
| 事故上报的时限与对象 | `emerg-02` |

这一类**可能不该进这个知识库**：作业票有独立的审批系统，应急预案有独立的发布渠道。
如果它们在别处，正确做法是让编排把这类问题路由过去，而不是复制一份容易过期的副本进来。
补之前先确认「有没有唯一权威来源」，有就接过去，别抄。

## 4. 补录规范（不影响命中，影响能不能照着做）

先说清楚：**不遵守这些规范不会「白补」**——§1.5 的 C 组已经证明，整段一块照样能命中。
所以这些规范不是为了「搜得到」，而是为了「搜到之后有用、可追溯、不出事」。
每条都标了它实际管的是什么。

1. **一份规程一个文档**。管的是**更新粒度与引用准确性**：六份合成一个大 PDF 入库，
   改其中一份就得整份重传，引用里还会出现「第 3 份资料的第 2 章」，查不到、也没法追责。
2. **标题层级必须真实**。管的是**引用可读性**。切片靠中文编号标题分节（`section` 存标题路径）。
   现有那份 OCR 的《技术规范》就是反面教材：「4.2 型号表示方法」被切成 **29 个切片**，
   因为一个表格被逐行拆开、每行都带同一个标题。补规程时优先给原生 Word/PDF，
   不要用扫描件 OCR 的产物。
3. **步骤类内容要能切成「一步一片」**。管的是**回答可用性**，这是最要紧的一条：
   整段 2000 字的处置流程切出来是一大块，用户拿到的是一屏文字，没法一步一确认。
   用编号步骤写，切片器才切得开；leak-01 在规范写法下能留 4 条独立步骤，坏写法只有 1 条整块。
4. **必须写适用设备型号**。管的是**安全**，而且是命中率完全测不出来的一项：
   同一句「切断阀复位」对 A 型和 B 型的动作不同，没有型号标注的规程会被当成通用答案，
   **这比没有更危险**。这一条不能靠工具验证，只能靠人审。
5. **来源字段留痕**：文件编号、版本、生效日期、批准人。管的是**可追溯**。
   现场按错误版本操作出了事，第一个问题就是「他看的是哪一版」。

对照 §1.5 的实验可以记住这个分工：**规范管「补了能不能照着做」，内容有无管「能不能搜到」。**

下面这份骨架按上述规范写好，拿到真实规程后照着填即可（**别把空模板原样扔进
`data/knowledge/`**，占位文本会被正常检索到）：

```markdown
# 城镇燃气调压箱泄漏应急处置规程

适用型号：XXX-A、XXX-B（其他型号不适用）
文件编号：XXX-2026-01　版本：V1.0　生效日期：2026-XX-XX　批准人：XXX

## 1 适用范围
本规程适用于上述型号调压箱在运行期间发生燃气泄漏时的现场处置。

## 2 处置步骤
1. 发现泄漏后立即关闭进气阀门，并记录阀位与时间。
2. 开启箱体强制通风，禁止启闭任何电气设备。
3. 设置警戒范围，疏散无关人员，警戒区内禁止明火与手机。
4. 在警戒区外等待专业人员到场，不得擅自复供。

## 3 上报要求
发现泄漏后 5 分钟内向值班调度首报，内容包括位置、气味浓度、已采取措施；
处置进展每 15 分钟续报一次。

## 4 常见错误
（这一节往往比步骤更有用：现场最容易漏的是哪一步、历史上出过什么差错。）
```

## 5. 补完怎么验收

1. 只跑这一类：`--category 泄漏与隐患处置`
2. 期望：4 条从「扣」变「中」，且 **top1 落在新补的文档上**
3. 如果变成「中」但 top1 还是《技术规范》，说明**这份资料压根没被召回**
   （查询词面被标准里的同名词占满），属于召回层问题——
   注意不要把它误判成「切片没做对」：§1.5 的 C 组证明切片再烂也能进 top1。
4. 再看引用粒度：每条查询留下的是几条独立步骤，还是一条大整块。
   这一步只能人眼看，但它决定回答能不能照着做
5. 全部补完后再跑全量 + `--min-covered 0.8` 收口

**关于「要不要上向量检索」**：这个判断已经不需要猜了。基线「空」为 0、补进同类内容后
4/4 命中（§1.5），说明现场类问题的瓶颈是资料，不是召回方式。
若真实规程补完仍大量「扣」，才算拿到了召回层真有问题的证据——那时再谈覆盖加权或向量召回。
**在此之前不要动检索**：这个平台已经因为提前动手改过两次并全部撤回。

## 6. 不该靠语料解决的问题

以下三类问题会被误当成「知识库答不了」，实际都不是知识库的事：

| 问题形态 | 正确去处 | 为什么不能进知识库 |
|---|---|---|
| 「现在 3 号箱出口压力多少」 | 实时数据工具（`query_pressure` 一类） | 知识库是静态文本，写进去当天就过期 |
| 「哪个站归谁管」「这台设备装的什么型号」 | 结构化台账 / 主数据 | 文档检索做不了精确匹配与聚合 |
| 「这个问题该问谁」 | 编排路由（`delegate_to_agent`） | 是调度问题，不是检索问题 |

这三类的共性是**需要实时或精确的答案**。知识库给的是「一般情况怎么做」，
给不出现场此刻的状态；硬塞进去只会得到一份没人维护的副本。
