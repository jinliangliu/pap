# 手工测试指南

面向人而不是 CI：每条用例都能复制执行，并给出**预期**与**怎么判断失败**。
自动化测试在 `tests/`，这里覆盖它测不到的东西——真实模型、真实数据库、
真实外部依赖，以及「看起来像 bug 但其实不是」的边界。

## 0. 准备

### 0.1 进服务器执行

```bash
ssh pap
cd /personal-agent-platform
H='X-Authenticated-Subject: pap-admin'                      # 默认租户的运维身份
H2='X-Authenticated-Tenant: test'                           # 申请切到测试租户
T='X-Authenticated-Subject: test-user'                      # 测试租户的成员
B=http://127.0.0.1:8000
```

直连 `127.0.0.1:8000` 免 Basic 认证，但**只有已存在的身份**能被 gateway 模式接受；
公网入口（80 端口）由 Nginx 做 Basic 认证并注入 `X-Authenticated-Subject`，
客户端自己伪造这个头会被覆盖。

### 0.2 两个租户、三个身份

| 身份 | 租户 | 能做什么 |
|---|---|---|
| `pap-admin` | `default` | 默认租户全部只读工具 + 写工具 |
| `test-user` | `test` | 同上，但数据完全独立 |
| 任意 | 申请非成员租户 | 一律 403 |

### 0.3 三条纪律

1. **不要用真实客户数据**，测试租户 `test` 就是为此准备的。
2. 写操作一定要**记下 `approval_id`**，否则后续 4 条用例没法做。
3. 出现异常先看日志，再判断是不是缺陷：
   `tail -100 /var/log/pap-api.log`、`journalctl -u personal-agent-platform -n 50`

### 0.4 浏览器控制台（可选）

不想敲 curl 时，把服务器 80 端口映射到本机：

```bash
ssh -N -L 8080:127.0.0.1:80 pap
```

浏览器打开 `http://127.0.0.1:8080/console/`，用 htpasswd 里的账号登录
（`pap-admin` + Nginx 密码；忘了就 `ssh pap 'htpasswd /etc/nginx/pap.htpasswd pap-admin'` 重设）。

页面能看就绪检查、当前身份、工具清单，能发对话、处理审批卡片、跑知识检索。
但它**不能切租户**——Nginx 固定把 `X-Authenticated-Tenant` 置空。
A 组的租户边界用例仍然要在服务器上用 curl 做。

## 1. 健康与就绪（H）

| # | 命令 | 预期 |
|---|---|---|
| H1 | `curl -s $B/health` | `{"status":"ok"}` |
| H2 | `curl -s $B/ready \| python3 -m json.tool` | `checks` 里 database / checkpointer / model_configured / tool_registry / rate_limiter / sandbox 全为 `true` |
| H3 | `curl -s $B/metrics \| head -20` | Prometheus 文本，能看到请求计数与耗时 |

**失败判据**：`/ready` 任一项 `false` 就是环境问题，后面全部不用测。

## 2. 身份与租户（A）

| # | 命令 | 预期 |
|---|---|---|
| A1 | `curl -s -H "$H" $B/api/v1/me` | `tenant_id=default`，`is_platform_admin=false` |
| A2 | `curl -s -o /dev/null -w '%{http_code}\n' -H "$T" -H "$H2" $B/api/v1/me` | `200`，且返回 `tenant_id=test` |
| A3 | `curl -s -o /dev/null -w '%{http_code}\n' -H "$H" -H "$H2" $B/api/v1/me` | `403`（pap-admin 不是 test 成员） |
| A4 | `curl -s -o /dev/null -w '%{http_code}\n' -H "$T" $B/api/v1/me` | `403`（test-user 落在 default，非其成员） |
| A5 | `curl -s -o /dev/null -w '%{http_code}\n' -H "$T" -H 'X-Authenticated-Tenant: nosuch' $B/api/v1/me` | `403`，不能凭空建租户 |

**为什么 A3/A4 是 403 而不是 401**：身份已确认，只是没有该租户的授权。
403 与 401 的区分是刻意设计的，看到 401 反而是缺陷。

## 3. 工具目录（T）

| # | 命令 | 预期 |
|---|---|---|
| T1 | `curl -s -H "$H" $B/api/v1/tools` | 本地 5 个：`get_platform_time` / `get_station_snapshot` / `search_knowledge` / `create_maintenance_ticket` / `execute_code`；启用 MCP 时另有 21 个 `prv_*` |
| T2 | 同上看 `requires_approval` | 本地后两个为 `true`、前三个为 `false`；`prv_apply_station_control` 为 `true` |

## 3b. 燃气 MCP（P）

前提：对端 `prv-mcp` 容器 healthy，平台 `.env` 有 `MCP_ENABLED=true` 与租户令牌。

| # | 操作 | 预期 |
|---|---|---|
| P1 | `default` 租户问「列出你能看到的所有燃气场站」 | 「共 10 个站点。」+ 逐条 `名称(序列号)`，**不是** 一段 JSON |
| P2 | `test` 租户（空白名单令牌）问同一句 | 「看不到任何站点…空白名单…不是服务故障，也不代表站点离线」 |
| P3 | 问「查一下 T002509008 的进出口压力」 | 「进口压力：1.538 kPa（正常）」这类一行读数 |
| P4 | 发起「把 T002511111 切到高压档」 | `status=awaiting_approval`；确认后由服务端串 prepare→execute，不要手工分两步 |

**失败判据**：P1 输出里出现 `{"success": true` 这样的原始报文，说明结果渲染退化了
（读工具路径不经过模型，排版由 `_summarize_result` 决定）。

P2 的两种隔离形态要分清：**没配令牌**是 `MCP_CREDENTIAL_MISSING`（拒绝），
**配了空白名单**是空结果（`count=0`）。后者不是故障，别当 bug 报。

## 3b-3. 连接器（CN）—— 2026-11-12 起

前提：平台管理员身份改**定义**（`$H`），租户成员配**凭据**（`$T`）。
控制台 `#/connectors` 或直连 `/api/v1/connectors`。

| # | 操作 | 预期 |
|---|---|---|
| CN1 | 用租户成员 `$T` 调 `POST /api/v1/connectors` | 403「需要平台管理员权限才能修改连接器定义」 |
| CN2 | 管理员建一个 MCP 连接器，端点填本机假 MCP（可用 `mcp.server.mcpserver` 起一个） | 201；`GET` 列表里各租户都能看到它，但 `credential_set=false` |
| CN3 | 用 `$T` `PUT /credential` 写一个令牌 | 200；**响应里没有任何回显**，只有 `credential_set=true`；审计 `connector_credential_set` 的 `metadata` 里只有名字与 `created` |
| CN4 | 换 `$H2`（另一个租户）查同一条 | `credential_set=false`——凭据按租户算，不是全局 |
| CN5 | 不配凭据直接 `POST /check` | `status=error`，消息里出现「凭据」两个字，不会去连对端 |
| CN6 | 配好凭据再 `POST /check` | `status=ok`，带上「远端提供 N 个工具」 |
| CN7 | `POST /discover` → 选一个工具 → `POST /tools`（**不传** `risk_level`） | 200；`GET /tools` 里该工具 `risk_level=write`——批量接入的默认值是「写入」，不是「读取」 |
| CN8 | 承 CN7，对话里触发这个工具 | **弹审批卡片**（写入及以上强制审批）。若直接执行，说明默认值被改回 read |
| CN9 | `PATCH` 连接器把 `enabled` 置 false | 它下面的工具从 `/api/v1/tools` 消失；但连接器页仍能看到它，标「已停用」 |
| CN10 | 承 CN9，在对话里问「你能做什么」 | 模型不再提这些工具；直接点名调用也不会被放行 |
| CN11 | 下面还挂着工具时 `DELETE` 连接器 | 400「这个连接器下还有 N 个工具……」 |
| CN12 | 先逐个取消接入，再删除 | 200；本租户的凭据当场消失（`connector_credentials` 查不到该 id） |
| CN13 | 给智能体的 `allowed_connectors` 只填这个连接器名 | 工具目录里出现连接器下的全部工具，**内置工具消失**（这是并集语义，不是 bug） |
| CN14 | 委派：父 Agent 收窄了 `allowed_tools`、没配 `allowed_connectors`，子 Agent 配了 | 拒绝，理由点出 `allowed_connectors`——纯函数看不到连接器下有几个工具 |
| CN15 | 列表里用 `curl` 翻整段响应 | 整段文本里不含你刚写入的那串令牌（这是 CN 里最该每次回归的一条） |

**失败判据**：`check` 用别人的凭据测出「正常」（多租户下会让人对着 401 自我怀疑）、
或凭据没配却调通了（说明回退到了 `.env` 或旧行上的 `token`）。

| CH7b | 收起历史后按 Tab 键走到该图标 | 焦点可见，「回车」能展开——收起后它是唯一入口，键盘也得到得去 |
| CH8 | 窗口缩到 1080px 以下 | 历史面板堆在对话上方；图标仍在，点一下整块历史消失、对话上移（窄屏更需要它：那块占了小半屏） |

**失败判据**：切换历史后回答丢了上文（`thread_id` 没还原）、
删除后消息还在（`messages` 未级联删除）、或菜单开着一滚动就悬在旧坐标上
（它是 `fixed`，滚列表必须主动收起）。

**注意**：删除是**销毁**，四处都要清空，缺一处就是缺陷：

| 位置 | 检查方式 |
|---|---|
| `conversations` / `messages` | 详情接口 404，列表无该 id |
| `agent_runs` | `SELECT count(*) FROM agent_runs WHERE conversation_id='<id>'` → 0（外键是 SET NULL，不删行摘要会留） |
| checkpoint 三张表 | `SELECT count(*) FROM checkpoints WHERE thread_id='<内部 thread_id>'` → 0 |
| 磁盘 | `data/uploads/<tenant>/<conversation>/` 消失，artifacts 的对象文件消失 |

历史残留（老版本删过的会话）用 `python -m scripts.purge_orphan_traces` 查看，
加 `--apply` 才删；判定前提是线程在 `conversations` 里完全不存在。

而那是会一直长的库存。SA38 是 P2 的验收条件本身：**批准与执行之间上游被收窄**。
最容易写错的是把它报成「执行失败」——那样排障会去查一个完全正常的执行方。

**SA41–SA44 首次实机结果（2026-11-12，服务器 `569bc19`）**：四条全过。

- SA41：`cs.depth=0` → 回答「当前智能体被配置为不转交任务」；审计
  `reject_reason=depth`、`limits.max_depth=0`、`from_revision=2`。
- SA42：`cs=1`、`tech=5`、`tech2=5` → `cs→tech` completed，`tech→tech2`
  rejected，**`limits.max_depth=1`**（不是 tech 配的 5），文案「最多 1 跳」。
- SA43：PATCH `null` → API 返回 `None`、库里是 `NULL`、`tech/tech2` 的 5 不受影响；
  再跑一次两跳都 completed。**这一步才是「撤销收窄」的证明**，只做 SA41 说明不了。
- SA44：`tech` 与 `tech2` 都是 `traces=0` 但 `delegated_turns=2/1`，
  `sum(traces)+unattributed == total_traces` 仍然成立。删掉智能体后它们的
  `status` 变 `null`，历史行与计数照旧。

**踩到的一个非代码问题**：前两次让 `cs` 转交，模型都没动手——第一次反问
「走哪种方式」，第二次说「我只能发起一次」。不是工具坏了，是它按职责
（客服只转交不判断）在权衡。给 `cs` / `tech` 的 `instruction` 里写明
「第一动作就是调用 `delegate_to_agent`，不要反问」之后一次就通。
**测委派必须配 instruction**，否则测的是模型的主动性，不是转交逻辑。

**SA45–SA47 读法**：三条测的是同一件事的三面——**产物有没有归属**。
只做 SA45 的话，「存下来了」就已经满足；但「存下来了、谁都能引用」与
「存下来了、只有这一场对话能用」是两种产品。SA46 的后半（另一个会话）与
SA47 才是把「按会话保留」真的钉住的地方。

反向验证的写法：把 `artifacts.conversation_id` 改成写 NULL，SA45 会绿而
SA46 前半也绿——只有 SA46 后半与 SA47 会红。这就是为什么必须三条一起做。

**SA45–SA47 首次实机结果（2026-11-12，服务器 `ed6bf95`）**：三条全过。

- SA45：`p3c-saver` 存下 `巡检记录.csv`（93 字节），回答里给出 `artifact_id`；
  库里该行 `conversation_id=a3e2b6d6-…`，正是本会话的内部 id。同租户历史上传的
  三份 PDF 仍是 `NULL`——**存量没被误伤**，这一条要和「新行有归属」一起看。
- SA46 前半（同会话下一轮，换个话题）：转交 `completed`；材料里带
  `文件名 巡检记录.csv / 类型 text/csv / 大小 0.1KB`；子调用 `p3c-target` 回
  「只看到文件名与大小，看不到 CSV 行内容」——`refs` 传的是**引用**不是正文，
  这正是设计要的边界。trace 里恰好一个 `kind=agent`、`name=agent.p3c-target`、`ok`。
- SA46 后半（另一个 `thread_id` 用同一 id）：`status=failed`、
  `error_code=REF_NOT_VISIBLE`，回答原文「这份产物属于另一个会话，不能在这里引用。」
  **不是 `REF_GONE`**；该次运行只有 `p3c-saver` 的 10 个 span，`tool.call` 是
  `error`，**没有 `p3c-target` 的 agent span**——拒绝发生在子调用之前。
- SA47：带 `conversation_id` 只回 1 条（`巡检记录.csv`）；不带参数回 4 条，
  多出来的三份 PDF 的 `conversation_id` 是 `null`。第五份 `test-note.txt` 属于
  `test` 租户，两次都不出现——那是**归属过滤**，不是少了一行（查库确认过）。

**查 span 时的一个坑**：`obs_spans.trace_id` 是 32 位 `varchar`，关联的是
`obs_traces.trace_id`，**不是** `obs_traces.id`（uuid）。按 `t.id = s.trace_id`
会直接报 `operator does not exist`；硬转类型后返回 0 行，看着像「这次没记 span」。

**SA44 读法**：这一条测的是「并集」而不是「聚合」。日志聚合跑得通、数字也对，
但那一行压根不出现——因为 `tech` 没有自己的 trace。检查的是**那一行还在不在**，
不是数对不对：数错了会显眼，行没了不会。

**SA41–SA43 读法**：三条都在测同一件事的三种状态——0、被上游收窄、空。
只看 SA41 的话，「把 0 当成没配」也能过（默认 2 跳下这次转交本来就成立）；
必须做 SA43，才能证明「撤销收窄」没有变成「永久禁止」。

**SA38 的第一次实机结果就是错的**（2026-11-12）：状态码与错误码都对，但那段话是
「「运行值班」已完成你确认的操作。操作未执行：…… 」。前缀跟着「点了确认」走，
没跟着执行结果走。所以这一条要**读文案**，不能只看 `error_code`——
错误码只能证明拦截发生了，证明不了它没被说成成功。

**失败判据**：翻历史时被甩到底部（会自动跟随）、点了刷新停在半路（平滑滚动跨度过大）、
放大后顶栏被盖住、或发射时面板与火箭同时出现（看起来像火箭被拍掉）——
都会让人不敢用这个面板。SA17 / SA18 是另一类：助手会话从对话台消失之后，
若审计里只剩 `tool_succeeded`，就没有任何界面能回答「它到底改了什么」。
SA23 是最该较真的一条：**只要它「记住」了密钥，就必须当作已泄露处理**。
SA25–SA28 是委派（`docs/AGENT_CONNECT.md`）：最容易看错的是 SA26——
「拒绝」不该表现为「跑了很久然后说做不了」，子集校验必须在子调用之前完成；
若审计里没有那条 `agent_delegated`，事后就答不出「这个智能体被谁叫去干过活」。

SA29–SA35 是引用传递（同一文档 §3、§7.1）。这七条里最容易做错的是**把三种失败混成一种**：
「无权看」（SA30/SA32）、「已失效」（SA33）、「对方其实没拿到材料」（SA34/SA35）——
对外表现都像「这次没答好」，但一件该改授权、一件该重新上传、一件该改写任务描述。
只要有一条验收把三者混在一起，这个区分就等于没做。另外 SA31 要盯的是**部分成功**：
送过去 1 个也算完成，是这一层最危险的行为——A 会以为 B 看到了全部。

**实机跑过之后的五条经验（2026-11-12）**，省下后来人重复踩：

1. **做只读委派（SA25–SA28）时，`ops` 要建成 `can_write=false`。** 如果 `cs` 是只读而
   `ops` 可写，它会因子集校验被排除出「可转交清单」，模型于是回答「我这边没有运行值班
   对应的 name」——看起来像清单功能坏了，实际是它被过滤了。想测**写**委派（SA36–SA40）
   就反过来：两边都要可写，且 `cs` 的工具清单得包含 `ops` 要用的那个写工具。
2. **问题里要给全站点与日期。** 只说「3 号泵昨天怎么了」，模型会先反问站点和日期，
   一轮就问掉了；这一轮不产生委派，不要误判成转交失败。
3. **审计的 `metadata` 现在从接口就能读到**（`/admin/tenants/{id}/audit` 每条带
   `metadata`：`refs` / `depth` / `limits` / `from_agent` / `before`+`after` 都在里面）。
   2026-11-12 之前这一列只在库里，核对一次委派拒绝就得连库。仍要直接查库时记住两件事：
   **必须先设租户上下文**——应用角色 `pap_app` 不是超级用户，裸查带 RLS 的表返回 0 行
   （「没写过」与「看不见」同形）；库里的 `event_type` 是**全大写**
   （`AGENT_DELEGATED`），按小写查同样是 0 行。
4. **SA28 的回环护栏不靠模型。** 模型常常自己就拒绝「转回去」这个请求，
   于是护栏根本没被触发。要确定性地验证它，看单测
   `test_delegate_rejects_cycle` / `test_delegate_rejects_self`，不要拿手工结果当结论。

## 5d. 审批卡回放（AR）—— 刷新之后还在不在

对话台里那张「需要确认」的卡是跟着本轮响应长出来的，历史里只留 `approval_id`。
这四条测的就是「关掉页面再回来」这一段：卡要能长回原样，且状态按**现在**算。

| # | 操作 | 预期 |
|---|---|---|
| AR1 | 对话台让助手发起一次写操作停在确认卡上，**不点**，刷新整个页面 | 卡还在，参数齐全，**确认 / 取消按钮仍可点**；点确认能正常执行。建工单这类单子要长成**卡片**：标题左侧是等级标（`【较大】` 被提出来，标题里不再重复）、场站单列一行、描述按「现场情况 / 等级与理由 / 处置建议」分段；底部流程条停在**人工确认**（第 1 个点实心绿、第 2 个空心环、后两个灰圈） |
| AR2 | 确认执行之后再刷新页面 | 同一位置变成「已处理」，状态标为「已核验」，**流程条四步全绿**，按钮消失，参数仍在（折在「原始参数」里，点开还是原来那份 JSON）；结论只有一句，写在流程条下面，不另占一行 |
| AR3 | 把某张待确认单子的 `expires_at` 拨到过去（不必等清理任务跑）再刷新 | 卡还在但标题是「已处理」，写「已过期，未执行——需要重新发起」，**没有按钮** |
| AR4 | 在 DevTools 的 Network 面板里把 `/api/v1/approvals?ids=` **屏蔽**掉再刷新 | 卡显示「状态未知」+「审批状态读取失败，刷新重试。」，没有按钮——不是整张卡消失 |
| AR5 | 找一张**参数不是工单**的审批单（例如改智能体配置） | 不出工单卡，退回「键 → 值」逐条罗列，键名保持原样（`can_write` 还是 `can_write`，不译成中文）；流程条第 3 步叫「执行操作」 |

**顺带看一眼 Network**：一次刷新只应该有一个 `GET /api/v1/approvals?ids=...`，
不是每张卡一个请求。按条发在长会话里就是几十次往返。

**失败判据**：刷新后卡整个不见了（最原始的症状——消息还在，只是读起来像结论）；
或者卡还在但按钮能点、点下去 409（说明「能不能点」是浏览器按本地时间自己算的，
而不是用服务端的 `actionable`）；或者确认过的那张卡刷新后仍然显示「需要审批」
（状态取了当初的快照，没有按现在算）。

AR3 最容易做错：**状态是 `PENDING` 不等于还能点**。清理任务是定时跑的，
过期时间到了而任务还没到的那段窗口里，按钮必须已经消失。

## 5e. 长对话上下文（CX）—— 2026-11-13 起

设计见 [`CONTEXT.md`](CONTEXT.md)。这一组看的是「模型这一轮到底看到了什么」，
不是界面上有没有一个新按钮。

| # | 用例 | 期望 |
|---|---|---|
| CX1 | 同一会话连问两轮：第一轮「把 3 号工单状态改成已关闭」，第二轮只问「刚才那个是哪张工单？」 | 第二轮能答出「3 号工单」。答「你没说过」说明历史没注入；答成别的东西说明角色串了（把助手的话当成用户说的） |
| CX2 | 手工造一次压缩压力：`UPDATE conversations SET last_prompt_tokens = 20000 WHERE thread_id = '<内部线程>';`，再发一轮 | `conversation_summaries` 新增一行（`turns_covered ≥ 2`、`tokens_after < tokens_before`）；这一轮的 trace 里有 `context.compact` span，`gain` 明显为正；随后那轮的 `llm.call` 里 payload 同时带 `conversation_summary` 与 `recent_turns` |
| CX3 | 把 `CONTEXT_ENABLED=false` 重启，重复 CX1 | 第二轮答不出「刚才那个」；对比 trace 里 `llm.call` 的 payload，**不该有** `conversation_summary` / `recent_turns` 两个键（是键不存在，不是空值） |
| CX4 | 看 CX2 那一轮的用户消息 | 它**不在**摘要正文里。摘要只覆盖被淘汰的旧轮次，当前这条永远是原文 |
| CX5 | 打开 CX2 那一轮的 trace 详情 | 「本轮摘要」卡最下面多一行 chip：`上下文 17.8k / 32k · 摘要覆盖 N 轮 · 最近 M 轮原文`。点一下 chip 变绿，下方展开摘要全文（五个小节）与一行 `2.4k → 236 · 模型 · 字数`。**没有压缩过的 trace 上不该出现按钮**，只是一行静态 chip |
| CX6 | 回对话台打开同一会话 | 消息流里、被折叠的最后一轮下方有一条虚线，中间写「更早的 N 轮已折叠为摘要」。点开显示摘要全文。**N 应当等于界面上那条线以上的提问条数**，不是库里 `turns_covered` 的数 |
| CX7 | 运行配置 → 模型供应商 → 编辑 → 给某个文字模型填 `128000` 并保存 | 列表里该模型显示 `· 128k`；再发一条消息，trace 的 `context.measure` 里 `window=128000`、`window_source=provider`。把输入框清空再保存 → 回到 `32k`、`window_source=env`。只填 `32` 应被拦下（越界提示），不是存进去 |

**失败判据**：CX2 里摘要写进去了但 `turns_covered=0`（说明切边界切错了）；
或者连续两轮都新增摘要行（说明水位没前移，每轮都在压同一段）；
或者摘要里出现「（助手建议）用户决定用 A」这种反转（极性写反了，比漏记更糟）。

造 CX2 的压力值不要乱填：`0.6 × 32000 = 19200` 是压缩线，`0.85 × 32000 = 27200` 是硬截断线。
填 30000 会跳过压缩直接硬截断，看到的是一个**没有摘要**的短窗口——那不是 bug。

CX1 / CX2 的实测记录（2026-11-13，线上）：第一轮「记住编号 QQ-2048」、第二轮只问
「编号是多少」，模型答出 `QQ-2048`；同一会话第二轮 `last_prompt_tokens = 12366`，
说明用量确实收集到了（修之前一直是 0）。八轮短对话（每轮几十字）**不会**触发压缩——
按 token 预算算，8 轮加起来也才几百 token，这是预期行为，不是压缩没生效。

**注意**：`conversations.thread_id` 是内部线程标识（`租户:用户:客户端线程`），
手工造压力时按 `thread_id` 精确匹配会一条都 UPDATE 不到；按 `last_active_at`
倒序找最近那条，或按客户端传入的 thread 尾巴模糊匹配。

## 5f. 编排（WF）—— 2026-11-13 起

设计见 [`ORCHESTRATION.md`](ORCHESTRATION.md)。这一组看的是「人写死的顺序真的被执行了、
审批真的接得上」，不是界面上有没有一个新页面。

前置：至少两个智能体（下面的例子用 `cs` 与 `ops`），`cs` 的「最大转交深度」不小于 2，
且 `cs` 的工具清单包含 `create_maintenance_ticket`（否则下一跳的子集校验会拒）。

```bash
# 一张会停在审批上的图：分类（cs）→ 建单（ops）→ 汇总
curl -s -H "$H" -H 'Content-Type: application/json' $B/api/v1/workflows -d '{
  "name":"ticket","display_name":"建单流程","description":"分类 → 建单 → 汇总",
  "definition":{"entry":"classify","nodes":[
    {"id":"classify","agent":"cs","task":"判断类别：{{input.text}}",
     "next":[{"when":null,"to":"execute"}]},
    {"id":"execute","agent":"ops","task":"为「{{nodes.classify}}」建维护工单",
     "next":[{"when":null,"to":"answer"}]},
    {"id":"answer","kind":"compose","task":"流程结论：{{upstream}}","next":[]}
  ]}}'
```

| # | 用例 | 期望 |
|---|---|---|
| WF1 | 把上面那张图的 `next` 里唯一一条 `{"when":null,...}` 删掉再保存 | **保存时就 422**，`detail.code = WORKFLOW_NO_FALLBACK`，话里点名是哪个节点。等到对话里才炸就说明编译期校验没生效 |

**失败判据**：WF5 里 `nodes_json` 只剩 `execute / answer`（续跑覆盖了前半段流水）；
或者同一张工单被建了两次（续跑重跑了停住的节点）；或者 WF6 里汇总节点仍然跑了。

**为什么没有「立即运行」按钮**：触发只有对话这一处（下拉里选，或打 `/workflow`），
两条路走同一个 `Command`。编排的结论必须落在一个会话里，用户才看得见、审计才查得到、
写操作才落得到同一条审批链上。用手指着这条设计时，判断标准是「这条结论现在归谁」——
没有归属的运行入口一律算缺陷。

## 5g. 追问卡片（CL）—— 2026-11-15 起

反问不再是一段「1) 2) 3)」的正文，而是可点选的卡片。用例全部在控制台 `#/chat` 里做。

| # | 操作 | 预期 |
|---|---|---|
| CL1 | 发一句有歧义的请求，例如「关观测时的一句话」 | 正文只有一句总述（不再排 1) 2) 3)）；下面出现一张卡片，每项一个单选组，每组末尾固定有「其他（自己填写）」 |
| CL2 | 单组卡片里点一个候选 | **点一下就直接发出**，不需要再点提交；消息记录里出现这句候选的文案 |
| CL3 | 多组卡片里只选一部分 | 底部「提交选择」保持灰的，提示「还在等 N 项」 |
| CL4 | 某项选「其他」而不输入内容 | 该项不算答完，提交按钮仍是灰的；输入框会展开并拿到焦点 |
| CL5 | 在输入框里打完字按回车 | 直接提交，不用再点按钮 |
| CL6 | 提交后看那条用户消息 | 多组时每条都带问题前缀（`- 问题：答案`），不能只剩「维护工单」这种光杆词 |
| CL7 | 刷新页面 | 卡片原样回来。已经过去的那张变虚线只读：点过的显示「已选：xxx」，没点过的显示「这一轮已跳过」 |
| CL8 | 点过的卡片再点一次 | 点不动（选项 disabled），也不会重复发出消息 |

**失败判据**：卡片出现了但点不动（说明事件没绑上，`#chat-log` 是重渲染出来的节点）；
刷新后卡片消失（`metadata.clarify` 没随消息落库）；或者正文与卡片把同三个问题各列了一遍
（模型没按 system prompt 第 3 条走，需要看这一轮的 `llm.call` 输出）。

**注意**：构建助手面板（`SA`）暂不渲染卡片，它只显示正文。那块是配置类对话，
追问多为「要改哪个智能体」，未接同一套交互。

（多半是令牌记在了一个并不存在的 user 上——dev 模式自动建号是不落库的，
本地验令牌必须先有一个真实用户行）。

CP5 变回可写（方向写反了，MCP 成了绕过智能体权限的通道）。

**失败判据**：IM6 出现「篇幅太长、请用侧栏导入」（说明仍走读取截断那条老路）；

IM8 直接建了文档或技能（替用户猜用途）；IM9/IM10 先弹一张注定失败的审批卡；
IM11 要求重新上传（说明附件生命周期又被绑回了轮次）；IM13 侧栏还留着按钮
（入口没删干净，点它会报错）；
IM14 回复里只有片数、没有字数对比，或库里仍能查到 `<td`（清洗没生效，或只在一处生效）；
IM15 只说「超过单篇上限，请拆分后再入库」而不给数字与调高路径
（那是句做不到的指令——导入入口没有拆分功能）。

## 5j. 权限（PM）—— 2026-11-16 起

入口在控制台「配置 → 权限」（`#/permissions`，仅平台管理员）。设计口径见
`docs/PERMISSIONS.md`，接口 `/api/v1/admin/permissions`。

准备：至少一个自定义 HTTP Tool、一个 MCP Tool，以及一个只读与一个写入类的内置工具。

| # | 操作 | 预期 |
|---|---|---|
| PM1 | 打开页面 | 顶部两行平台开关（默认动作 / 外部通道接入）；左列默认只列自定义与 MCP 工具 |
| PM2 | 切到「全部来源」 | 列表里出现内置工具；切回后内置工具消失，选中项不被清空 |
| PM3 | 点一个只读工具，「策略动作」选「需确认」→ 保存 | 行尾标签变「需确认」，行下小字变「已配置策略 · 需确认 · 读取 · 需审批」 |

| PM5 | 选中一个写入类工具 | 「策略风险」里「读取」是灰的；硬改成 read 走接口应 400 并说明只允许上调 |
| PM6 | 只读工具把风险上调为「写入」→ 保存 | 行尾风险变「写入」，小字出现「需审批」；再对话时调用会先弹卡 |
| PM7 | 把某工具设为「拒绝」→ 保存 | 行尾变「拒绝」；对话里模型看不到它；硬拼工具名调用被拒（审计 `DENIED_TENANT`） |
| PM8 | 点「恢复未配置」 | 行下小字回到「跟随默认动作」；`psql` 查 `tenant_tool_policies` 该行**已删除**（不是留空行） |
| PM9 | 打开「未配置工具的默认动作」→ 保存 | 未单独配置的工具从对话工具目录消失；PM3 里显式配过的工具仍在 |
| PM10 | 关掉「外部通道接入」 | `curl -i` 带有效令牌打 `/mcp` 得 **503** `mcp_channel_disabled`；不带令牌仍是 401 |
| PM11 | 重新打开外部通道 | `/mcp` 恢复正常；已签发的令牌不用重签 |
| PM12 | 用非平台管理员打开 `#/permissions` | 显示权限不足的说明页，不发权限接口请求 |
| PM13 | 改完立刻看「工具」页 | 工具列表照旧（那是配置视图）；只有对话目录与状态标签变了 |

**失败判据**：PM4 只读工具直接执行（`approval_required` 没被 `confirm` 覆盖）；
PM6 上调后仍免审批（`risk_with_override` 没生效）；PM7 目录里还能看到（`allow_tool`
没读 `action`）；PM8 留下一行全空的记录（`set_tool_policy` 的删除分支没走到）；
PM10 返回 404 而不是 503（客户端会去改路径）、或上传入口仍可用（分流顺序写反）。

## 5k. 知识治理（KG）—— 2026-11-17 起

入口在控制台「知识库」（`#/knowledge`）的四个页签：概览 / 加工流水线 / 评估与反馈 /
生命周期。设计口径见 `docs/KNOWLEDGE.md` §11，接口全部以 `/api/v1/knowledge/` 开头。

准备：一个**新上传**的文档（有流水线快照）、一份在本轮改动之前就已入库的老文档、
同一标准的两个版本（例如某国标的 2011 版与 2020 版）、一个有 `knowledge:write` 的账号

### 加工流水线

## 6. 写操作审批闭环（W）—— 核心用例

这条链路最长，务必按顺序做，**把 `approval_id` 抄在纸上**。

| # | 动作 | 预期 |
|---|---|---|
| W1 | 发起：`给 station-001 创建维护工单，标题「手工测试」，描述「审批闭环」` | `status=awaiting_approval`，`preview.parameters` 三个字段齐全，`expires_at` 比 `created_at` 晚 300 秒 |
| W2 | `curl -s -H "$H" $B/api/v1/approvals/<id>` | 同样的预览内容，`status=PENDING` |
| W3 | 确认：`confirm -d '{}'` | `status=VERIFIED`、`verified=true`、`success=true`，`result.ticket_id` 以 `demo-ticket-` 开头 |
| W4 | 再确认一次 | **200** + 「该操作此前已完成，本次不会重复执行」，`status` 仍是 `VERIFIED` |
| W5 | 取消一条新的审批 | `status=REJECTED`、`verified=false` |
| W6 | 对已取消的再确认 | **409** + `status=REJECTED` + `success=false` + 「不能执行」 |
| W7 | 对已取消的再取消 | **409** + `success=false` + 「无需重复取消」 |
| W8 | 对已执行完成的再取消 | **409** + `success=false` + 「已完成」——不能让人误以为拦下了一次已经发生的写入 |
| W7 | 篡改参数确认（见下） | **422** + 「确认参数与预览内容不一致」 |
| W8 | W7 之后查审计 | 多一条 `APPROVAL_PARAMETER_MISMATCH`，`metadata` 里只有 `tool_name` 和 `submitted_keys`，**没有参数值** |
| W9 | 等 5 分钟后再确认一条新审批（慢用例，可最后做；或直接把 `expires_at` 拨到过去） | 单子变成 `EXPIRED`，**什么都没执行**。**两种时序都必须是 409**：清理任务先跑到 → 预检拦下；没跑到 → 执行期判过期。body 里带回 `status=EXPIRED`、`success=false` 和「已过期，请重新生成预览」那句。若没跑到清理任务时回了 200，说明路由只看预检状态 |
| W10 | 确认成功后看会话里最后一条助手消息 | 是**工具自己的结论**（「工单已在演示模式下受理，尚未核验。」「已导入知识库《…》：N 片 · 分级 internal。加工链路：…」），**不是**「操作请求已提交，但尚未获得可确认的回读结果」那句通用文案。核验与否由卡片上的 `EXECUTED / VERIFIED` 表达，不挤掉结论 |
| W11 | 在对话里导入一份规范并确认，然后看审批卡状态 | 状态是 **`VERIFIED`**（不是 `EXECUTED`）。再查这条审批的 `verification`：`{"verified": true, "source": "documents_table", "ref": "<document_id>", "chunks": N}`。导入技能或工具时仍停在 `EXECUTED`，`verification.reason` 是 `no_document`——它们不落 `documents` 表，没有可回读的落点 |
| W12 | 手工把刚入库那份文档 `status` 改成 `deleted`，再走一次确认 | 状态停在 `EXECUTED`，`verification.reason` 是 `deleted`/`pending`。核对的是「库里现在是 ready 且有切片」，不是「刚才写入返回了 200」 |
| W13 | 在对话里让助手下架一份文档并确认 | 状态 **`VERIFIED`**，`verification` 是 `{"verified": true, "ref": "<document_id>", "chunks": 0}`。手工只把 `documents.status` 改成 `deleted`、切片仍 `is_active` 时不通过，`error_code=VERIFY_CHUNKS_STILL_ACTIVE`——下架的承诺是「切片不再参与检索」，不是「状态字段改了」 |
| W14 | 在构建助手或对话台点确认，先看当场的样子，再刷新 | 两处**一模一样**：卡片写「已处理 + 已执行并核验通过」，结论（片数、加工链路、标签）是**紧跟着的一条独立气泡**。当场不该出现 `{"filename": …}` 这类 `执行结果：` JSON——它只在内存里，刷新就没了，看着像数据丢了 |
| W15 | 刷新后数一数同一次确认留下了几张审批卡 | **一张**，挂在「待确认操作…」那条消息下面；结论那条消息只有文字。两张以上说明还原历史时把结论消息上的同一个 `approval_id` 也当成了发起消息 |

```bash
# W1 发起
curl -s -H "$H" -H 'Content-Type: application/json' -X POST $B/api/v1/chat \
  -d '{"thread_id":"m-w1","message":"给 station-001 创建维护工单，标题「手工测试」，描述「审批闭环」"}'

# W3 确认
curl -s -H "$H" -H 'Content-Type: application/json' \
  -X POST $B/api/v1/approvals/<approval_id>/confirm -d '{}'

# W7 篡改
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" -H 'Content-Type: application/json' \
  -X POST $B/api/v1/approvals/<approval_id>/confirm \
  -d '{"parameters":{"station_id":"station-001","title":"被篡改","description":"x"}}'

# W8 查审计
psql "$(cat /root/.pap-admin-db-url)" -c \
  "select event_type, success, metadata_json from audit_logs where resource_id='<approval_id>' order by created_at desc;"
```

**W3 里 `source=mock` 是正常的**：没配 `STATION_PLATFORM_BASE_URL` 时工单走演示模式，
不要当成真实外部写入。`verified=true` 在 mock 下的含义是「回读到了本地记录」。

**W9 首次实机结果（2026-11-12，服务器 `61495f7`）**：把 `expires_at` 直接改到 5 分钟前、
**不等清理任务**，再确认 → `HTTP 409` + `status=EXPIRED` + `success=false` +
「该操作预览已过期，请重新生成预览。」。改之前这一步是 200：同一个事实因为清理任务
有没有先跑到而给出两个状态码。控制台的对应改动是「409 带 `status` 就写结论」，
否则卡片会留着按钮，而那张单子点几次都只会再拿一个 409。

**审计页的「详情」**：`GET /admin/tenants/{id}/audit` 每条现在带 `metadata`，
控制台在「说明」格里折一行 `详情`（原生 `<details>`）。实机看到
`approval_expired` 那条带着 `{"tool_name":"create_maintenance_ticket"}`——
以前这类内容只能 psql 才看得到。

**审计列表是限高滚动，不是整页拉长**：条数下拉能选到 500，列表必须在自己那块
58vh 里滚（表头吸顶），上面的「租户 / 条数」筛选器始终留在视野里。整页跟着长
就是错的——换租户得先滚回顶部。同一套容器观测页的调用链表格也在用。

**W10 运行必须跟着审批一起收口（2026-11-13 起）**

任一终态之后查对应运行，状态不能还是 `WAITING_FOR_APPROVAL`：

```bash
psql "$(cat /root/.pap-admin-db-url)" -c \
  "select r.status, r.error_category, r.finished_at
     from agent_runs r where r.approval_id='<approval_id>';"
```

期望：确认并核验通过 → `COMPLETED`；点取消 → `CANCELLED` +
`approval_rejected`；放到过期（等 30 秒清理任务）→ `CANCELLED` + `approval_expired`；
执行失败 → `FAILED` + 工具错误码。

**判据只看 `status` 与 `error_category`，别看 `finished_at`**：`finish_run` 无条件写它，
停在「等审批」的行本来就有结束时间，以前因此一直看着像已经收尾了。

**兜底对账**：把一张单子的 `expires_at` 改到 10 分钟前、`status` 直接改成
`EXPIRED`（绕过清理任务），等一个维护周期（30 秒）再看运行，应被
`reconcile_waiting_runs` 收成 `CANCELLED / approval_expired`。日志里有
`runs_closed_for_approval`。

## 12. 这些现象不是缺陷

| 现象 | 解释 |
|---|---|
| 工单 `source=mock` | 未配置外部场站平台，演示模式，README「已知边界」已说明 |
| 检索 `version=v5` 而别人看到 v1 | 每个租户独立版本号；同租户内多次入库会递增 |
| 入库后要等几秒才搜到 | 索引缓存 5 秒（`KNOWLEDGE_INDEX_REFRESH_SECONDS`） |
| 同一 thread 并发两问，历史出现分叉 | 已知边界：checkpoint 保证不丢，不保证不分叉，需要应用层幂等键 |
| 第一次问知识库慢约 1 秒 | jieba 首次初始化同步执行 |
| 取消后 confirm 返回 409 而不是 200 | 本轮已改：状态冲突必须能被客户端识别 |
| 重复取消曾返回 200 | 本轮已改：cancel 与 confirm 统一用 409，客户端不必写两套判断 |
