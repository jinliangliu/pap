# 技能：把「这类活怎么干」从提示词里拆出来

控制台「配置 → 技能」。技能 = **一段作业指令 + 一组触发词 + 一份可选工具白名单**。
命中后由服务端注入规划提示，并把工具目录收窄到白名单。

先说它不是什麼：不是工作流引擎，不是第二套工具注册表，不是技能市场。

## 1. 边界：和另外四样东西的分工

| 概念 | 回答的问题 | 存在哪 | 生效点 |
|---|---|---|---|
| 工具 `tools` | 「能调用什么」 | `ToolRegistry` + `custom_tools` | 网关执行时 |
| 知识库 `knowledge` | 「事实是什么」 | 向量索引 + 原文 | 检索节点 |
| 记忆 `memories` | 「这个人是谁、偏好什么」 | `memories` | `plan_request` 前注入 |
| **技能 `skills`** | **「这类活按什么步骤、用哪些工具、产出什么格式」** | `skills` | `plan_request` 前注入 + 收窄目录 |

拆出来的动机很具体：OCR 附件的规矩、表格/图表的排版要求、审批怎么写，
原本全写死在 `SYSTEM_PROMPT` 里——十几条硬规则，每轮都发、每轮都占 token，
加一条要改代码发版。技能把这类**场景性知识**变成数据：能加、能停用、能导入导出。

不做四件事：

- 不做 DAG / 多步编排——`ActionPlan` 一轮一个动作，硬塞流程图会变成两套调度；
- 不做技能内脚本执行——`python` 工具已走沙箱，技能不该成为绕过沙箱的新入口；
- 不做远程拉取 / 技能市场——只支持手写与导入导出，避免供应链问题；
- 不做多技能串联——同时命中只取一个，指令冲突的调试成本远大于收益。

## 2. 一次请求里的位置

```
用户消息
  │
  ├─ 显式：以 /技能名 开头 ────────────────┐
  ├─ 隐式：触发词命中（确定性，不调模型）──┤
  │                                       ▼
  │                                选中 1 个技能
  │                       ┌────────────────┴────────────────┐
  │                       ▼                                 ▼
  │             system 追加「## 当前技能」          工具目录 ∩ 白名单
  │                       └────────────────┬────────────────┘
  ▼                                        ▼
plan_request ─────────────► create_action_plan ─► 执行 / 审批 / 回答
```

三条约束，都是踩过或预见得到的坑：

1. **技能只能收窄权限，不能放大。** 白名单与 `gateway.list_available_for_context()`
   取交集，绝不并集。配了当前身份看不到的工具，静默丢弃、页面标「不可用」；
   报错等于告诉调用方「这个工具存在但你没权限」，那是个探针。
2. **匹配不花模型调用。** 关键词/显式在服务端匹配，命中即注入，一次规划照旧。
   让模型自己挑技能要「先选再规划」两次调用，延迟翻倍，且模型选的技能不可预测，
   出问题时无法从日志复原原因。
3. **指令进 system，不进 human payload。** payload 是「数据」，模型会当事实引用；
   作业规则属于「规则」，放 system 才有正确优先级。记忆放 payload，两者别混。

排序口径：优先级大的先；同优先级取触发词更长的（更具体）；再同按名字稳定排序，
避免同一句话两次请求命中不同技能。

## 3. 数据模型

表 `skills`，继承 `TenantScoped`（`tenant_id` 自动填充，RLS 隔离）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `name` | varchar(64) | `^[a-z][a-z0-9_-]{1,63}$`，租户内唯一，**保存后不可改** |
| `display_name` | varchar(64) | 展示名，如「设备控制共同执行流程」 |
| `description` | varchar(256) | 一句话说明什么时候用它 |
| `instruction` | text | 作业指令正文（Markdown），硬上限 8000 字符 |
| `trigger_keywords` | jsonb | 触发词，≤12 个，空数组合法（只能 `/名字` 调） |
| `allowed_tools` | jsonb \| null | `null`=不收窄，`[]`=一个工具都不给，数组=精确白名单 |
| `priority` | int | 同时命中取最大，默认 100 |
| `enabled` | bool | 停用即不参与匹配，数据保留 |
| `source` | varchar(32) | `manual` / `imported` |
| `created_by` | varchar(128) | 创建人 |
| `created_at` / `updated_at` | timestamptz | Python 侧赋值，见 §8 |

`null` 与 `[]` 必须分开：用空数组表示「不限制」的话，纯指令技能就没法表达了——
而「不放任何工具，只按格式作答」是真实需求。

> 时间字段在 `skill_service` 里显式赋值，不依赖 `server_default`。
> 服务端生成的列在 `flush()` 后是过期状态，异步会话再读会触发一次隐式 SELECT，
> 轻则多一次往返，重则 `MissingGreenlet`——接口 500，数据其实已经提交了。

### 命中记录 `skill_hits`

命中次数是「这条指令到底有没有人用、触发词配得准不准」的依据，因此单独存表：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `skill_id` | uuid | `ON DELETE CASCADE`：删技能时计数一并消失 |
| `skill_name` | varchar(64) | 冗余名字，导出与排障不必回连 |
| `matched_by` | varchar(16) | `explicit` / `keyword` |
| `keyword` | varchar(64) | 命中的触发词，显式调用为空 |
| `thread_id` / `run_id` / `trace_id` / `user_id` | varchar | 便于回溯到具体那一轮 |
| `created_at` | timestamptz | 只追加，不修改 |

三条口径：

1. **不挂 `obs_spans`。** 观测有保留期（默认 14 天），还能被观测开关
   整体关掉；命中趋势不该跟着诊断数据的开关一起消失。
2. **一轮只记一次。** `plan_request` 会因为「工具执行完再规划」被重复调用，
   按 `run_id` 去重，否则一次任务走三步就记三次，趋势图直接失真。
3. **召回测试不记账。** 那是调试工具；调指令的人一天点几十次，
   记进去就把真实使用量完全盖掉。

窗口口径是 7 天（`HITS_WINDOW_DAYS`）。7 天够看出趋势，又不至于让一次历史高峰
在页面上挂一个月。

## 4. 页面

侧边栏「配置 → 技能」，左列表右编辑器，底部一条可展开的召回测试：

```
┌────────────────┬──────────────────────────────────────────────┐
│ Skill 列表  3个 │ 编辑 Skill                       [未保存]     │
│ ┌────────────┐ │ Skill ID [device-control-execute]  ● 已启用   │
│ │已启用       │ │ Skill 全文                        270 / 8000 │
│ │设备控制…    │ │ ┌──────────────────────────────────────────┐ │
│ │关阀或切换…  │ │ │ # 设备控制共同执行流程                    │ │
│ └────────────┘ │ └──────────────────────────────────────────┘ │
│ ┌────────────┐ │ 名称 […………]        描述 […………]              │
│ │已启用       │ │ 触发词 [关阀, 切换档位]   优先级 [100]        │
│ │放散报表     │ │ 工具范围  ☐ 不限制                            │
│ └────────────┘ │  (平台时间)(创建检修工单)(识别附件)           │
│                │ [保存 Skill] [删除]                            │
└────────────────┴──────────────────────────────────────────────┘
▾ 召回测试   尚未运行 / 命中 设备控制共同执行流程
```

设计取舍：

- **状态是独立开关，编辑不改 `enabled`。** 改一句话不该让线上行为悄悄变；
  「保存内容」和「是否启用」是两件事。
- **`name` 保存后禁用输入框。** 改名等于换了一个技能，历史调用记录与用户习惯的
  `/旧名` 都会失效，所以接口层也拒绝（`extra="forbid"` → 422）。
- **白名单只能勾选，不能手输。** 手输打错会静默失效；勾选列表来自 `/api/v1/tools`，
  停用或越权的工具灰显并标「不可用」。
- **保存栏放在滚动区外。** 字段一多编辑器就要滚，按钮跟着滚走就找不到了。
- **召回测试与真实链路共用 `match_skill`。** 测试与线上不一致的「测试」比没有更糟；
  它同时显示「命中方式 / 命中词 / 指令字数 / 可用工具数」，一眼看出是没命中还是收窄过头。
- **未保存就切换技能会二次确认**，避免辛苦写的一段指令被点没了。

## 5. 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/skills` | 成员 | 列表，`can_write` 由权限推导 |
| GET | `/api/v1/skills/{id}` | 成员 | 详情，含 `missing_tools` |
| POST | `/api/v1/skills` | `skill:write` | 新建；重名 409，名字非法 400 |
| PATCH | `/api/v1/skills/{id}` | `skill:write` | 局部更新；`allowed_tools` 用字段是否出现区分「不改」与「改回 null」 |
| DELETE | `/api/v1/skills/{id}` | `skill:write` | 物理删除 |
| POST | `/api/v1/skills/recall` | 成员 | 召回测试，不写审计 |
| GET/POST | `/api/v1/skills/export` `/import` | `skill:write` | `version: 1`，同名覆盖 |
| GET | `/api/v1/skills/templates` | 成员 | 内置模板（在代码里，不是库里的行） |
| POST | `/api/v1/skills/templates/{key}` | `skill:write` | 复制成本租户的技能，默认停用；重名 409 |

写操作落 `ADMIN_ACTION` 审计，只记**字段名**与长度，不记正文——技能正文里常有业务细节。
读与召回测试不审计，否则列表每刷一次就是一条记录。

导入用「同名覆盖」而不是跳过：最常见的用法是「改完导出、在另一台机器导入」，
跳过会让两边悄悄不一致。

权限只有两个粒度：读写都认 `skill:write`，平台管理员天然具备；普通成员（`dev` 角色）
只能看。想给某个租户管理员开编辑权，给他加一条 `skill:write` 即可——和其它 scope 一样，
按角色授予，不按人。

## 6. 观测

不加新 span 类型，把属性挂在 `plan_request` 已有的 `llm.call` 上：

| attr | 值 |
|---|---|
| `skill.name` | 技能名，未命中不写 |
| `skill.matched_by` | `explicit` / `keyword` |
| `skill.tools_before` / `skill.tools_after` | 收窄前后工具数 |
| `skill.truncated` | 正文超限被截断 |
| `skill.chars` / `skill.limit` | 正文长度与上限（详情页显示「1,240 / 8,000 字符」） |
| `tools.count` / `tools.names` | 本轮目录的工具数与名字清单（收窄后） |

`tools.names` 记的是**这一轮实际给模型的目录**，不是回查注册表的结果：
详情页要回答「模型当时看到哪些工具」，而注册表只能回答「现在有什么」。
工具改名或租户策略调整之后，两者就不再是同一件事了。

另外 `obs_traces` 上单独加了一列 `skill_name`（与 `tool_name` 同理：列表页要按技能筛，
扫 JSON 太贵）。观测页因此多了一个「技能」下拉与一列标签，筛的是**这一轮用没用到该技能**，
不是「用到了哪个工具」。下拉选项来自窗口内的实际记录，所以已经删掉的技能也会出现——
那正是排查「删了技能怎么还有人用 `/名字`」时要看的东西。

`llm.call` 的 `input` 记录了完整 system 消息，所以「这段指令到底喂给模型的是什么」
可以直接在观测详情里看到——这是排查「模型为什么不按步骤走」的第一现场。

## 7. 落地状态

**已完成（P0）**

- `skills` 表 + 迁移（含 RLS 策略）
- `skill_service`：匹配 / 收窄 / 注入文本 / 截断 / CRUD
- `plan_request` 接入，`ActionPlan` 未改（不改模型输出结构）
- 7 个接口：列表、详情、新建、修改、删除、导入导出、召回测试
- 控制台技能页：列表 + 编辑器 + 召回测试

**已完成（P1）**

- `skill_hits` 表 + 迁移（含 RLS 策略与级联删除）
- 命中计数进列表（近 7 天次数）与详情（最近 5 次，含命中方式与线程 id）
- 观测：`obs_traces.skill_name` 列、列表「技能」列与筛选下拉
- 内置模板「巡检比对」「报表排版」：`GET /templates` + 复制接口，
  复制出来的是普通技能（`source=template`，默认停用）
- 测试 6 项：一次一轮只记一次、召回不记账、窗口外不计、模板复制与重名、观测筛选

模板为什么不做成「每个租户预置两行」：租户是动态建的，预置要么挂在建租户流程里，
要么每次升级补一遍（可能覆盖用户改过的同名技能）。做成可复制的起点最省事，
也自然满足「可复制不可删」。

**再想（P2）**

- 模型自选技能（`ActionPlan.skill_name` + 至多一次重规划）
- 技能引用知识库 scope
- 命中后的满意度统计（追问率 / 重试率）

三项都待定，等 `skill_hits` 攒够 1～2 周真实命中分布再决定先做哪一项。

## 8. 验收

1. 配一个只允许 `get_platform_time` 的技能，问「帮我发封邮件」——
   必须回「该操作不在当前可用的受控工具范围内」；
2. 技能正文写「你可以调用 send_email」但白名单没有——不能调用成功；
3. 同一条消息，技能停用前后 `available_tools` 数量不同，规划结果不同；
4. 召回测试说命中，真实对话里也命中（同一条消息，同一个 `match_skill`）；
5. 删除技能后，`/名字` 不再命中，历史 span 不受影响。

前两条是安全底线：技能是「怎么干」的描述，不是「能干什么」的授权。
