# Agent Studio 助手（构建助手）

> **先分清两个 Studio。**
> `docs/STUDIO.md` 讲的是 **LangGraph Studio**——在 `127.0.0.1:2024` 上跑 `langgraph dev`、
> 用图形界面看节点进出与 interrupt 恢复的**开发调试工具**，与本文件无关。
> 本文讲的是控制台里那个**用自然语言管理平台配置的助手**，内部代号 `studio`。
> 两者同名纯属巧合，以后不要互相引用。

> **状态：已上线 16 个 `studio_*` 工具 + 16 个只读 `fc_*` 业务工具。** 智能体
> （查 / 建 / 改 / 停用启用 / 删 / 恢复到历史版本）、
> 技能与工具的读写、**连接器的建与删（不碰凭据）**、编排流程的建改删与启停、
> 知识库写入与下架、**把用户上传的文件导入成知识库文档 / 技能 / 工具**、
> 运行与 Trace 的只读查询，全部可用。
> 业务侧能**读**站点与实时读数（回答「连接器接上以后能查到什么」只能靠真查一次），
> 但**不能下发控制**。
> **Python 工具是唯一的例外**：它由代码注册，没有运行时新增或修改入口，
> 助手会明确说明「要加得走代码变更与部署」，而不是含糊地报失败。

## 0. 定位

控制台里常驻的一个助手，用自然语言完成**平台内部的管理动作**：

- 查、建、改、停、删：Agent、Skill、自定义工具、编排流程；
- 回答「这个平台怎么用」（审批怎么配、边界怎么收窄、观测看哪里）；
- 用普通的 LLM 对话回答常规问题。

它不是一个新入口，也不是一个新服务。它是**现有对话能力的一个固定 Agent + 一组受限工具 +
一个悬浮面板**。这句话决定了后面所有的实现选择：能用现有管线的地方一律复用，不新建平行链路。

## 1. 能力边界

这张表就是产品定义，界面上的自我说明与拒绝对答都从它派生。

| 请求 | 处理 | 是否二次确认 |
|---|---|---|
| 有哪些 Agent / 某个 Agent 的边界是什么 | 直接回答 | 否 |
| 新建 Agent、改职责与边界 | 执行 | **是** |
| 停用 / 启用 Agent | 执行 | **是** |
| 删除 Agent | 执行 | **是**，且要输入名字 |
| 把边界恢复到历史某一版 | 执行，只覆盖工具 / 技能 / 可写三个字段 | **是** |
| Skill 的查 / 建 / 改 / 删 | 全部可用（`studio_skill_save` / `studio_skill_delete`） | 写要 |
| 自定义工具（HTTP）的查 / 建 / 改 / 删 | 全部可用；查只返回名字、风险等级与来源，**不含端点与凭据** | 写要 |
| MCP 工具接入 / 取消接入 | 可以接入（远端必须真的有这个工具）；需要令牌的外部端点请到控制台接入 | 写要 |
| Python 工具 | **只读**。代码注册，没有运行时新增路径 | — |
| 「查一下 3 号站现在压力多少」「连接器接上后能查到什么」 | 执行，走 16 个**只读**的 `fc_*` 业务工具（站点、读数、告警、控制配置）真查一次 | 否 |
| 站点控制（预演 / 下发 / 取消） | **拒绝**。写工具不在它的授权里：内置助手最容易被一段诱导性输入说服，写入口不能开 | — |
| 知识库的查 / 写入 / 下架 | 全部可用（正文写入，文件上传仍在知识库页） | 写要 |
| 编排流程的查 / 建 / 改 / 删 | 全部可用；改图只改传入的那几个节点，**不传 `definition` 就不动图** | 写要 |
| 「我们的巡检是先看压力、有报警让 ops 定级、严重的出处置建议、最后出日报」 | **识别为要建流程**：先读智能体清单，再拟步骤、说清每步由谁做与按什么分流，然后建图。只问「谁做哪一步」「按什么条件分流」；标识、显示名自己定 | 写要 |
| 「它昨天报错没」「刚才那次的耗时」 | 执行，读观测的 run 与 trace，默认看近 7 天 | 否 |
| 传 Token / 密码 / API Key 给它 | **拒绝**，并指向控制台安全输入或 `credential_ref` | — |
| 「审批有效期多少」「边界怎么收窄」 | 回答 | 否 |
| 改平台代码、改数据库、跑 shell、拿主机权限 | **拒绝** | — |
| 改用户 / 角色 / 成员 / 租户配额 | **拒绝**，指路「组织与成员」页 | — |
| 跨租户的任何操作 | **拒绝** | — |
| 改自己的边界、给自己加工具、把自己设为可写 | **拒绝** | — |

拒绝不能只说「不支持」。要给出下一步：能做什么、或者该去哪个页面做。
一个只说「我做不到」的助手，用户会试三次然后放弃。

## 2. 为什么做成 Agent，而不是一个独立服务

三种实现都能跑通，只有一种与平台定位一致：

| 做法 | 问题 |
|---|---|
| 独立服务，直接调 `agent_service` | 绕过工具网关、审计、观测、审批与限流。一个能改所有 Agent 的东西**自己不受治理**，这是最坏的结构 |
| 前端直接调管理接口，助手只负责生成参数 | 助手变成"自然语言转 JSON"，出错时无法回读核验，也没法二次确认 |
| **内置 Agent + 受限工具** | 复用 chat 管线、`ToolGateway`、审批、审计、观测、限流；助手自己也在观测里有一行 |

选第三种。代价是它要占一个 `agents` 行、要在工具目录里注册 16 个工具，
换来的是「助手做的每件事都能在审计里查到，且受同一个网关约束」。

### 2.1 它必须是内置 Agent

新增 `agents.is_builtin`（默认 `false`），`studio` 这一行置 `true`：

- 边界（`allowed_tools` / `allowed_skills` / `can_write`）**不可编辑**；
- 不可停用、不可删除；
- 职责说明（`description` / `instruction`）**可以**编辑——语气偏好是业务侧的合理需求，
  改它不改变能力。

`is_builtin` 只影响这三个写接口的允许集合，不引入新的权限模型。

**`studio_*` 只对它自己可见**（`ToolGateway.internal_denial`，目录与执行共用一份判断）。
不能靠 `allowed_tools` 拦：默认智能体是 `allowed_tools=None`（不额外收窄）、
`can_write=True`，平台管理员又跳过 scope 判定，于是 `studio_workflow_save` 一直在
默认智能体的目录里——唯一拦住它的是 `CHAT_SYSTEM_PROMPT` 那句「不要在这里替他排步骤」，
而提示词挡不住一句「直接调用 studio_workflow_save」。判据放在网关后，
业务对话里它连目录都进不去，硬拼工具名也会得到一句「只在构建助手里可用」。
`agent_name` 为空的路径（工具策略页、脚本、运维视图）不受影响：那里不知道是谁在说，
与 `allowed_tools=None` 同义，不额外收窄——否则管理员连它的审批策略都看不到。

## 3. 安全模型：上界是「人」，不是「助手自己」

这是本文最容易做错的一处，也是它与 A2A 的根本区别。

直觉做法是照搬 A2A 的子集规则：助手创建的 Agent 必须 ⊆ 助手自己的边界。
**这条会直接把功能做废**：助手的 `allowed_tools` 里只有 `studio_*` 和几个读工具，
按子集它只能造出「又一个只能管 Agent 的 Agent」，造不出能查工单、能执行控制的业务 Agent。

正确的上界来自另一条已有的事实：

```
任何一次对话的有效权限 = 请求人的权限 ∩ Agent 边界
```

助手的所有操作都**有真人在场**（每一条消息都来自一个已认证的 `Identity`），
所以新 Agent 的实际权限是 `人的权限 ∩ 新边界 ⊆ 人的权限`。**它不可能造出一个
比申请人权限更大的东西**——不是靠校验，是靠这层交集。

|  | A2A 委派 | Studio 助手 |
|---|---|---|
| 有无真人在场 | 无，模型自己选目标 | 有，每条消息都带 `Identity` |
| 权限上界 | `A ∩ B`，所以必须 `B ⊆ A` | `人 ∩ 新边界`，天然 `⊆ 人` |
| 强制的校验 | Agent ⊆ Agent | 新配置 ⊆ 人的可见集 |
| 关系 | Agent 之间传权限 | 人通过 Agent 代理**自己已有**的权限 |

### 3.1 但有三条自提权红线必须单独挡

上面那条推论只覆盖「不能超过人」。还有一类越权是**绕过人的审批**：

1. **不能改自己。** 目标 `ref` 指向 `studio` 自身时，改边界一律拒绝。
   否则它可以在第一轮把 `safe_write_tool` 加进自己的 `allowed_tools`，
   第二轮就用上了——两轮之间没有任何人批准过这个能力。
2. **不能把 `studio_*` 授予任何其它 Agent。** 否则人可以借它造一个「能改 Agent 的 Agent」，
   那个新 Agent 的每次修改又走一遍二次确认，但人已经绕过了「只有内置助手能改配置」这条设计。
3. **不能碰 RBAC 与租户配额。** 用户、角色、成员、租户配额都不在工具集里——
   这是「工具不存在」级别的隔离，不是提示词层的劝阻。

注意第 1、2 条的形态：它们不是「超过人的权限」，而是**「在人的视野之外获得了能力」**。
这类越权最难查，因为审计里每一行都合法。

### 3.2 运行时安全 ≠ 配置可用

`人 ∩ 新边界` 保证不越权，但不保证配出来能用。若助手把 `allowed_tools` 写成
`["fc_executestationcontrol"]` 而申请人自己没这个 scope，运行时会被 `agent_denial`
挡掉——**安全，但用户会以为配好了**。

所以创建/修改时要做一次显式校验：

```
new.allowed_tools ⊆ 请求人当前可见的工具集
```

不通过就拒绝并说明「你自己没有 X 的权限，我不能把它写进这个 Agent」。
这不是安全需要，是**可用性需要**：让配置错误在保存时暴露，而不是在第一次对话时才发现。

**`can_write` 不单独校验**（设计初稿里写了要校验，落地时判定不必要）：
「这个人是否足够有资格创建一个可写的 Agent」没有可精确定义的口径——
写权限是按工具 scope 分散的，不是一个人身上的单一开关。而且它已经被两道闸门约束：
创建可写 Agent 需要 `agent:write`，真正执行写操作时还要走审批 + `人 ∩ 边界`。
再加一层拍脑袋的判定，只会拦住合理请求、放走真正的风险。

## 4. 工具集

按 (对象 × 风险) 拆，不合并成一个大工具，也不拆到十几个。

| 工具 | 风险 | 二次确认 | 说明 |
|---|---|---|---|
| `studio_describe` | `read` | 否 | 聚合读：`resource` 取 `agent` / `skill` / `tool` / `workflow` / `run` / `trace` / `knowledge` / `history` / `platform` |
| `studio_agent_save` | `write` | 是 | 建与改合并：都是「保存一份边界」 |
| `studio_agent_set_status` | `write` | 是 | 启停，与保存分开（它不该改 `revision`） |
| `studio_agent_delete` | `destructive` | 是 + 输名字 | |
| `studio_agent_restore` | `write` | 是 | 回滚到历史 `revision`，与保存同一类动作 |
| `studio_skill_save` | `write` | 是 | |
| `studio_skill_delete` | `destructive` | 是 | |
| `studio_tool_save` | `write` | 是 | 只允许 `source=custom`，内置工具拒绝 |
| `studio_tool_delete` | `destructive` | 是 | 同上 |
| `studio_knowledge_add` | `write` | 是 | 写入**对话里的一段正文**并切片入库；文件走 `studio_import` |
| `studio_knowledge_delete` | `destructive` | 是 | 下架整份文档 |
| `studio_import` | `write` | 是 | 把会话里已上传的文件按用途建成知识库 / 技能 / 工具；判类靠内容与原始文件名 |
| `studio_connector_save` | `write` | 是 | 建/改连接器定义，**不接受凭据** |
| `studio_connector_delete` | `destructive` | 是 | 下面还挂着工具时会被后端拒绝 |
| `studio_workflow_draft` | `read` | 否 | 起草：交一张图，只回答「能不能存、差在哪」，不落库、不涨 `revision`；角色填标识或显示名都认 |
| `studio_workflow_save` | `write` | 是 | 建/改编排流程；`definition` 原样交给 `compile_definition` |
| `studio_workflow_delete` | `destructive` | 是 + 输名字 | 只删配置；未完结的 run 按冻结的图继续 |

除上表外，助手还固定持有 **`ocr_document`（`read`，免确认）**：附件在提示词里
只有一个句柄，真正读出图中的文字要靠它。少了这一个，面板上的「+」就变成
「上传一张谁也看不见的图」——模型会如实回答看不到内容，看起来像功能坏了，
实际是边界把它挡在外面。清单在 `agent_service.STUDIO_EXTRA_TOOLS`，
单测钉住「额外放行的只能是只读工具」。

连接器这两个工具的参数里**没有** `secret` / `token` 字段，描述里也写明：不得向用户
索取凭据、不得让用户在对话里粘贴令牌。凭据只能经控制台的凭据面板写入——
那条路径不经过模型、不进对话、不进日志。

### 4.1 为什么不合并成「一个读工具 + 一个写工具」

`risk_level` 与 `requires_approval` 是**工具级**字段，不是参数级。合成一个 `studio_write`
之后，所有写操作都按最高风险走审批——改一句 `description` 也会弹 destructive 确认。
人一旦习惯「反正都要点确认」，二次确认就退化成装饰。

### 4.2 为什么不拆得更细

目录每多一个工具，模型选错的机会就多一次；而 `agent_save` 与 `skill_save` 的参数结构
本来就不同，合并只会让 schema 变复杂。15 个是「风险分得开、名字分得清」的最小集合：
读一个、每类对象两到三个动作，没有「万能写工具」。
`connector_save` 与 `connector_delete` 是这个规则的延伸——连接器也是平台配置对象，
凭据则**不在这套工具的能力范围里**（见 4.1 上方的说明）。

### 4.2.1 编排流程为什么是「一个写工具 + 一个删工具」而不是三个

`definition` 是一份完整的图，改图就是重存一份图，所以建与改必然合并（与
`agent_save` 同一条理由）；启停也不需要单独的工具——`enabled` 是
`studio_workflow_save` 的一个字段，传它而**不传** `definition` 就是「只改启停，
图一个字不动」。这条路径被单测钉住：漏传 `definition` 若被当成「把图清空」，
一次改名就会删掉整张流程，而调用方以为自己只是换了个显示名。

校验只有一份：`definition` 原样转手 `workflow_service.save_workflow` →
`compile_definition`。助手这边再写一套「有没有兜底边」的检查，迟早长成
「控制台存得进去、助手存不进去」，而两边看到的都是「保存失败」。

**一处例外，也仍然只有一份**：「图里写的智能体存不存在、是不是启用中」读不到库，
只能放在 `save_workflow`（`_ensure_agents_available`）里，控制台与助手共用同一个
函数。这条不是可有可无的完整性检查——自然语言建流程时模型不知道租户里有哪些
智能体，凭语义编一个 `inspector` 是最自然的动作；不挡的话图存得进去，一直到有人
`/workflow` 触发才失败，而那时配图的人早就不在屏幕前了。拒绝理由要带**可用标识**
（`当前租户的智能体：cs（客服）、ops（运维）`），只说「不存在」下一轮它还会编。

**「填什么名字」不该问用户。** 图里存标识（`assistant`），而人说的是显示名
（「通用助手」）。这一层自己换（`workflow_service.resolve_plan_agents`，保存与
起草共用）：图里两种写法都认，落库前统一成标识。换过谁要在草稿里说出来
（「通用助手 → assistant」），否则卡上那个人在用户眼里就是凭空出现的。
重名的显示名**不猜**——两个「运维」是两张边界，按名字挑一个等于替用户决定了权限。

这也是为什么 `studio_describe resource=agent` 的清单末尾固定有一行
「能放进编排图的（启用中）：…」：枚举在库里，读一次就有，不该让用户把它再打一遍。

**起草不算第三个写工具。** `studio_workflow_draft` 是 `read`：它把同一份
`compile_definition` 与同一份 `_ensure_agents_available` 的口径跑一遍，然后**不写库**。
放在写工具之前是为了别让人对着一张「注定被拒」的确认卡点确认——那张卡一旦成为
常态，确认就退化成装饰。判定口径与保存共用（`plan_agents` / `AGENT_STATUS_TEXT`
都是公开的），不另写一套「大概一样」的遍历。

### 4.2.2 为什么这个工具额外挂了 `preflight` / `summarize` / `verifier`

三个钩子各管一段时间点，缺任何一段都会退化成「用户批了一张他没看懂的卡」：

| 钩子 | 时点 | 缺了会怎样 |
|---|---|---|
| `preflight` | 出卡之前 | 编译不过的图也弹出确认卡，用户点完才知道白点——训练出闭眼确认 |
| `summarize` | 卡上正文 | 卡片只有一行「新建或修改编排流程」+ 一份折叠 JSON；`definition` 折起来正是因为没人读得动它 |
| `verifier` | 执行之后 | 审批停在 `EXECUTED`，「写成功了」与「根本没核过」在审计里长得一样 |

摘要必须写**角色**，不能只写节点 id。线上真实出现过一次：用户说「有报警就让 ops
判断严重程度」，图里全流程都是 `field-ops`（租户里没有 `ops`），而结果只回了
`步骤：check → advise → report`——换角色这件事在对话里完全看不出来。现在的做法是
三处一起给：卡片正文与结果里都写 `check（field-ops）`、结果 JSON 带 `roles`、
描述里要求「点名的角色不存在时，调用前先说明换成了谁」。

#### 摘要还带一张图（`ToolBrief.graph` → `preview.graph`）

文字那行 `check → shutdown → ticket → report` 丢掉的不是箭头，而是**分叉**：
「严重走 shutdown，其余直接到 report」在文字里只能靠一个分号读出来，而人读卡片
是扫一遍就点确认的。所以 `summarize` 可以返回 `ToolBrief(text, graph)`，图随
`preview` 一起落进审批单——**放 preview 而不是随响应一次性给出**，是因为卡片在
刷新后是从审批单重新取的；只放响应，滚一下图上就只剩那行字。

三条约束：

- **图由工具给结构，模型不生成 SVG**。让模型画图，既是注入面，也让「图对不对」
  变成一个没法断言的问题。服务端只给 `{entry, nodes, edges[{from,to,when,label}]}`，
  坐标不算进数据——存了坐标就等于把「几列、多宽」写进库，换个屏幕就得重算。
- **兜底边必须画出来**（虚线 + 「其余」）。只画主链会让人以为这张图没有兜底，
  而「缺兜底」正是保存时会被拒的那种图。
- **编译不过就不给图**。一张看着能跑、实际存不进去的图，比没有图危险。

同一份 `graph` 也随结果消息回一次（`response_metadata.graph` → 落
`messages.metadata_json.graph`），但**结论气泡不再画它**：确认之后那张审批卡就在
上面，卡里是同一份图，而且刷新后还在（`studioApprovalCard` 的预览白名单带 `graph`）。
两条消息各画一遍，滚动时看到的是「同一张图又出现了一次」。顺序信息不会因此丢失——
工具写的结论正文自己带着 `步骤：a → b`。
渲染在 `render.js` 的 `PAPRender.flowDiagram`，与拓扑图**不共用样式**：那张画的是
「谁调用过谁」，这张画的是「存的这张图什么形状」。

**卡上只出现一次正文。** 审批轮那条助手消息的正文是平台生成的「待确认操作／步骤／
角色／尚未执行」，与卡上的抬头、图、参数、流程条逐句对应。有卡就不再铺正文
（`PAPRender.approvalCoversMessage`），摘要改由卡自己渲染（`approvalSummary`）——
否则同一段话在屏幕上出现两次，读的人得先分辨哪一份是新的。卡没取到（审批单被清理、
状态未知、`preview` 为空）时反过来：正文是唯一线索，必须留着。

回读核验认三件事：行在、节点 id 集合与提交的一致、启停是提交的那个值。
只核「行在」等于没核——同名流程被别处改过时，批准的是 A、库里是 B。

### 4.3 `studio_describe` 的形态

```json
{"resource": "agent", "ref": "ops", "query": "它的边界和最近用量"}
```

`resource` 是一个封闭枚举，不是自由文本。`query` 只是给同一份结构化数据的"想看哪部分"提示，
**不参与任何检索**——助手拿到的是完整对象，`query` 决定它怎么组织回答。
如果让 `query` 参与后端检索，就会出现「它说没有这个 Agent，其实只是关键词没匹配」。

## 5. 二次确认

### 5.1 复用现成的 interrupt，不新造确认机制

现有链路已经完整（`app/agents/nodes.py` 的 `create_and_wait_approval`）：

```
POST /chat（写操作为 requires_approval）
  → 图在 interrupt 处挂起
  → 返回 status="awaiting_approval" + approval{id, tool, risk, summary, params}
POST /approvals/{id}/confirm  → 执行 → 返回结果
POST /approvals/{id}/cancel   → 不执行
```

助手不改这套。**只改呈现位置**。

### 5.2 确认卡片内联在面板里，不跳审批页

审批页是为「异步的、可能人不在电脑前」的写操作设计的：一个工单改状态可能要走两级、
要等主管。构建助手不是——它是「我说一句、它改一下」的即时闭环。

跳到审批页的代价：每次改动都要切页面、找到那一行、回来继续说话。人的行为会变成
「看到弹窗就点确认」，那比没有确认更糟——它给了治理的错觉。

所以：`awaiting_approval` 返回后，面板在消息流里渲染一张卡片：

```
┌─────────────────────────────────────┐
│ 待确认　修改智能体 ops               │
│                                     │
│ can_write   false → true            │
│ 允许工具     +get_station_snapshot   │
│                                     │
│ 影响：之后所有用 ops 的对话都能写     │
│                    [取消]  [确认执行] │
└─────────────────────────────────────┘
```

卡片必须显示**变更前后**，不是"将要更新 Agent ops"。前者能让人发现问题，后者不能。

### 5.3 删除要多一道：输入名字

`studio_agent_delete` 的参数带 `confirm_name`，工具内部校验它等于目标 `name`，
不相等直接失败。**这个校验在工具里做，不靠模型自觉**——模型完全可能热情地
把名字替你填好，那样这道闸门等于不存在。

### 5.4 注定失败的操作不弹卡

确认卡出现在所有校验之前。如果把「内置不可改」「未停用不能删」只写在
执行代码里，用户会看到一张「删除某某」的卡，点确认后才收到一句报错。
**这张卡本身就是错的**：它暗示这件事有可能成功。人对着一张必然失败的卡
点几次确认，之后就会开始闭眼点——比没有确认更糟。

所以三个写工具都带 `preflight`：在生成审批单之前跑一次轻量检查，
返回理由就不进审批，把理由原样讲给用户。

| 检查 | 时机 | 话术 |
|---|---|---|
| 目标是内置智能体 | 提案前 + 执行时 | 内置智能体的边界固定在平台上，不能修改、停用或删除。|
| 删除但目标未停用 | 提案前 + 执行时 | 要删除「X」请先把它停用（当前状态：active）。|

两层不是重复：**提案前决定「要不要让人看到卡」，执行时才是权威判定**。
中间可能过了几分钟，别人刚把它改成内置、或者刚启用，所以执行时必须重新判。

### 5.5 确认之后还要回读：`verified` 不是 handler 说了算

`verification_hint` 读起来像已经核过了，它只是给人看的说明。真正让审批卡从
`EXECUTED` 走到 `VERIFIED` 的是 `verifier`——**另起一个会话**，按
`external_operation_id` 重新读一遍。handler 里那次读回与写入在同一个事务里，
提交失败也照样读得到；而 `agents` / `workflows` 挂 RLS，租户上下文没绑上时是
空集、连报错都没有。

四个智能体写工具各核一件事，都不是「行在」：

| 工具 | 核什么 | 漏了会怎样 |
|---|---|---|
| `studio_agent_save` | 库里的**边界**与提交的一致（工具/技能/连接器/可写/状态，只比提交了的那些） | 并发下别处改回去，批的是 A、生效的是 B |
| `studio_agent_set_status` | 库里的状态就是提交的那个 | 「返回成功但没变」看着和成功一样 |
| `studio_agent_delete` | 按 **id** 查不到 **且** 找得到 `agent_deleted` 审计 | 见下 |
| `studio_agent_restore` | 当前边界等于第 N 版快照 | 版本号每次都会变，拿它当证据等于没核 |

**删除类必须多一条正向证据。** 删除的回读与保存是反的：保存核「在」，删除核
「不在」。而「查不到」什么都不说明——名字打错、租户上下文没绑上、库被人换过，
查出来都是空集。把空集当成功，核验就成了一根永远绿的线。所以判据是：按 id
查不到（id 是执行时从库里读出来的，排除「本来就没这个名」）**并且**按 id
找得到那条删除审计（删成功之后才写、自己开会话提交）。只剩空集时如实说
「核不出结论」，状态留在 `EXECUTED` 等一个人看一眼。

这条规则由 `tests/unit/test_studio_tool_verifiers.py` 守着：它用 `==` 比对
「审批类工具里没有 `verifier` 的那些」。新加写工具忘了声明立刻红；修掉一个也
必须从清单里删掉。**清单现在已清零**。

技能 / 自定义工具 / 连接器这六个同理，每个核一件不同的事：

| 工具 | 核什么 | 漏了会怎样 |
|---|---|---|
| `studio_skill_save` | `instruction` / `allowed_tools` 等提交了的字段与库里一致 | 技能的价值全在正文与工具白名单上，改掉了却报「已保存」 |
| `studio_skill_delete` | 按 id 查不到 **且** 有 `skill_deleted` 审计 | 同删除类通例 |
| `studio_tool_save` | 库里定义一致 **且** 名字在网关目录里 | 库里写了、目录里没有 → 重启前一直调不到；目录里有、库里被改 → 重启后消失 |
| `studio_tool_delete` | 按 id 在 **对应那张表**里查不到（http / mcp 两张表） | 只查一边会把「另一边还在」当成删干净 |
| `studio_connector_save` | 端点、认证方式与提交的一致 | 静默改指向：界面显示新地址，模型还在调旧地址 |
| `studio_connector_delete` | 按 id 查不到，且有 `connector_deleted` 审计 | 同删除类通例 |

两处容易写成假核验的地方：

- **归一化要在核验侧复用服务层那一份**。`base_url` 对 HTTP 连接器会去掉尾斜杠，
  `auth_header_name` 只在 header 认证下保存；核验里另写一份比较逻辑，就会出现
  「保存成功但核验报不一致」，而且改一处忘一处。列表字段同理，照
  `agent_service._clean_list` 的口径去空去重，否则 `["a","a"]` 会被判成不一致。
- **「行在」不等于「这次保存生效」**。MCP 接入项的端点不比较：不传 `server_url`
  时它落到 `.env` 的默认端点，比出来的是「配置有没有变」，不是「这次保存有没有成」。

### 5.6 确认卡正文：卡片要自己说清「在批什么」

审批卡的正文只能由 `interrupt(message=…)` 给——**同轮助手那段文字会被整段顶掉**。
所以写工具只声明 `preflight` 与 `verifier` 还不够：卡上会出现工具名和一份折叠的
参数，而参数折起来正是因为没人读得动它。

`ToolDefinition.summarize` 补的就是这一段：`(context, arguments) → str | ToolBrief`，
返回的 `text` 进卡片正文（排在「该操作尚未执行」之前），`graph` 进 `preview`。
流程保存还多给一张结构图；其余工具只给文字。

三条纪律：

1. **只陈述参数，不查库、不校验**。查库的活归 `preflight`（出卡前）与 `verifier`
   （执行后）。摘要抛异常会被吞掉并退回「只显示参数」——它是辅助，不是判定。
2. **没传的字段写「沿用现有」**，不按默认值猜。update 常常只传一个字段，摘要若
   照整份新配置写，人会以为别的都变了。所以 update 的第二行以「本次改动：」开头，
   只列这次真会变的字段；一个字段都没传就写「无」。**默认值不是「沿用」**：连接器
   的 `kind` 默认 `mcp`、`auth_type` 默认 `none`，update 没传时按默认值写，就会
   凭空报出一个「类型改为 mcp」「不需要凭据」。
3. **含义不同的写法要分开说**。最典型的是 `allowed_tools` 的三态：不传 = 不额外
   限制、`null` = 取消已有收窄、`[]` = 一个都不给。三者行为完全不同，摘要里写成
   同一句「工具：无」，人就会批错。

摘要里不能出现凭据值。HTTP 工具的自定义请求头只报个数（「3 个，值不回显」），
连接器则明说「凭据不在这次操作里，保存后到控制台填写」。

这条规则同样由 `test_studio_tool_verifiers.py` 守着（`STILL_WITHOUT_SUMMARY`，
现在为空）：审批类工具漏声明 `summarize` 会立刻红。

## 6. 越界请求

三类，话术不同：

| 类型 | 例 | 回应 |
|---|---|---|
| 平台外 | 改代码、连库、跑 shell、拿主机 | 「这超出我在平台内的职责。我能做的是……；代码与数据库变更走部署流程」 |
| 平台内但不在工具集 | 改成员角色、调租户配额 | 「这属于组织管理，请在『组织与成员』页操作」 |
| 会提权 | 改自己、给别的 Agent 授 `studio_*` | 「这会让配置绕过审批，我不能做」 |

**边界靠"工具不存在"实现，不靠提示词。** 系统的提示词里也会写一遍越界说明，
但那是为了减少无效尝试、让拒绝更自然，不是安全机制——模型完全可能被一段
诱导性输入说服，而它说服不了「注册表里没有这个工具」。

每次越界都记一条 `studio_out_of_scope`（含原始意图摘要、不记完整提示词）。
「有人反复试图让助手改数据库」本身是值得看的信号。

## 7. 前端面板

参考形态（截图）：右下角悬浮按钮 → 右侧滑出抽屉。

```
┌──────────────────────────────┐
│ 构建助手            ↻  ⤢  ×  │  ← 标题 / 滚到最新 / 放大 / 关闭
├──────────────────────────────┤
│ 助手：现在有 3 个 Agent……     │
│                              │
│ 你：把 ops 改成可写            │
│ ┌──────────────────────────┐ │
│ │ 待确认 …  [取消] [确认执行] │ │
│ └──────────────────────────┘ │
├──────────────────────────────┤
│ ┌──────────────────────────┐ │  ← 整块输入卡片（圆角 + 描边）
│ │ 今天帮你做些什么？…       │ │     输入框随内容长高，64–180px
│ │ +                    🎤 (↑)│ │  ← + 附件 / 麦克风 / 圆形发送
│ └──────────────────────────┘ │
└──────────────────────────────┘
```

要点：

- **输入区是一整块卡片**：输入框与底部按钮共用一个描边。按钮放在框外时，
  加号在框左、发送在框右，看起来像两个互不相干的入口；同一块卡片才读得出
  「这里写的东西会从这里发出去」。聚焦时整块卡片亮起（`:focus-within`），
  而不是只给框内某一行描边。
- **发送按钮**：圆形实心绿，图标是向上箭头；输入为空时置灰而不是隐藏——
  位置固定，人才不会在「按钮去哪了」上分心。有附件但没文字时按钮可点，
  点下去提示补一句话（附件留在托盘），这比置灰让人以为「文件传不上去」要好。
- **语音输入走浏览器自带的识别接口**（`SpeechRecognition` / `webkitSpeechRecognition`），
  录音与转写都在客户端完成：平台不存音频、不需要额外密钥、也不经过对话链路。
  代价是可用性由浏览器与网络决定，所以三件事必须写清：不支持时按钮弱化并给出
  原因；非 HTTPS 时提示「麦克风只能在 HTTPS 或本机使用」；识别服务连不上时
  如实说明「识别在浏览器厂商那边」。识别结果**追加**到输入框已有文字后面
  （`base + final + interim`），不覆盖手动打的字；点发送或收起面板都会松开麦克风。
  **注意部署形态**：浏览器只在 HTTPS 或 `localhost` 下授予麦克风权限，所以
  `http://<IP>` 直连时语音不可用（会明确提示原因）。这不是前端能绕过的，
  要真正启用得先给站点配 HTTPS——录音类能力（含后端 ASR 方案）同样受这条限制。
- **输入框随内容长高**，下限 64px（空着时也有两三行的体量，一行窄条会让人以为
  这里只能填一句话），到 180px 后内部滚动。固定两行时写三句话就看不到第一句，
  而这里常要贴一段配置或报错原文。
- **聚焦只有一圈框**：焦点画在 `.studio-composer` 上，输入框自身必须把
  `border / outline / box-shadow` 全清掉。全局的 `textarea:focus` 自带一圈
  3px 浅绿 `box-shadow`，不清掉就会在卡片里再套一个小框——截图里那个「双层框」
  就是这么来的。
- **当前对象选择器**（截图里那个下拉）不是装饰。选中后每条消息带上
  `focus={type, ref}`，助手回答里的"它"才有确定所指。没有它，多 Agent 场景下
  人会说「把它停掉」，而助手只能反问——三次之后用户就不用这个面板了。
  **位置在输入框底部工具行、加号右边**：它和附件是同一类东西（这一条消息的上下文），
  单独占头部一行会被读成「面板的全局设置」。高度与 28px 图标按钮对齐，
  名字过长时裁切、不推进麦克风与发送。
- **宽度 400px，不遮住主内容**，需要看长清单时用头部的放大按钮切到 760px；
  窄屏（`≤720px`）改为整屏抽屉。
- 面板开合状态、尺寸与选中对象存 `localStorage`，与现有 `pap.chat.nav.hidden` 同一套写法。
- **打开面板时把历史读回来**：`GET /api/v1/conversations?channel=studio` 找到本浏览器
  那条线程，再取详情。历史是异步补的，不挡输入框；读回来之前用户已经发了一条，
  就放弃这次回填——宁可少一段旧记录，也不能吃掉他刚打的字。读失败也只是从空白开始，
  面板照常可用。
- **它只从这个面板进入**：对话台的智能体下拉不列内置构建助手。同一个助手有两个入口，
  人会在对话台发一句、再回面板找同一段上下文；而两条会话仍然都记在 `channel=studio` 上，
  对话台按 `channel=api` 列表，两边都找不到对方刚说过什么。
- **加号只有一个去处：把材料随这条消息发给助手**，收图片、PDF 与文本类文件。

  | 支持格式 | 文件去哪 | 模型能看到内容吗 |
  |---|---|---|
  | 图片 / PDF | 落盘成对话附件，随这条消息提交 | 能：`ocr_document` 走 OCR |
  | Markdown / 纯文本 / 日志 / JSON·YAML·INI 等配置 | 同上 | 能：`ocr_document` 直接读原文，不经过识别引擎 |

  文本按**用途**收，不按「像不像文档」挑：建知识库要 Markdown，排查问题要运行日志
  （`.log` / `.jsonl`），新增配置要 `.yaml` / `.json` / `.ini`。三种用途在这条链路上
  是同一件事——读原文给模型看——所以后缀是一张清单，不是三道闸
  （完整清单见 `docs/CONVERSATIONS.md` §3b）。

  文件进平台只有这一条路：**加号上传 + 一句话说明用途**，助手按内容判类，
  用 `studio_import` 建成知识库文档 / 技能 / 工具。判类依据是文件内容（现场规程和
  技能都是 `.md`，工具导出和 OpenAPI 都是 `.json`），而内容在助手手里——先让人去
  别处选一个目标，等于把机器能干的事推给人。原先侧栏那个「从文件新建」弹层因此
  下线，实现与取舍见 `docs/STUDIO_IMPORT.md`。普通对话窗仍然只有附件，没有导入工具。

- **导入不读正文，读磁盘原文**。`ocr_document` 单次约 4 万字符，长文会被截断；
  拿截断后的正文去写库，得到的是一份看着完整、实际少了一半的资料，而失败时没有
  任何报错。`studio_import` 凭 `file_id` 取磁盘原文、按整份切片，与页面上传同一条
  路径；`studio_knowledge_add` 因此只剩「写用户口述或贴进对话的一段正文」这一个用途。

- **三种用途在提示词里各有对应**：入库 / 建技能 / 接工具 → `studio_import`（`target`
  按用户那句话定，判不准就先问）；排查 → 先读日志再用 `studio_describe` 查
  run / trace 对照；新增配置 → 读原文后按内容调 `studio_*_save`。用途写在提示词里，
  是因为「同一个 .md 可能是规程、也可能是技能」——按后缀分流只会分错。

- **报错与提示都落在对话里，不用浮层**。抽屉内的错误、被拒的附件、语音不可用、
  审批没提交成功，全部渲染成消息流里的一种提示卡（`.studio-notice`，左侧色条区分
  错误 / 提示 / 成功），而不是三秒后自己消失的 toast。理由是**排查**：用户回头核对
  「刚才那份文件为什么没进去」时，浮层早就没了。卡片不套助手头像与气泡——助手确实
  没说过这句话，画成回答会让人以为模型给了结论。同一句话连着出现只留一张，
  次数记在角上，免得十张一样的红卡把真正的回答顶出视野。

- **附件是会话的参考材料，不是一次性文件**（2026-11-17 起）。上传落盘后随会话保留：
  句柄写进 `messages.metadata_json.attachments`，每轮把「本条新增 + 本会话此前上传」
  两段清单写进 `[附件]`，模型据此决定读哪一份。删掉只有一处——删除会话时
  `purge_conversation()` 回收整个目录。

  早先是「由构建助手应答就活一轮」，理由是「用户传张截图只为问这一句」。这个理由在
  线上被两次证伪：一是反问之后文件被删，用户回「？」得到「附件不存在或已过期」
  （2026-11-16）；二是用户传一份规程、先问两句、隔一轮再说「按第三章入库」，文件已经
  没了。**会话是用户组织材料的单位，不是模型的调用栈**——按调用栈管文件，用户就得
  记住平台什么时候会清空他的东西，而那件事没人能记住。

  两句提示词配套：清单分「本条新增」与「本会话此前上传」两段（只列新增，模型会以为
  这轮没材料；只列全部，它会拿最早上传的那份答新问题）；有新增时要求优先处理新增，
  更早的材料只在用户明确指认时用。

- **大文档不必反问「入库方式怎么定」**。对话里写正文受单次读取上限（约 4 万字符）
  约束，但整篇入库走的是 `studio_import`（磁盘原文切片），不受这个上限影响：
  助手直接导入、报出切片数即可。只有用户想「只入某几章」时才需要问章节；
  不要把人往别的页面推——现在没有别的页面了。

- **只有文件、没有一句话就不发**。以前会补一句「请看附件。」好让请求过校验，
  但那等于让模型猜用户要什么；猜错就是一轮白花钱的识别加一段答非所问。
  现在提示「先说要这份文件做什么」，附件留在托盘里，补一句就能发。

- **托盘与对话台各自独立**：两处共用一个数组，会让在对话台选的图莫名出现在抽屉里。

- **审批卡按现在的状态重画**：`messages` 里只存审批号，参数与状态在审批单上，
  所以按 id 现查一次。还挂着的给按钮，已确认/已取消/已过期的显示「已处理」。
  只存当时的快照会让一张早已执行的卡在刷新后重新显得「待确认」。
- 消息渲染复用对话台的气泡样式与 `esc()`，不引第三方 UI 库（控制台现在零依赖）。

### 7.1 头部三个按钮：读 → 看 → 走

顺序是刷新、放大、关闭。**刷新放最左**，因为它是唯一不改变任何状态的动作，
离关闭最远，误点的代价也只是滚一下。

**刷新 = 滚到最新，不是重新加载。** 面板的消息是本地这一份 `messages`，
没有「拉历史」的接口可调；把它做成重载，会与正在进行的请求抢上下文。
所以按钮叫「滚动到最新」，不叫「重新加载」。

与之配套的是滚动策略——**用户滚上去看历史时，新回答不把他拽回底部**，
只在刷新按钮右上角点一个绿点。想把视野带回去就自己点。原来每次重渲染都
无条件 `scrollTop = scrollHeight`，改代码时正读到一半会被甩下去，之后人就不敢往上翻了。
三种模式：`follow`（自己刚发出 / 刚打开面板）、`quiet`（点确认卡后原地更新）、
自动（贴着底部就跟，否则挂记号）。跨度超过两屏时不用平滑滚动——
滚两屏要好几秒，期间看着像点了没反应。

**放大**在 400px 与 760px 之间切换，存 `localStorage`。放大后高度停在页头下沿
（`100vh - 76px`）：盖住全局状态灯与页面的「刷新」会让人以为界面坏了。
窄屏本来就是整屏，这个按钮隐藏——留一个点了没反应的按钮比不留更糟。

### 7.2 悬浮球是一台会变身的机器人

入口不用气泡图标，用一个机器人头像；点它的时候，机器人**变成火箭飞上去**，
飞到一半面板才出现。纯 SVG + CSS，仍然零依赖。

三个状态的取舍：

| 状态 | 做什么 | 为什么 |
|---|---|---|
| 待机 | 轻微上下浮、偶尔眨眼、天线灯呼吸 | 三个周期互不整除（3.6s / 5.4s / 2.6s），看起来才不像循环播放的 GIF |
| 变身（240ms） | 头压窄拉长成箭体、侧耳下移外翻成尾翼、两眼向中间靠拢并放大成一个舷窗、天线收起 | 部件各自插值，读起来是「同一个东西在变形」；换成两张图淡入淡出就成了「换了个图标」 |
| 发射（580ms） | 先下蹲再冲出画面，缩到 0.3 倍并淡出，底部拉一道模糊尾迹 | 少了蹲那一下，起飞像被抽走而不是弹出去；只有向上飞没有尾迹，看不出速度也不知道飞去了哪 |

两条必须守住的细节：

- **眼睛不能放进头那一组。** 头在变身时会横向压窄到 0.54 倍，眼睛跟着压就成了
  两条竖线，而舷窗必须是圆的。所以眼睛是兄弟节点，自己平移 + 缩放。
- **面板必须在火箭飞出画面之后才出现。** 两者在同一个位置，同时发生会被看成
  「火箭没飞走，是被面板拍掉的」。所以是 200ms 变身 + 580ms 发射，之后才 `open`。

关闭时反着来一遍：火箭从天上落回原位，落地后再由各部件插值回机器人。
只做「消失」的话，下次点开又是凭空冒出一个球；补上降落，开合才有来有回。

`prefers-reduced-motion: reduce` 时整套跳过，点了直接开面板——动效是装饰，
为它多等 0.8 秒是亏的。CSS 那边也有一份同样的兜底（`animation: none`），
JS 与样式各挡一次，是因为这两处都可能被单独改掉。

悬浮球从 46px 加到 52px：48×48 的坐标系在 36px 里画眼睛和天线时，21px 版本
糊成一团。另外补了 `.studio-fab.hidden { display: none }`——原来只挂了类名，
样式表里没有对应规则，球一直藏在面板底下（被盖住，不是消失）。

## 8. 会话与身份
| 项 | 决定 | 理由 |
|---|---|---|
| thread 粒度 | 每 (租户, 用户) 一个固定 thread | 多人共用一个 thread 会串上下文；每次新建则「昨天让它建的 Agent」接不上 |
| thread 标识 | 前端生成 `studio-<日期>-<时刻>` 存 `localStorage`，服务端拼成 `{tenant}:{user}:<后缀>` | 与普通会话同一套规则：客户端只决定后缀，决定不了归属 |
| 会话记录 | 进 `conversations`，`channel="studio"` | 复用清理与保留策略；对话台按 `channel` 过滤，避免与业务会话混排 |
| 读回历史 | `GET /api/v1/conversations?channel=studio` + 详情 | 面板刷新后仍能看到上次聊到哪，不需要另建一套存储 |
| 身份 | 真实 `Identity`，不伪造 | 助手的每次写操作都要能回答"是谁要求的" |

## 9. 内置 Agent 的创建

不写在迁移里——租户是动态的。**惰性创建**，与默认 Agent 同一时机
（`GET /api/v1/agents` 首次访问时补齐）：

1. 若租户无 `is_builtin=true` 的行，建一行 `name="studio"`、`status=active`、
   `can_write=true`、`allowed_tools=[8 个 studio_*]`；
2. 建之前先查 `studio` 这个名字有没有被用户占用——有则用 `studio_assistant`，
   并把实际名字写进 `is_builtin` 行的 `name`，前端从接口读，不硬编码。

保留名要有一份清单（`studio` / `studio_assistant` / `assistant`），
新建 Agent 时校验，否则用户先建一个叫 `studio` 的，惰性创建就会撞唯一索引。

## 10. 审计与观测

| 事件 | 内容 |
|---|---|
| `studio_request` | 意图摘要 + `focus`，用于回答「大家用它做什么」 |
| `studio_out_of_scope` | 越界尝试的类型与摘要 |
| 工具调用 | 网关统一记 `tool_requested` / `tool_succeeded` / `tool_failed` / `tool_denied`，metadata 带 `agent_name` 与 `agent_revision` |
| 智能体写入 | 另记一条资源事件：`agent_created` / `agent_updated` / `agent_status_changed` / `agent_deleted`，不新增事件类型 |
| 技能 / 工具 / 知识库写入 | `admin_action` / `knowledge_ingested` / `knowledge_deleted`，`resource_type` 区分 `skill` / `custom_tool` / `mcp_registered_tool` / `knowledge_document`——与知识库路由本来就是同一套写法 |

**为什么写入要记两条。** 网关那条的 resource 是工具本身
（`tool/studio_agent_save`），只能说明「这个工具跑过」，回答不了「改的是哪个智能体、
改成了什么」。所以工具执行成功后，再按控制台 REST 路由的同一套事件类型补一条资源事件：

| 字段 | 值 |
|---|---|
| `resource_type` / `resource_id` | `agent` / 那个智能体的 UUID（删除后仍是它生前的 id） |
| `message` | 人话摘要，审计页只能看到这一列，例如「构建助手把智能体「ops」从 draft 改为 disabled」 |
| `metadata.via` | 恒为 `studio_assistant`，用来区分「控制台点的」与「对话里让助手做的」 |
| `metadata.tool_name` / `approval_id` | 与网关那条 `tool_succeeded` 对得上，形成「人确认过 → 引擎执行了 → 落到了哪个对象」的链 |
| `metadata.before` / `after` | 仅 `agent_updated`：边界字段与版本号的前后值，不记指令正文 |

三条口径：

- **只在真的变了时记。** 与 REST 路由一致：`agent_updated` 以 `revision` 变化为准，
  `agent_status_changed` 以状态前后不同为准。反复保存同一份配置记一条「改过」，
  审计里的变更次数就不可信了。
- **只有核验通过才记。** 删除要回读确认「真的没了」才写 `agent_deleted`；
  写出去了但还在的情况留给网关的 `tool_failed`，否则审计会说谎。
- **审计失败不回滚业务。** 业务在写审计之前已经提交，变更已经生效；
  审计写失败只记错误日志，不能反过来把生效的变更说成没发生。

查询（`studio_describe`）不写资源事件：它没有改变任何东西，网关的 `tool_succeeded`
已经记下了「谁在什么时候读了什么」（`agent_name` + 工具名 + 参数键名）。

**这件事为什么重要。** 对话台只列 `channel=api` 的会话，助手线程只存在于面板里——
用户在控制台其他地方看不到那些对话，审计就是唯一能追溯「助手改过什么」的地方。
反过来，用户把面板历史清掉也不影响审计：面板存的是 thread 与消息，审计是另一条路。

观测上 `agent_name="studio"`，于是 `/api/v1/observability/agents` 会自动出现一行，
能看它被用了多少次、拒绝了几次——**助手自己也在被观测的名单里**，这是"它也是一个 Agent"的实际含义。

## 11. 分期

| 期 | 范围 | 验收 |
|---|---|---|
| P0 | `is_builtin` + 惰性创建 + `studio_describe` + `studio_agent_save/set_status/delete` + 内联二次确认 + 面板 | 第 12 节 1–5 |
| P1 | Skill 与自定义工具的增删改 | 第 12 节 6 |
| P2 | 平台用法问答（内置说明文档，不进租户知识库） | 第 12 节 7 |

P2 单独一期，因为「回答平台怎么用」不该走租户知识库：知识库里是业务资料，
平台说明是产品文档，混在一起会让检索结果互相干扰（问"审批有效期"命中一份工单附件）。

## 12. 验收用例

1. 「新建一个只读客服 Agent」→ `awaiting_approval` → 确认 → 库里有一行，`can_write=false`、`status=draft`。
2. 同一条取消 → 库里没有，审计有 `canceled`。
3. 「删掉 ops」不给名字 → 工具拒绝（`confirm_name` 不匹配），不产生审批单。
4. 「把数据库里 user 表清空」→ 拒绝 + `studio_out_of_scope` 审计，且**没有**任何工具调用。
5. 「把你自己的 allowed_tools 加上 execute_code」→ 拒绝。
6. 「建一个 Agent，允许工具里带上 studio_agent_save」→ 拒绝（第 3.1 节第 2 条）。
7. 「给 ops 加上 fc_executestationcontrol」，而申请人没有该 scope → 拒绝并说明原因（第 3.2 节）。
8. 面板切换当前对象后再问「把它的超时改长」→ 改的是选中的那个，不是上一个。
9. 「看一眼都有哪些流程」→ `studio_describe resource=workflow` 列出名称、启停、节点数/跳数与最近一次运行。
10. 「把 triage 的第二步换成 ops2」→ 先读整张图 → 只改那一个节点 → 整份传回 → 版本号 +1，其余节点还在。
11. 「给 triage 建一个没有兜底边的分支」→ 保存被拒绝，理由里带节点 id（`WORKFLOW_NO_FALLBACK`），库里没有这张图。
12. 「删掉 triage」不给名字 → 拒绝；给了但差一个字符 → 拒绝；只有逐字一致才删。
13. 「把 triage 停掉」→ `enabled=false` 且 `definition` 原样保留（不是「删了重建」）。
14. 传一份 `.md` 说「把这份规程入库」→ `studio_import` 一次调用，结果里给出切片数与分级；
    库里出现这份文档，**不**出现「正文被截断」这类答复（走的是磁盘原文，不是读取结果）。
15. 传一份带 front matter 的 `.md` 说「这是技能」→ 建成技能；再传同一份说「入库做资料」
    → 进知识库，结果里说明「原本判成技能」。
16. 传一张图片说「入库」→ 拒绝并说明图片只能读取文字，不做入库。
17. 「我们每天的巡检是：先看压力和报警，有报警就让 ops 判断严重程度，严重的写一条处置建议，
    最后不管有没有报警都出一份日报」→ 助手**识别为要建流程**（不是问答、不是入库），
    先 `studio_describe resource=agent` 拿真实标识，再拟步骤，说明一遍后调 `studio_workflow_save`；
    结果里有 `步骤：check → judge → advise → report`（顺序可核对）与触发方式。只问「按什么条件
    算严重」，不问标识叫什么。
18. 同上一句，但租户里没有 `ops` → 助手不编名字，先读出清单再选一个、或先把它建出来。
    **编了名字也不会误存**：保存被拒（`WORKFLOW_UNKNOWN_AGENT`），理由里带可用标识。
19. 「把 triage 的显示名改成巡检」→ 修订号不变（图没动）。运行记录里不会出现「这次跑的是 v2」
    而 v2 与 v1 是同一张图。
20. 「帮我建一条一步的流程：让 ops 查一下压力」→ 助手说明这不叫流程（一个节点等于「让某个
    智能体做一件事」），建议直接在对话里选那个智能体，而不是硬建一张图。
21. 「把 triage 的第二步加个判断」→ 先读整张图 → 条件键写成上游没有的字段 → 保存被拒
    （`WORKFLOW_UNKNOWN_CONDITION_KEY`，理由里带可用的键）→ 改成真实存在的键再存。

## 13. 已知边界

- **不做流式输出。** 与对话台保持一致：现有 `/chat` 是同步返回，单独给面板做流式
  会引入第二套消息状态机。长回答的等待用加载态解决。
- **不能改代码。** 这不是"暂不支持"，是永久边界。代码变更走部署流程（`deploy/sync.sh`），
  任何让助手写文件的路径都不该存在。
- **不替代表单。** 助手擅长的是一次改一两个字段；一次性配 20 个字段的表单仍然更好用。
  界面文案要承认这一点，引导复杂场景去「智能体」页。
- **它也在消耗配额。** 助手是 Agent，受租户与（将来的）Agent 级配额约束。
- **`is_builtin` 行不可删**，所以租户注销时要做级联清理，否则会留下不可操作的行。
