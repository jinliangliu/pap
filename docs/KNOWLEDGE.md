# 知识库：把「事实是什么」和「能做什么」分开

控制台「配置 → 知识库」。知识库存的是**可引用的资料原文**，
回答「这件事的规定/参数/流程是什么」，检索后带引用返回。

它不回答「这个人偏好什么」（那是[记忆](MEMORY.md)），
也不回答「这类活按什么步骤干」（那是[技能](SKILLS.md)）。

## 1. 两条入口，各自管各自的文档

| 入口 | 谁用 | 语义 | `source_type` |
|---|---|---|---|
| 页面上传 | 懂业务的人 | 一份一份加/删，立即生效 | `upload` |
| 目录同步 | 运维 | `KNOWLEDGE_DIR` 是该租户的**全集**，目录里没有的视为已删除 | `file` |

**为什么必须分开**：目录同步的语义是「以目录为准」。如果上传的文档也落在同一个
目录里，一次同步就会把页面上传的内容当成脏数据清掉。所以上传文件落在
`KNOWLEDGE_UPLOAD_DIR`，与扫描目录物理隔离，同步时也只处理 `source_type='file'`。

早期版本是「全量替换」——先 `DELETE` 掉该租户所有文档再插入扫描结果。
只有目录扫描时这没问题，接上上传之后就出事：一次同步删光所有上传文档。
现在是**每份文档独立 upsert**。

## 2. 数据模型

| 表 | 作用 |
|---|---|
| `documents` | 文档元数据：标题、文件名、来源、内容哈希、状态、分级、索引时间 |
| `document_chunks` | 切片与检索元数据：正文、序号、ACL、`is_active` |
| `knowledge_index_state` | 每个租户一个索引版本号，各进程按它热加载 |

`documents.id` 由 `uuid5(tenant_id + logical_id)` 派生——同一个 `logical_id`
在多次入库之间得到同一个 UUID，引用不会因为重新入库而失效。
`logical_id` 对目录文档是「相对路径派生」，对上传文档是首次上传时生成的 id。

### 增量判定

`upsert_document` 在写入前看四件事，全满足才跳过：

1. 状态是 `ready`；
2. `content_hash` 相同；
3. 切片数与本次切出来的一致；
4. `metadata_json.chunker_version` 与本次切片器版本一致。

第 3 条不能省：内容没变但切片被手工删过（或切片参数变了）时，
只看哈希会认为「已经是最新的」，实际上索引是残的。

第 4 条是给**切法升级**用的。标题感知切片上线时，一篇只有一个标题的文档
内容哈希没变、切片数也还是 1，但 `section` 要从「第 1 段」变成真实小节名——
前三条判据完全看不出来，会被误判成 `unchanged`，怎么同步都不变。
所以 `CHUNKER_VERSION` 写进 `metadata_json` 一起比；老行没有这个字段按版本 1 处理，
升级后第一次同步自动重建一次，之后恢复 `unchanged`。**改切片规则必须 +1**，
否则线上不会重建。有 `test_chunker_version_forces_rebuild_of_legacy_rows` 钉着。

**上传文档也要跟着升级**：目录同步只扫磁盘，碰不到 `source_type='upload'` 的行。
如果只重建目录里那批，点完「同步目录」看起来万事大吉，实际上传的文档
会永远停在旧切法（引用一律「第 N 段」）。所以同步结束后会额外挑出
「版本过期的 ready 上传文档」逐篇重切，返回里多一个 `migrated` 计数。
这里只重切、不增删文档，两条入口的存在性边界不变；原文缺失的跳过并保留旧切片，
下次同步再试。有 `test_sync_migrates_outdated_upload_documents` 钉着。

### 软删而不是硬删

下架 = `status='deleted'` + `deleted_at` + 切片 `is_active=False`。
检索层只读 `status='ready'` 的切片，所以下架**立即**生效；
保留行是为了「谁在什么时候删了什么」有据可查，也避免误删后无从恢复。

注意 `status` 列在库里存的是枚举名（`ready` / `READY`），
`native_enum=False` 的 Enum 默认持久化成员名。接口对外统一返回小写枚举值。

### 历史行的一次性迁移

早期入库脚本给 `documents.id` 用的是随机 UUID，`logical_id` 却已经存在
`metadata_json.document_id` 里。升级到「按 `logical_id` 派生主键」之后，
**第一次同步会把这批老行全部下架、再按新主键重建一遍**，
接口表现为 `created=N, deleted=N`（一行不变的内容也会重建）。

这是预期内的一次性迁移，第二次同步起就是 `unchanged=N`。判断方法：
老行的 `id` 不等于 `uuid5(tenant:logical_id)`，且 `created_at` 很早。
代价是老行永久留在 `deleted` 状态（软删不清理），见 §10。

## 3. 入库链路

```
字节/文件 → 排除规则 → 文本抽取 → front matter(ACL) → 切片 → 上限 → upsert → bump 版本
```

**排除规则**（`is_excluded`）：密钥、凭据、备份、日志、构建产物、二进制一律不入库。
上传走同一套规则，传一个 `id_rsa.md` 上来同样被拦。

**文本抽取**：`.md/.markdown/.txt` 直读；`.pdf` 走 pypdf；`.docx` 走 python-docx；
`.html/.htm` 走 BeautifulSoup。上传走 `extract_text_from_bytes`，与磁盘文件共用同一套解析。

> 上传是**先解析、后落盘**：解析失败时磁盘上不该留一个永远不会被索引的孤儿文件。

**切片**：先按标题分节，再在节内按自然段累积到 800 字符，相邻保留 120 字符重叠；
单段超长时按窗口滑切。Markdown `h1–h3` 与「一、xxx」这类中文编号都算标题，
只认 `1. xxx` 之外的形式（那是有序列表，认了会把操作手册切成一堆碎片）。
代码围栏里的 `#` 注释不当标题。

标题行**留在正文里**：BM25 命中标题词本来就是强相关信号，丢掉反而变差。
每个切片带一个 `section` 标签，取最近两级标题拼成「手册 / 压力阈值」；
同一个小节被切多片时补「（1/3）」这样的序号。没有标题的文档（PDF / Word / HTML
抽出的纯文本、无标题 txt）回落到原来的自然段切片，标签仍是「第 N 段」。

检索引用展示的就是这个标签——「第 12 段」对用户没有定位价值，
「阀门停机规程 / 压力阈值」才有。

单篇超过 `KNOWLEDGE_MAX_CHUNKS_PER_DOCUMENT`（默认 400）直接报错，
**不静默截断**——截掉后半本手册会出现「看起来能用但永远查不到后半部分」的缺陷。

**ACL**：`---` 头信息优先，其次按路径猜（含 `confidential`/`机密` → confidential）。
`user_private` 没有 `owner_user_id` 直接拒绝入库——宁可少入库一份，
也不能把「本该私有」的文档变成全员可见。

**版本号**：写入后 `bump_version`，同时主动 `invalidate` 本进程缓存。
不主动清的话「刚上传就检索」会因为 5 秒轮询拿不到新内容，用户只会以为上传失败。

## 4. 权限

| 操作 | 要求 |
|---|---|
| 看列表 / 详情 / 检索 | 登录即可，但按 `access_scope` 过滤（`public` / `internal` / `confidential`） |
| 上传 / 重建 / 下架 / 同步目录 | `knowledge:write` 或平台管理员 |
| 上传 `confidential` 文档 | 还要持有 `knowledge.confidential` |

分级不够时**按 404 处理**，不返回 403：403 等于告诉对方「这里有一份你看不到的文档」。

检索侧的过滤发生在排序之前（`retriever._is_visible_for`），未授权内容不会进入 BM25
候选，更不会进入模型上下文。**不要改成「先检索再让模型忽略」**——那时内容已经在上下文里了。

## 5. 检索

BM25 + jieba 分词，默认召回 4 条。相关性前提是「查询词与切片有交集」，
BM25 只负责排序。

**索引文本包含标题与 section**（`retriever.index_tokens`）。原先只索引 `text`：
标题行虽然留在 Markdown 正文里，但 PDF / Word / HTML 抽出的纯文本没有标题，
`section` 只是「第 N 段」，文件名（`title`）里的「approval_policy」「平台能力说明」
这类词一次都没进过索引。现在按 `KNOWLEDGE_TITLE_BOOST`（默认 2）与
`KNOWLEDGE_SECTION_BOOST`（默认 1）把字段分词重复若干次并入同一套 BM25，
等价于 ES 的 `copy_to` + boost；不建第二套索引，因为小语料下第二套的 IDF
会整体为负，加权只会放大噪声。设 0 回到只索引正文。

字段加权只缓解「词在标题里」的漏召回，**治不了同义词与口语化提问**：
零字面交集仍然返回 0 条，那需要向量通道（见 §TODO P1）。

**查询侧同义词扩展**（`knowledge/synonyms.py`）是登记式词表，默认关闭
（`KNOWLEDGE_QUERY_EXPANSION_ENABLED=false`）。只改查询侧——索引侧扩词会把
avgdl 与 IDF 一起弄脏。它是廉价补丁，不是解法：覆盖不到没登记的说法，
扩词还会带进更多假阳性（交给重筛剔除）。开启前先用评测脚本做 A/B。

**分词要剔虚词和标点**（`retriever.tokenize`）。索引侧和查询侧必须用同一个函数：
只在查询侧删，语料里仍留着「的」这类高频词，avgdl 被虚词撑大、长度惩罚就算错，
而且虚词挨着 `epsilon` 拿到正权重后照样能挤进前四。实测过一条反面案例——
查询「描述一下你的能力」时，排第四的切片**只靠一个「的」字**命中。

停用词表只收「单看几乎不携带信息」的词。`前 / 后 / 上 / 下 / 时` 这类不能删：
「停机前」和「停机后」是两条规程，删了就分不清。数字与带数字的串（`2.31`、`k10`）
必须保留，压力值、版本号本身就是检索目标。

**阈值有两层**：

| 配置 | 含义 |
|---|---|
| `KNOWLEDGE_MIN_SCORE` | 绝对下限，**只对正分生效** |
| `KNOWLEDGE_MIN_RELATIVE_SCORE` | 相对下限，低于第一名这个比例的直接丢，`0` 关闭（默认 0.3） |

绝对阈值实际拦不住东西：BM25 分数没有量纲，7 个切片时 0.4 可能毫不相关，
700 个切片时 0.4 可能是最相关的一条。所以真正起作用的是相对阈值。

`min_score` 只对正分生效的原因：小语料下 BM25 的 IDF 会整体为负
（词出现在全部文档里时 IDF < 0，`epsilon` 也抬不回正数），
这时分数只代表相对排序、没有绝对意义。拿阈值去卡，会把「唯一一份资料」判成不相关——
新租户传完第一篇就搜不到，看起来像上传失败。这个缺陷有回归测试钉着
（`test_single_document_corpus_still_returns_hits`）。相对阈值同理，只在第一名是正分时才裁。

分数接近 0 是正常的，不代表不相关。

**检索分两步，答复始终不经模型生成**：

1. **召回**：`retriever.search` 在 ACL / 分级过滤之后按 BM25 取
   `KNOWLEDGE_RERANK_CANDIDATES`（默认 12）条。召回阶段把两个阈值都关掉——
   语义相关但 BM25 低分的片段必须先有资格被判定，否则重筛还没开始就被裁掉了。
2. **语义重筛**（`knowledge/rerank.py`）：把候选逐条交给**当前生效的 chat 模型**
   判「是否真正提供了问题所问的那类信息」（0/1/2 三档，只保留 2 分），
   返回保留编号。模型不重排序、
   不改写原文、不生成结论；最终仍按 BM25 相对顺序取 `KNOWLEDGE_TOP_K` 条，
   拼进 `KNOWLEDGE_HEADER / EXCERPT / FOOTER` 模板（每段截 400 字）直接返回。

这一步解决的是 BM25 治不了的**实词假阳性**：「描述一下你的能力」里，
「不得将失败**描述**为成功」是字面对上、语义无关。停用词与相对阈值清不掉它。

约束：

- 候选全部来自已过滤的检索结果。扩大召回池**不是**放宽权限，
  `confidential` 内容绝不会因此进入模型提示词（有回归测试钉着）。
- 模型只做保留/剔除。判定口径必须区分「回答了问题」与「只是同一主题」：
  实测过「宽松保留」会把讲安全禁令、技术原则的片段都判成相关，
  最关键的假阳性仍排第一。让模型输出顺序决定摘录次序，同一问题每天会得到不同答案。
- `{"keep": []}` 是合法判定（全部无关），返回「资料不足」，**不能**当作解析失败
  回落成假阳性。
- 任何异常都回落到原始 BM25 结果：模型未配置、超时
  （`KNOWLEDGE_RERANK_TIMEOUT_SECONDS`，默认 8 秒）、调用报错、输出不是合法 JSON、
  编号越界。检索是主链路，不能被一次可选增强拖成 500。
- 代价是每次知识问答多一次模型调用；`KNOWLEDGE_RERANK_ENABLED=false` 可完全关掉，
  检索链路不再发起任何模型请求。重筛不在 LangGraph 节点里，不进 `obs_traces`，
  诊断看 INFO 日志 `knowledge_rerank_applied` / `knowledge_rerank_fallback`
  与 `/search` 的 `rerank` 字段。

**关键词串不要另做一套判据**（2026-11-15 查证）：拿「调压箱 泄漏 通风」这类串去搜
返回 0 条时，第一反应往往是「判据把关键词串当问句判，所以全被剔了」。实测否掉了这个
猜测——库内确有相关内容时，严格口径与另写的「覆盖口径」四次比对**结果完全相同**；
差异只出现在内容本就缺失的查询上，多留的是边缘条目。那次改动做了一半就撤了。**0 条在这里是「资料不足」的正确答案**，改判据只会让边缘内容混进来。

空答复分两种，不能说同一句话：「一条都没召回」用 `KNOWLEDGE_EMPTY_ANSWER`，
「召回后全被重筛剔除」用 `KNOWLEDGE_REJECTED_ANSWER` 并带上剔除条数。
严口径下后者会变多，若混成「资料不足」，用户会以为检索链路坏了。

### 检索评测：改检索之前先量一次

`tests/fixtures/knowledge_golden.json` 是 25 条标注集：21 条可回答（标了应命中的
`source_path`）、4 条库里本就没有答案。**后者命中算假阳性，不是「查到了」**。
新增文档或改切片规则后必须重跑，不要改期望值迁就结果。

```bash
uv run python -m scripts.eval_knowledge                  # local：纯 BM25 召回上限
uv run python -m scripts.eval_knowledge --no-boost      # 关掉字段加权做对照
uv run python -m scripts.eval_knowledge --expand        # 打开同义词扩展做对照
uv run python -m scripts.eval_knowledge --mode http \
  --base-url http://127.0.0.1:8000/api/v1 --subject <已认证主体>
uv run python -m scripts.eval_knowledge --json report.json --fail-under 0.90
```

- `local`：直接扫 `data/knowledge`，不连数据库、不调模型，可进 CI。与线上
  `_retrieve` 的**召回阶段**同参（关掉两层阈值），量的是「能不能取到」。
- `http`：打 `/knowledge/search`，含 ACL 过滤与语义重筛，量的是端到端结果。
- 指标：`Hit@k`、`MRR`、`answerable_zero_hit_rate`（可回答却零召回 = 召回上限的
  直接证据）、`false_hit_rate`（不可回答却返回内容）；http 模式另统计重筛
  生效 / 回落原因 / 剔除数 / 耗时分位。**两种模式的假阳性率不可直接比较**，
  local 高是词面撞词的预期表现，重筛在下游负责。

2026-11-09 基线（6 篇 / 25 切片，`top_k=4`）：

| 配置 | Hit@4 | MRR | 可回答零召回 | 假阳性率 |
|---|---|---|---|---|
| 默认（字段加权开） | 0.9524 | 0.881 | 0 | 0.50 |
| `--no-boost` | 0.9048 | 0.8333 | 0.0476 | 0.50 |
| `--expand` | 0.9524 | 0.9048 | 0 | 0.50 |

字段加权把 `approval_policy`（只出现在文件名里）从 0 条变成命中，这是它唯一
可证明的召回收益；同义词扩展把「描述一下你的能力」「你会做什么」的正确文档
提到第一位（MRR +0.024），却把「远程服务」那条从 1.0 压到 0.5——
**净收益很小，因此默认关闭**。基线里还留着一条已知 miss：问「幂等键在哪里使用」
时，`notes/使用说明.md` 的四个切片占满 top4，把真正含答案的审批策略挤出去，
见 §10。

线上端到端基线（2026-11-09，部署 `c35d4e1` 并同步目录后，7 篇 / 118 切片，
`--mode http --subject pap-admin --k 4`）：

| 指标 | 值 |
|---|---|
| Hit@4 | 0.9048 |
| MRR | 0.9048 |
| 可回答零召回率 | 0.0952（2/21） |
| 假阳性率 | 0.0（4 条无答案用例全部返回资料不足） |
| 重筛 | 25/25 生效、无 fallback、共剔除 201 条，p50 896ms / p95 1181ms |

`http` 模式的语料比标注集多了页面上传文档，且经过严口径重筛，所以 Hit@4 与
`local` 的 0.9524 **不是同一口径**，别拿 local 数字当线上门禁。两条 miss 都不改期望值：

- `meta-capability-colloquial`（「你会做什么」）：只召回 3 条且全被剔除。补了
  《平台能力说明》仍召回不到，原因是查询与文档零词面交集——**这就是召回上限的实测证据**。
  `--expand` 能把能力文档提到第一位，但默认关闭（见上）。
- `idempotency-key`：12 条候选全被重筛剔除，local 的「同一文档刷屏」缺陷之外
  又叠加了严口径的代价，见 §10。

## 6. 页面

| 区块 | 内容 |
|---|---|
| 索引状态 | 文档数、切片数、索引版本、后端、知识目录、可检索范围 |
| 文档 | 标题+文件名 / 来源 / 分级 / 切片数 / 大小 / 状态 / 更新时间 / 操作；卡片头放大镜可筛选 |
| 行展开 | 该文档的切片原文（等宽、按 Markdown 原样显示），用来核对「检索到的到底是什么」 |
| 检索验证 | found、citations、每条命中的 score；引用标题可点击；语义重筛是否生效、剔除几条、耗时 |

**文档筛选是前端筛选，不是搜索接口**。点「文档」卡片头的放大镜展开输入框，
按标题 / 文件名 / 原始路径做子串匹配（大小写不敏感），输入即时生效；
计数 chip 变成「匹配 N / 共 M 篇」，空结果与「还没有文档」分开说。

三个有意的取舍：

- **只筛已加载的那一批**（`KB_DOC_LIMIT = 200`）。接口返回的 `total` 是过滤后的条数、
  不是库里的总数，所以拿不到真实总量；命中上限时筛选条显示「仅在前 200 篇内筛选」，
  不假装筛过全库。真要全库搜索得给接口加 `q` 参数。
- **收起筛选条 = 取消筛选**。留着过滤后的列表却把输入框藏起来，人会以为文档丢了。
- **引用跳转命中被筛掉的文档时自动清空筛选**并提示，否则链路上看起来像「引用打不开」。
  同理，上传成功后清空筛选——新文档标题多半不匹配当前关键词，
  不清的话会出现「提示成功但列表里没有」。

**引用可点开**：对话页与检索验证页的每条引用都能跳到知识库页，自动展开对应文档
并高亮命中的那一个切片。链接形如 `#/knowledge?doc=<logical_id>&chunk=<chunk_id>`，
`chunk_id` 末四位就是切片序号。

这里有两个容易踩的坑：引用的 `document_id` 是**逻辑标识**，不是 `documents` 表主键，
要先用 `logical_id` 在列表里换成 UUID；详情接口每页 50 条，引用可能指向第 51 条之后，
得按序号算出 `offset` 再请求，否则永远高亮不到目标、还会误高亮第一段。
查找行时不要用 `CSS.escape` 拼属性选择器（它转义的是标识符，UUID 常以数字开头，
放进 `data-id="..."` 的值里反而匹配不上），直接比对 `dataset` 最稳。

失败的行会把 `error_message` 直接显示在标题下面——只显示「失败」等于让人去翻日志。
没有写权限时整个操作列都不渲染，而不是留一列空按钮。

窄屏（≤1120px）隐藏「来源」与「大小」两列：文件名已经在标题下面，大小可以点开详情看；
时间与状态留着，那两列才是判断「这份文档可不可用」的依据。

## 7. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/knowledge/status` | 索引状态 |
| GET | `/api/v1/knowledge/documents` | 文档列表（含 `can_write`、白名单、上传上限） |
| GET | `/api/v1/knowledge/documents/{id}` | 详情 + 切片（`limit` / `offset`） |
| POST | `/api/v1/knowledge/documents` | 上传（multipart，`file` / `title` / `access_scope`） |
| DELETE | `/api/v1/knowledge/documents/{id}` | 下架 |
| POST | `/api/v1/knowledge/documents/{id}/reindex` | 按原文重切 |
| POST | `/api/v1/knowledge/reindex` | 目录增量同步 |
| POST | `/api/v1/knowledge/search` | 检索验证（请求 `{query, limit}`，`limit` 决定返回条数；响应含 `rerank` 诊断） |

`limit` 曾经被接口吞掉（无论传什么都固定用 `KNOWLEDGE_TOP_K`），2026-11-09 修好：
现在透传到 `answer_from_knowledge` 的 `top_k`，评测脚本才能测 Recall@k。

`rerank` 字段：`applied` 是否生效、`fallback` 回落原因、`candidates` 召回条数、
`dropped` 剔除条数、`elapsed_ms` 耗时。验证页据此区分「模型判定全不相关」
和「重筛故障回落」——只看结果变少是分不清的。

**上传是幂等的**：同一份内容重复上传会复用原文档（按 `content_hash` 查），不会变成两份。
只对 `ready` 状态的去重——下架或失败的不算「已存在」，重新上传会新建一行。

写操作落 `ADMIN_ACTION` 审计，只记文件名、大小、分级与操作类型，**不记正文**。

## 8. 运维

```bash
# 目录增量同步（与页面「同步目录」同一套逻辑）
uv run python -m scripts.ingest_knowledge --tenant default
# 额外留一份 JSON 快照（排查用，不参与运行时检索）
uv run python -m scripts.ingest_knowledge --export-json
```

重建单个租户的索引不需要重启：切片在 PostgreSQL，进程内只是按版本号刷新的派生结构。

但**改检索侧代码（分词、停用词表、字段加权）必须重启进程**：索引指纹只在入库时变，
只改代码不动数据的话，旧进程会一直拿着旧词表，表现为「改了没生效」。
字段加权的开关在 `.env`，改完同样要重启；`scripts/eval_knowledge.py` 的 local 模式
是独立进程，不受这个缓存影响，适合改配置前后各量一次。

**升级切片规则之后点一次「同步目录」即可**，目录文档和上传文档会一起按新规则重切
（返回里的 `migrated` 是上传文档的重建数）。不需要逐篇点「重建」，也不需要停机；
第二次同步就会回到 `unchanged`，不会反复重切。

上传文件按租户落在 `KNOWLEDGE_UPLOAD_DIR/<tenant>/<document_id><ext>`，
文件名用文档 id 而不是用户给的名字（那是不可信输入，`../` 与同名覆盖都要处理），
原始文件名单独存在 `documents.filename`。

## 10. 已知边界

- **没有向量检索**：召回仍是 BM25 关键词，同义词、口语化提问的**召回上限**受限于
  词面交集——模型重筛只能从召回池里剔除错误结果，救不回一个从没被召回的片段。
  典型历史案例：问「描述一下你的能力」，排第一的切片靠「不得将失败**描述**为成功」
  拿到 1.997 分；现在语义重筛会把它剔除。阶段 0 补了《平台能力说明》之后，
  线上评测里「你会做什么」**仍只召回 3 条、且 3 条全被剔除**（Hit@4 的两条 miss 之一）：
  补语料解决的是「有资料可引用」，解决不了「查询与资料零词面交集」。
  阶段 0 的字段加权与登记式同义词表只分别缓解「词在标题里」和「已登记的说法」，
  和「已登记的说法」，都不改变这条上限；彻底解决要 embedding + RRF 融合，见 §TODO P1。
  开放式元问题另补了《平台能力说明》，那是补语料，不是改检索口径。
- **「零词面交集」对现场类问题并不成立（2026-11-15 实测）**：上一条讲的是
  元问题（「你会做什么」）那种情况，**不要外推**。拿 23 条现场问题跑探测，
  结果是 `空 0 · 扣 21 · 中 2`——一条都没落到「零召回」，因为 `阀 / 压力 / 报警 /
  处理 / 作业` 这些通用词在《技术规范》里到处都是，每条都能召回 5–12 条，
  只是召回来的全是产品标准条文、被重筛正确剔除。  所以现场类问题的病根是
  **语料形态**（只有产品标准，没有运行规程），补语料即可解决，不必上向量检索。
  **同日已用内存预演验证**：基线 0/4 → 叠加同类规程后 4/4，top1 全部落在新资料上；
  而把同样内容写成「整段一块、section=正文」也是 4/4 —— 说明切片形态不影响**命中**，
  只影响留下的是几条独立步骤还是一条整块。切片质量的代价落在「回答能不能照着做」，
  不在「搜不搜得到」。
- **同一文档会占满 top-k**：`retriever.search` 不做来源去重，评测集里的
  `idempotency-key` 用例就是 `notes/使用说明.md` 的 4 个切片把真正含答案的
  `notes/approval_policy.md` 挤出榜单。行业做法是 MMR 或「每文档最多 N 条」的
  结果多样化；改动会动线上排序，先用 golden set 钉住这条基线，等真实语料上量再开工。
- **重筛增加一次模型调用与最长 8 秒等待**：问答链路延迟上升，模型侧费用按调用计费。
  重筛是三档打分后取 2 分，判定本身仍会误判（尤其问题短、意图模糊时）；
  口径偏严、宁可返回「资料不足」也不塞沾边片段，并在任何异常下回落 BM25。它不在 `obs_traces` 里，只留 INFO 日志与 `/search.rerank`。
- **引用只定位到切片，不定位到句子**：高亮的是整段切片（最多 800 字符），
  命中词没有二次标注。要精确到句子需要检索层回传 term 位置，目前没有。
- **标题层级最多记两级**：更深的小节会折成「父 / 子」，避免长文档里出现
  「A / B / C / D / E」这种没法读的标签；同名子标题不区分。
- **没有并发上传队列**：多选上传是串行逐个 POST，进度只有「第 2/5 个」，
  没有单文件百分比（文件本身也不大）。
- **软删不清理磁盘**：下架后原文文件仍在上传目录里。要彻底清理得配一个保留期任务。
- **软删不清理行**：`documents` / `document_chunks` 的 `deleted` 行一直留着，
  连同上一条一起归属「保留期清理任务」，目前没有。历史迁移留下的死行同理
  （它们的 `id` 不是由 `logical_id` 派生的，永远不会被重新命中）。
- **日志键名不能撞 `LogRecord`**：`logger.info(extra={...})` 里用 `created` /
  `message` / `filename` 这类保留字段会抛 `KeyError` 让接口 500，
  而且测试默认 WARNING 级别不构造 record，本地全绿、线上才炸。
  已统一加 `_documents` 后缀，并有 `test_sync_logging_survives_info_level` 钉住。
